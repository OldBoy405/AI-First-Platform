## 分析范围与依据

- **分析对象**：AIFI-45 / `CR-FS-2026-004`。时间从 10-18 11:52Z 到 10-21 06:45Z；截至复盘时点，CR 停在 `writing-back`。
- **评论证据**：Issue 共 89 条评论。Agent 72 条，其中协调者 25 条；Ray 15 条；系统 2 条。约 16 条涉及 `blocked`。
- **代码证据**：
  - 本机 tools `main@9e41ad7`（与 `origin/main` 一致）
  - 本机 multica `main@f6e90ab80`
  - 复盘时平台保存的 Agent instructions（`multica agent list`）

评论反映本次运行的历史行为，本机代码反映上述 SHA 的实现；二者不一致时，先核实线上部署版本、旧 run 与实际调用路径，不能据历史现象认定当前代码仍缺少对应能力。

## 总体结论

本 CR 的主要摩擦来自两类问题：

1. **权威边界不清或交接未完成**。评审额度被重复裁决，审批结果已记录但尚未消费、发布，主干解析存在独立实现，Agent 部署文本与源文件不一致。问题不在副本数量本身：缓存、历史证据、签名凭证和执行记录各有用途，不应一律删除。
2. **同一动作有多个派发通道**。平台 Runner、Agent 之间的 @直连、协调者转派并存，产生纯中转；但删除 Agent 接力前，必须先打通 Runner 对应阶段的恢复路径。

15 次人类介入中，可辨认的业务裁决有 4 次（3 次审批、1 次开第二轮），其余主要用于排障、配置和交接。减少这些往返是合理目标，但不等于所有检查都是冗余：生成一致性、运行版本兼容、签名和落点校验仍有独立作用。

因此，方向是**消除重复维护和重复裁决，不追求消灭所有副本；先修复已发生的断点，不借减负之名重构整套流程**。

## 三、3 次 loop 用完后，评论开第二轮为何无效、重置后为何还要多转一手

### 3.1 评论不生效：授权与执行能力落在了不同的 run

1. crctl 已支持非 TTY 的认证人类继续入口。授权来自平台注入的任务绑定、人类成员身份、来源评论 ID，以及对应角色 owner 校验；`--continue-reason` 只是说明文本，不是授权本身。code 评审对应 `owners.development`，同一来源指令不能重复开启 cycle。
2. Ray 的评论 `01a15c4c` 直接触发的是**协调者**的 run（#65）。这个 run 持有认证触发事实，但 instructions 禁止它执行受控写命令。
3. 协调者 @ reviewer 后，后者由 Agent 触发，不能继承原评论的认证事实；help 又仍称“仅限交互式终端”，于是停止（#66）。
4. 协调者让 Ray 开终端（#67），又遇到 crctl 不在 PATH（#68），最终用 node 全路径完成重置（#69）。

应让收到明确“继续”指令的 run 调用既有 reset 入口，按 help 提供 CR-ID、`--loop`、`--reason`、`--workspace` 和 `--continue-reason`；不转交授权，不把任意成员评论视为继续，也不删除 TTY 运维恢复入口。

### 3.2 重置后不派作者：恢复路径未接通，旧接力又增加中转

- **F1**：crctl 已开启 cycle 2，但 Runner 仍停在耗尽结果。节点唯一键没有 cycle，投影还会拒绝较小 attempt；简单把 attempt 重置为 1，可能复用旧任务或被判为过期。Runner 节点 attempt 与执行重试不能整体删除。
- **恢复入口**：当前 CLI resume 只调用需求流水线接口，不能直接接管 code 阶段的“重置后派 implement-code”。这不是只改 prompt 或把 `failRun` 改成等待即可完成的小改。
- **F8、F9**：旧 instructions 要求 reviewer 与作者直连，于是协调者 @ reviewer（#71），reviewer 仅转交并复述 canonical `code.yml` 的 blocker（#72），没有产生新的业务价值。

删除接力规则必须与对应阶段的 Runner 恢复能力一起上线：新 cycle 能准确派到 repair-target，重复恢复不重复派发，旧 cycle 证据不能推进新 cycle。否则只同步文本会留下“无派发方”的断点。

## 四、减负建议：修复断点，删除重复操作，复用现有能力

### 4.1 原则

1. **区分业务事实、执行记录与历史证据。** 同一事实不由多处独立裁决，但保留有用途的投影、缓存、凭证和执行幂等记录。
2. **复用已有解析和交接原语。** 不新建主干解析器、审批续跑机制或公钥配置链路；保留现有兼容行为。
3. **一个动作，一个调度者。** Runner 接管某阶段后删除对应 Agent 接力；恢复能力与文本切换配套上线。
4. **授权与受控执行在同一 run。** 明确的人类继续指令走既有认证路径，不能用转述、评论 ID 参数或 Agent 自报替代认证。
5. **在节点交接前完成发布，而非每次写入都推送。** 复用 checkpoint 和现有事务边界，不把减负扩成 Git 事务层改造。
6. **评论只写结论、必要错误和链接。** 删除固定快照和全文复述，保留签名、白名单、owner、生成一致性及运行版本兼容校验。
7. **只修已证实的断点。** 不新增通用状态机、Agent、审批类型、对账框架或全局去重账本，不做单 CR 特例。

### 4.4 可以删除的负担与必须保留的检查

- **可以删除**：协调者转述机器事实、reviewer 纯转交、评论固定快照、重复提交，以及已由部署和 Runner 接管的 prompt 路由副本。
- **保留生成一致性与运行 digest 校验**：单一模板来源仍可能被错版本生成或部署，不能因 F10 归一就删除检查（`runner.go:1128–1131`）。
- **保留目标 spec 落点校验**：`TARGET_SPEC_AUTHORITY_DRIFT` 当前比较 `cr.md` 与 `_backlog.yml` 的 `target-spec-id`（`workspace-transactions.mjs:274–293`），与删除评论快照无关。只有冗余字段实际移除后，才删除相应对账分支；缺失、非法落点仍须拒绝。
- **不批量删除巡检与安全边界**：`review-alignment` 等按具体检查项判断是否失去对象，不能整套视为副本成本；签名、owner、白名单和发布落点校验不在本次删减范围。
