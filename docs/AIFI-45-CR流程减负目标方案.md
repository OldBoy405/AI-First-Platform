# AIFI-45：CR 流程减负目标方案

> 版本：v0.1
>
> 状态：设计共识已确认，待按正式 CR 流程实施与验证。
>
> 依据：[原复盘](./AIFI-45-CR流程复盘与减负建议.md)及围绕该复盘完成的 Q1–Q23 设计访谈。本文独立成文，不修改原复盘。

## 1. 定位、目标与边界

本方案不是把原复盘 R1–R12 原样转成实施清单，而是从“为什么需要人介入”重新确定现有 CR 流程的目标。历史现象、当前源码事实与未来设计分别表述；本文的设计确认不等于代码已实现、平台已部署或现行门禁已变更。

### 1.1 首要目标

**节省人类注意力，安全性质不降低。** 人应处理业务取舍、授权和确需责任人介入的异常，而不是搬运命令、转述机器结果、手动派发下一步或机械增加评审额度。

- 面向现有 CR 的通用协作流程，不做 AIFI-45 单例特化，也不扩大为通用工作流平台。
- 允许质疑现有阶段、固定产物、审批数量与角色分工，不预设“把现有流程自动化”就足够。
- 授权可信、权限受控、证据可追溯、交付落点与版本正确是底线；具体检查和实现机制可以替换，但不能因减负而批量删除安全边界。
- 不以评论数或派发跳数下降替代效果验证，不承诺技术阻断归零。

### 1.2 不做什么

不另建工作流引擎、中央流程总账或全局去重账本；不新增 Agent 来承担纯转交职责；不把所有 Git 操作收归一个入口；不把项目资源、本地目录布局、仓库绑定与授权范围混为一个事实。保留仍有用途的执行记录、投影、缓存、凭证和历史证据。

## 2. 目标流程

下图只描述决策与责任，不是另一份 CR 状态机；正式状态与转移仍以 tools 权威声明为准。

```text
收到请求
  → 判断是否来自有权者、是否明确要求实施、授权包是否充分
      ├─ 不充分：调查可查事实，只向人补问关键取舍或授权
      └─ 充分：绑定授权包，进入执行，不重复设置阶段性人工确认
  → 在授权与执行上限内实施、验证
      ├─ 需要扩大授权或执行未授权敏感动作：暂停相关动作，申请明确授权
      ├─ 测试或评审阻断：在剩余额度内派发修复，再验证
      │    └─ 额度耗尽或连续两次无进展：停止自动修复并升级
      ├─ 环境、凭据、部署等故障：按既有有界恢复路径处理，必要时找维护责任人
      └─ 验收与独立验证通过：完成约定交付，发布事实并通知结果
```

人工门围绕风险、承诺和授权变化设置，不围绕“又进入一个阶段”机械设置。授权范围内允许调整实现、拆分任务与修复问题。

## 3. 授权与风险合同

### 3.1 授权单位

一次授权必须能明确对应以下内容，执行上限可引用授权者已接受的默认规则：

| 内容 | 需要说清什么 |
|---|---|
| 目标 | 要解决什么问题，不把实施中的新想法自动纳入 |
| 允许变更范围 | 哪些对象与行为在授权内，约定交付到哪里 |
| 验收标准 | 用什么结果与证据判定完成 |
| 禁止事项 | 哪些动作或边界不得突破 |
| 执行上限 | 使用的修复额度及适用限制 |

可信来源中的原始请求若已包含充分内容并明确授权实施，可以直接构成授权，不必整理完再要求同一个人确认一遍。缺少关键业务取舍才补问；可从环境查到的事实由 Agent 调查，技术实施细节不一概交给人决定。

Agent 自行提出的范围扩张、他人转述、评论 ID 参数或 Agent 自报，不能替代可信的人类授权事实。改变目标、扩大范围、放宽验收或突破限制，必须重新获得相应授权；不能先改文档，再把越界操作解释为合法。

### 3.2 风险判断与敏感动作

按潜在损害、影响范围、可逆性和验证把握判断风险，不按文件数、代码行数或所属阶段判定。Agent 可以提出风险评估，不能自行豁免强制授权项。风险不清时先调查；关键不确定性仍无法消除时升级，不默认低风险放行。

普通实施授权覆盖实现、验证及约定的仓库交付，**不默认包含**：

- 生产发布；
- 破坏性数据操作；
- 权限扩大；
- 未经授权的对外承诺或支出。

以上动作需要针对性的明确授权，可以在初始请求中一次给出，也可以后续补充；授权已明确覆盖时不重复审批。授权实施不等于授权任意上线，已有费用授权也不等于允许新增对外支出。

授权及验证证据必须适用于实际执行范围与版本。材料变化涉及授权边界时重新授权；不能以旧版本批准或旧 cycle 证据错误推进当前执行。

## 4. 有界自动修复

### 4.1 首版采用资源代理，不承诺费用预算

第一版以**累计修复次数**约束自动执行规模，不同时引入完整费用、token 或运行级耗时记账系统。它是资源代理，不是实际费用保证；既有节点时限和有界执行重试继续有效。

默认额度为：**每个 CR 累计最多 6 次修复尝试。** 这是待代表性回放验证的试运行初值，不是已经证明最优的数字。可由事先授权明确覆盖默认值；追加额度必须显式授权、记录追加量并保留历史，不能把累计消耗清零。

### 4.2 计数合同

| 情形 | 处理 |
|---|---|
| 首次正常实施 | 不计入修复额度 |
| 因测试或评审失败而启动一次纠正性修复 | 计一次，修复失败也计入 |
| 同一次逻辑修复被重复投递或恢复 | 不重复扣额度，不重复派发 |
| 同次修复内部的命令、提交或有界执行重试 | 不按命令或提交另算一次修复；不能借此无限执行 |
| 切换阶段、重置 cycle | 继承 CR 累计消耗，不重新获得额度 |
| 达到授权总额 | 不再派发新的修复，携证据升级 |

以既有执行身份识别逻辑修复，不以评论、报告或提交数量计次。正常实施中的自测失败不按每条测试重复扣数；进入纠正性修复执行时，按上述合同累计。

轮数可作为自动诊断信号，不再天然构成人工审批门。重置 cycle 是恢复动作，不是新的授权来源；不能通过重置、改阶段或重复恢复规避累计上限。

### 4.3 无进展停止

连续两次修复后，同一根因仍造成阻断，且没有以下任一实质进展时，停止当前自动修复循环并升级：

- 验证结果有可核验的改善；
- 有效排除相关假设，并产生足以改变后续判断的实质新证据。

同一 blocker 尚未消失，不必然等于无进展；blocker 数量减少也不是唯一标准。重复运行未改变输入、改写措辞、扩写日志或作者自称“已改善”，不能算进展。判断必须引用测试、诊断或独立评审证据；独立评审负责核验上述进展，不能以笼统的“其他进展”豁免停止条件。

停止通知要说明剩余阻断、已尝试路径、停止原因及所需动作，不能只让人回复“继续”。不为诊断另开不受同一边界约束的无限循环。

## 5. 验收与独立验证

- 保留交付前独立验证；中间评审按风险与决策需要安排，不为每份中间材料机械设门。
- 作者不能仅凭自报 PASS 完成交付；独立评审必须检查实际差异和适用的可运行证据，而不是复述作者结论。
- 其他实质变更保留独立评审及适用测试。
- **只有可证明无语义变化的机械变更**，才允许由独立执行的确定性检查替代 Agent 评审，例如满足约束的纯格式化，或相同输入与工具下的可复现生成。
- 生成规则、输入或工具自身发生语义变化，不能仅凭“生成结果可复现”获得免审；业务规则、授权说明、验收标准的修改也不是机械变更。

人工审批减少不意味着验收标准降低，也不意味着独立验证者有权扩大授权。

## 6. 文档按持续有效的信息组织

不将“常规变更”和“需要长期维护的规则”当作互斥分类。很小的变更也可能改变长期规则；很大的实现调整也可能不改变任何对外约定。

判断内容是否进入长期事实源，问三个问题：CR 归档后是否仍需以它为准？是否改变系统应如何工作的约定？是否包含代码不能直接解释的重要决策与约束？

- **每个 CR**保留最小变更与验证记录，能追溯目标、范围、授权、结果与证据，不要求重复抄写机器账本。
- **长期规则变化**更新对应的现有权威配置、契约、规则说明或基线，不为每次 CR 复制一套规范。
- **独立且重要的决策**在现有载体不足以表达时新增设计文档；不固定 PRD、SDD、计划等文件套餐。
- 能从代码、schema 或配置可靠生成的事实不手工复写；仍需保留不能自动推导的理由、取舍与限制。

| 变更 | 长期文档处理 |
|---|---|
| 修复实现，使其符合既有规则 | 规则未变，不另写一份设计；保留修复与测试证据 |
| 修改评审额度 | 更新权威规则及必要理由，不在多份文档手抄数值 |
| 新增人工授权边界 | 更新持续有效的授权规则与执行合同 |
| 改动接口契约 | 更新既有契约与兼容说明，能生成的内容不重复维护 |
| 作出有长期约束的架构选择 | 记录必要决策、取舍与限制 |
| 处理一次临时环境故障 | 留恢复记录；形成可复用要求时再更新运维说明 |

内容与证据充分才是门禁，文件数量不是。既有平台级文档保持其归属，不强行搬入单 CR 的 specs；基线更新也不能用本次 CR 文档覆盖累积内容。

## 7. 事实归属与执行职责

### 7.1 沿用现有事实源，扩展必要合同

| 对象 | 目标归属与边界 |
|---|---|
| 可信人类授权与审批决定 | 平台记录；执行方核验适用范围与可信来源，不把 ACK 当作已消费或已执行 |
| CR 状态、评审意见、累计修复额度 | crctl 权威记录裁决，核验和消费相应授权；新额度合同扩展既有记录，不另建中央总账 |
| 执行身份、节点调度、执行重试 | Runner 维护，不独立裁决第二套业务额度；执行幂等与历史不能因减负删除 |
| 交接发布 | 复用 Git／checkpoint 及既有事务边界，交接前发布所需事实，不要求每次写入都 push |
| Agent 与流水线定义 | tools 源文件及锁定版本为源，平台是部署产物；保留生成一致性和运行版本校验 |
| 评论、看板、运行摘要 | 事实的视图与链接，不形成另一套状态、授权或评审结论 |

发布失败走既有有界恢复，不能为了重试发布而重复审批、重复扣额度或重复 reset。投影和缓存可以保留，但不能与权威记录各自裁决同一业务事实。

### 7.2 单一自动派发方

Runner 是唯一自动调度方。协调者负责解释、澄清、异常沟通，可以调用明确授权的受控恢复入口，但不另派一遍作者或 reviewer，也不在 prompt、评论里维护另一套路由表。

尚未接通 Runner 的阶段暂留旧路径；恢复能力与文本接力规则按阶段配套切换。新旧自动派发路径不能同时接管同一动作。常规流程不要求人手敲 crctl，但保留受控 TTY 运维恢复入口。

### 7.3 异常分流

| 异常 | 接收者 | 通知应包含 |
|---|---|---|
| 目标、范围、验收取舍，或追加执行授权 | CR 决策者／有权授权者 | 需决定的问题、已有证据、可选路径及影响 |
| 环境、凭据、部署、绑定等故障 | 维护责任人 | 已尝试恢复、具体阻断与所需维护动作 |
| 额度耗尽或无进展 | 按根因分流；涉及追加授权仍找有权者 | 已消耗额度、修复与验证证据、需要的判断或处置 |

两类责任可以由同一个人承担，不新增 Agent 或组织层级。维护权限不自动赋予扩大业务授权的权限；业务方也不应被要求替系统转述命令或调度执行者。

## 8. 通知策略

默认只在以下情况主动通知：需要补充授权或业务判断、出现需要责任人处理的阻断、完成约定交付。

中间进度留在可查询的运行记录；评论写结论、必要错误、canonical 证据链接和所需动作。不复制 blocker 全文、固定 next/status 快照或整份 JSON 报告。

相同未变化的阻断不因重放重复提醒，新失败、重要变化及交付结果仍可通知。复用既有执行与通知上下文实现，不为此新增全局去重状态。

## 9. 实施顺序与兼容迁移

### 9.1 三步落地

1. **事实核对与必要解阻**：核实真实部署版本、活动 CR 的权威位置及仍存在的故障。从原复盘措施中筛选当前确需修复的项，不把历史故障一概当成现存缺陷，也不把 R1–R12 全部列为必做。
2. **形成可试点的配套能力**：正式修订授权、门禁与产物合同，接通累计额度、无进展判断、独立验证、发布与恢复。Runner 能力和 Agent 文本同步切换；不能只改 prompt 宣布新流程生效。
3. **新 CR 试点并验收**：使用代表路径及失效用例验证，再决定扩展；不以单个 AIFI-45 回放通过代替通用可靠性证明。

当前解阻和目标流程改造分开管理，避免一次局部修复承载全部改造。涉及状态机、gates、模板或权限矩阵的修改必须走正式 CR 设计、评审与审批；本方案不授权绕过现行门禁。

### 9.2 在途 CR 默认不迁移

- 新 CR 小范围试点；在途 CR 默认保持原合同和流程版本。
- 显式迁移时记录新授权、适用流程版本、历史消耗和剩余额度，保留旧授权、评审与执行证据。
- 不因换版本而自动获得满额预算；历史无法可靠核实时不静默迁移或清零。
- 上线前核实 tools 源文件、生成版本和平台部署是否一致。确认本地 SHA 不等于确认线上版本。

## 10. 验收与效果验证

至少覆盖普通已授权变更、高风险动作、包含失败与恢复的变更三条代表路径，并验证以下行为。

| 编号 | 场景 | 必须满足的结果 |
|---|---|---|
| AC-1 | 普通请求已具备充分授权 | 不重复要求阶段性人工确认；无需人搬命令、转结果或手动推进 |
| AC-2 | 授权不充分或范围扩大 | 仅补问必要取舍；未授权部分不先执行，不靠改文档事后合法化 |
| AC-3 | 授权内、有进展的修复 | 在剩余额度内自动继续，不要求人机械续杯 |
| AC-4 | 累计额度达到上限 | 默认达到 6 次后不派发第 7 次；跨阶段与 cycle 的消耗仍有效 |
| AC-5 | 连续两次无进展 | 停止自动修复，携可核验证据与所需动作升级 |
| AC-6 | 重复投递或恢复 | 同一逻辑修复不重复派发、不重复扣额度；发布重试不重复消费授权 |
| AC-7 | 旧版本或旧 cycle 证据返回 | 不错误推进当前执行；仍能追溯历史 |
| AC-8 | 未授权敏感动作 | 无法仅凭模糊实施授权、作者自报或转述放行 |
| AC-9 | 交付与机械变更例外 | 交付证据可核验；实质变更具有独立验证，机械例外不能掩盖规则变化 |
| AC-10 | 环境等维护故障 | 有界恢复后找对责任人，不把技术搬运转嫁给业务方 |
| AC-11 | 通知与文档 | 无固定节点汇报和全文复制；最小记录完整，长期规则更新到事实源 |
| AC-12 | 在途 CR 与阶段切换 | 不静默迁移；新旧派发不双写，恢复能力未就绪时不提前删旧接力 |

AIFI-45 用于只读历史记录回放和隔离测试中的根因回归，不据此向实际在途 CR 派发任务、改写状态或重新扣额，也不执行未经授权的真实敏感动作。实际接入新流程仍须遵守 §9.2 的显式迁移规则。

上线后观察需要人做业务判断、维护处置和无价值搬运的次数，区分三者；不沿用原复盘中的固定介入次数目标作为本方案承诺。

默认 6 次额度需要结合真实修复结果、停止原因与运行成本校准；校准必须更新有版本的默认规则，不能暗中放宽单次已授权上限。真实费用或运行级预算若要引入，另行设计与确认，不伪称已被修复次数覆盖。
