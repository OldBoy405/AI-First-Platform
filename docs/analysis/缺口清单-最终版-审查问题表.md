> 审查对象：`docs/product/缺口清单-最终版.md`（审查前版本）
> 审查目的：识别过度设计、事实漂移、职责越界、歧义和内部冲突，并给出最小处理决定。
> 审查方法：按“复用现有能力 > 标准库 > 原生 Git/文件 API > 已有依赖 > 一行代码 > 最小新增代码”核对；事实以当前仓库和权威分支为准。
> 结果状态：审查决定已经用户确认，产品决策文档已按本表收敛。

## 2. 审查结论

| 级别 | 问题 | 风险 | 确认后的最小处理 |
|---|---|---|---|
| 阻断 | 文档同时承担能力清单、优先级、Runner PRD、Runner SDD 和维护规则 | 未注册 CR 的实现预设被误当成既定合同 | 收敛为“能力处置决策入口 + 当前候选立项卡” |
| 阻断 | “Runner 是最大产品缺口”只有组件缺失证据，没有用户痛点和运行频率证据 | 把技术空位误判为产品优先级 | 改为当前战略候选；Core 负责验证价值 |
| 阻断 | Core 未验证就承诺 Main Track | 在未知抽象上提前锁定第二个大 CR | Main Track 降为条件候选 |
| 阻断 | 文档使用落后远端 12 个提交的 Multica 本地 checkout 作为最终基线 | “未实现”判断可能基于过期代码 | 改用本次审计的权威分支 SHA；注册时重新核实 |
| 阻断 | run 固定启动模板版本，但只保存 digest，不保存或加载旧 registry | 部署后无法按旧模板恢复，却声称能够恢复 | Core 遇 digest 漂移时 fail closed；不建多版本模板库 |
| 阻断 | projector 与未来 Runner 都会创建/更新 `pipeline_run` | 双写可能产生重复 run 和互相覆盖 | 复用同一逻辑 run；禁止平行运行表或记录 |
| 阻断 | 人工审批后的执行责任不完整 | grant 已签发但 CR 不一定推进，Runner 可能误判完成 | 明确“投递 ACK → Runner 调度 approve Skill → crctl 推进” |
| 阻断 | Runner Core 只接受 `replayNodes`，现有 architecture 模板没有该字段 | Core 无法按自己声明的合同执行回修 | 先修 Pipeline 权威合同；Runner 不做兼容猜测 |
| 高 | “registry 刷新”混合旧 UUID 修复和完整执行 registry 新增 | 把新增能力伪装成机械刷新 | 分开描述；Core 执行 registry 只含 architecture |
| 高 | Core 同时实现 skip、code generation、四主 Pipeline 等未使用语义 | 纵切退化为通用工作流引擎建设 | Core 只支持 architecture 当前五节点和 abort |
| 高 | Runner 设计自己递增和判断 review attempt | 与 Pipeline/`crctl` 权威重复 | Runner 只消费结构化结果；attempt/maxAttempts 保持原权威 |
| 高 | 实现状态与产品处置混在五种标签中 | “未实现”被误读为自动值得排期 | 拆为实现状态与当前处置两列 |
| 高 | 未实现项没有价值准入门槛 | 代码中不存在的组件持续进入 backlog | 增加用户证据、替代能力、最小结果、依赖、验收五项门槛 |
| 高 | 65 个细粒度 ID 没有外部引用 | 维护成本高，制造伪精确度和永久 backlog | 合并为复用、当前候选、条件候选、排除/维护四组 |
| 高 | “只允许两个主线 CR”是排他性治理规则 | 可能阻止安全、bug 和必要维护 CR | 改为当前只有一个产品候选，不限制其他合法事实入口 |
| 高 | Wiki 在总清单中是条件项，独立方案却使用确定性排期语气 | 独立设计可能绕过当前处置直接实施 | Wiki 文件头标注 conditional、非实施授权，并回链本决策文档 |
| 中 | `APP-04` 身份桥被当成独立能力 | 技术前置脱离真实授权问题单独膨胀 | 与动态审批角色策略合并为条件项 |
| 中 | `RUN-13` 迷你门禁条来自 TASK 描述，非 PRD FR/AC | 把历史 scope creep 变成新待办 | 删除独立候选身份；真实定位困难出现后再评估 |
| 中 | tools 批量安装被描述为从零安装器能力 | 重复 Multica 已有 Skill 导入 API/CLI | 先做干净 workspace 安装验收；失败后只补版本化批处理 |
| 中 | 上游 PR 整理和测试诊断被列为产品能力 | 工程维护污染产品缺口视图 | 移到工程维护附录；测试失败按 bug 处理 |
| 中 | QA-01～08 被称为“未实现” | 实现状态和验证状态混淆 | 改为“未验证”，不注册独立功能 CR |
| 中 | Main Track 强制捆绑价值复盘 Lite | 自动调度与指标产品相互扩大范围 | 解除捆绑；至少 3 条真实 run 后先做确定性查询 |
| 中 | 大量聊天、移动、通知和组织智能微功能只有想法 | 条件 backlog 永久增长 | 只保留有独立设计、可测阈值或明确否决价值的项目 |
| 中 | Agent/Skill/测试数量在多处硬编码 | 数量已漂移并互相冲突 | 正文删除数量；审计快照只记录一次并指向索引 |
| 低 | 状态机规模和事实源说明重复 | 人读文档逐渐变成第二合同 | 只保留权威引用，不复制执行合同 |
| 低 | Runner SDD 预写函数名、锁、upsert 和精确故障窗口 | 跳过真实代码设计评审，锁死实现 | 候选卡只保留结果级验收，细节留注册后的 SDD |

## 4. Runner Core 收敛边界

### 保留

- `architecture-design` 五节点顺序。
- review block 的显式 Pipeline 回修链。
- 人工审批暂停和签名 grant 消费。
- 同一 run 复用、任务归因、重复唤醒幂等。
- 服务重启恢复和模板 digest 漂移阻断。
- 手动 Skill + `crctl next` 路线回归。

### 移出 Core

- requirement/code/writeback 和四主 Pipeline 串联。
- `onFail=skip`、`code_generation` 和其他未使用节点种类。
- requirement 注册后补 CR-ID。
- 通用 passCondition 表达式解释器。
- 多版本模板仓库。
- 新运行表、幂等表、消息总线或第二事务框架。
- Runner 控制台、价值复盘 API、统计表和组织评分。
