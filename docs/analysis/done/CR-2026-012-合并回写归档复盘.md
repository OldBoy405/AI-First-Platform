## 二、根因分析

### 2.1 `_backlog.yml` 集中状态双写是最大摩擦源（工具包设计）

所有状态推进提交都改 `change-requests/_backlog.yml` 里同一个 CR 条目的 `status` 字段（同时改 `cr.md`），两个长期分支各自推进时必然冲突。CR-2026-012 的生命周期共产生 9 个状态推进提交，rebase 时**每一个**都在 `_backlog.yml` 同一区域与 master 冲突，形成"冲突 → 解决 → 下一个提交又冲突"的连环。

这是比"设置"更深一层的**数据布局选择**：状态是高频写、低并发的数据，集中存放天然与长期分支模型冲突。

### 2.2 skill 的 git 操作没有非交互适配（工具包适配缺口）

`merge-feature-branch` / `cr-archive` 里大量 `git commit` / `git rebase --continue` 会弹编辑器，Agent 执行时直接挂死（本轮两次 180s 超时均源于此）。crctl 对 TTY 有保护（非 TTY 拒绝审批），skill 层反而没有对应的非 TTY 约定——保护做在了错误的层级。

### 2.3 writeback 文档与工程纪律打架（已知，靠纪律兜底）

skill 字面写的是 `cp` 覆盖 specs 基线，直接照做会用单阶段文档覆掉整个平台基线（CR-2026-002 回写时已咬过一次，固化为 AGENTS.md 工程纪律 #6）。虽然纪律已覆盖，但每次执行都要人脑判断"照做会毁基线"，这部分决策成本其实也不小——**文档与纪律不一致，靠人脑记住"不要照做"不是可持续状态**。

### 2.4 会话内现写脚本反噬（执行操作）

为省事在会话内现写 PowerShell/Python 脚本处理 YAML 账本，反被 Write 工具的转义问题反噬（`\r?\n` 被写成真实换行、反引号被吞、`-replace` 参数错位），一次坏脚本把 9 个冲突块原样提交进历史，事后手工修复。这类操作应该沉淀为可复用脚本，而非每次会话内现写现调。

### 2.5 Windows 环境适配缺口（环境 + 工具包）

- worktree 删除 `Filename too long`：git 失败后工具包没有 `Remove-Item -Recurse -Force` 兜底指引，靠现场判断。
- SSL 代理拦截、CRLF：属环境固有问题，但工具包未提供任何 Windows 环境的已知问题清单。

## 三之二、优先级排序与依赖风险

### 优先级

| 序 | 项 | 理由 | 量级 |
|---|---|---|---|
| 1 | T3 | 唯一会毁数据的缺陷 | 小 |
| 2 | T2（代码化） | 一行 env + 文档，消灭挂起 | 小 |
| 3 | T1-lite | 立即消掉最大耗时源的大头 | 小 |
| 4 | T4+T5 合并 | 一份文档 + `core.longpaths` 根治 | 小 |
| 5 | P1 收尾 | `implement-code` 加一行完成标志 | 极小 |
| 6 | T1-full | 收益最大但改造面覆盖 31 个 skill + 双适配器，需走正式 CR | 中偏大 |
| 7 | P2 | 依附 T1-full，范围随其定型 | 中 |

### 依赖关系

- **T1-full 是 P2 的前置**：`_backlog.yml` 降级为注册索引后需要脚本化的账本操作少一半，先定 T1-full 范围再定 P2 具体子命令。
- **T1-full 必须与 claude-code 适配器（SessionStart 注入）、CI 适配器（`crctl gate`）同版本发布**，否则状态读写源分裂；crctl 需加兼容读（cr.md 优先、`_backlog.yml` 回退）。
- **T2 / T3 / T4+T5 / P1 相互独立**，无顺序约束，可并行推进。
- **风险**：T1-lite 的"取状态机靠后一侧"解法依赖"advance 是唯一写入者"这一不变量（已被纪律 #5 保障），skill 文档需显式写明该前提，否则解法可能被误用于非 crctl 产生的冲突。
