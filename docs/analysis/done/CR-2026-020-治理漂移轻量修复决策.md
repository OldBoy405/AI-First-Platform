## 四、merge-commits 字段契约（保留，硬结论）

回答"实际几个字段合理"——**必填 3 个 `{repo, trunk, sha}`，其余宽进严出**。判据是"能否从落点提交复原"：

| 字段 | 定档 | 理由 |
|---|---|---|
| `repo` | 必填 | 多仓，无从复原 |
| `trunk` | 必填 | trunk 名各仓不同（master / main / custom/main），无从复原 |
| `sha` | 必填 | 落点锚，traceability 的根；缺它整条记录无意义 |
| `branch` | 选填（crctl 自动补） | 恒为 `requirement/{CR-ID}`，由段 key + 命名约定可推导 |
| `source-sha` | 不要求（留存不拒） | = 合并提交第二父，`git` 从 `sha` 可复原 |
| `merged-at` | 不要求（留存不拒） | = `sha` 提交时间，`git` 从 `sha` 可复原 |

**核心契约**：必填集 ≡ 唯一生产者 `crctl merge-metadata` 保证输出的集合。写回脚本"严出"只校验这 3 个，"宽进"接受任意额外字段、绝不 reject 历史 6 字段 / `message` 变体。这才根治 CR-2026-020 那 ~6min bug——bug 本质是"脚本 require 6 / 生产者 emit 3"的契约错位，不是字段数大小。

真实数据分布（核实命令 `grep -A6 'merge-commits:' specs/ai-first-platform/traceability.yml`）：CR-001 四字段（含 message）、CR-002/007/008/009 六字段、CR-019 四字段（含 branch）、CR-020 三字段（crctl 纯输出）。
