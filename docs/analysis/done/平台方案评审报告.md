## 一、架构合理性

### 1.1 multica（Go 后端 + TS 前端 monorepo）

**事实：**
- 后端分层规范：`server/internal/`（handler → service → storage，另含 daemon / daemonws / realtime / scheduler / middleware 等 25 个包）与 `server/pkg/`（可复用库：agent / db / llm / protocol / redact / skillbundle）边界清晰。
- **Agent CLI 抽象**（`server/pkg/agent/`）：实测支持 14 种 CLI（antigravity / claude / codebuddy / codex / copilot / cursor / hermes / kimi / kiro / **openclaw** / opencode / pi / qoder / traecli），每种带独立测试文件。注意 `openclaw` 已是上游原生支持的 agent 类型——这对我们"五方组装"中 OpenClaw 渠道生态的接入是重大利好，接入成本比方案预估的更低。
- **任务分发**：DB 表 `agent_task_queue` + `FOR UPDATE SKIP LOCKED` 原子 claim（`server/internal/service/empty_claim_cache.go:64` 注释引用 `ClaimAgentTask`），daemon 侧通过 `POST /api/daemon/runtimes/{id}/tasks/claim` 拉取（`server/internal/daemon/client.go:185`）。单写者语义由 DB 层保证，这是正确的做法。
- 本地执行架构（daemon 在用户机器上运行、凭据不出本机）与我们"本地执行、隐私优先"的设计主张完全吻合。

**评价：** 架构合理，与平台方案的假设匹配。**但注意：P2 设计中的"50 位 FIFO 队列"在 Multica 上游并不存在**——队列表存在但无容量上限，50 位是 CodeBanana 的产品行为，属于我们 fork 后要自研补齐的部分（见第六节）。

### 1.2 openwiki（TS，LLM 生成/维护 wiki）

**事实：**（本节含后台深度评审结论）
- 分层：`cli.tsx`（Ink TUI）→ `commands.ts`（argv 解析）→ `agent/index.ts` 的 `runOpenWikiAgent()` 单编排入口 → deepagents/LangChain。
- 确定性护栏放在了正确的层：`docs-only-backend.ts` 在 backend 层拦截 write/edit 并做 `..`/反斜杠归一化后前缀检查（84–94 行）；`okf-middleware.ts`（仅 136 行）三段式 beforeAgent 迁移 / wrapToolCall 写后校验 / afterAgent Mermaid 校验+确定性重建索引。"LLM 写内容、代码管结构"分工干净。
- `.last-update.json` + 内容快照哈希实现 update no-op 判定与中断恢复，失败晚期也持久化元数据——工程细致。

**评价与警示：**
- 🔴 **高**：shell `execute` 工具**绕过 docs-only 边界**——`docs-only-backend.ts` 只覆写 write/edit，agent 在 init/update 期间可用 shell 重定向写出 `openwiki/` 之外的任何文件，目前只靠提示词纪律（`prompt.ts:36`）。**这直接验证了我们《Wiki子系统设计》把写白名单放在 daemon 层（`rules.json#taskWriteAllowlist`）的决策是对的，但我们的实现必须确保白名单同时覆盖文件工具和 shell 两条路径**，否则会复刻同一缺口。
- 🟡 中：`runOpenWikiAgent` 在 `options.outputMode` 未设时静默忽略 `cwd` 参数（`agent/index.ts:130`）；流事件解析约 490 行启发式代码，上游协议升级时静默丢文本。

### 1.3 tools（方法论包 + crctl）

**事实：**
- **状态机声明式外置**：crctl 不硬编码状态，从 `dir-graph.yaml#change-request-track.state_machine` 读取（`crctl.mjs:266`）。实测状态机含 16 个状态（含 `(new)`：drafting → requirement-reviewing → requirement-approved → tech-designing → tech-design-review-pending → tech-design-reviewed → task-breakdown → developing → code-reviewing → code-approved → merging → writing-back → archived，另有 rejected / withdrawn 两个 any-active 出口）——与文档"16 状态"一致。
- **crctl.mjs 实测恰好 1006 行、零外部依赖**（仅 node: 内置模块），与文档声明一致。
- 质量亮点：权威文件写入采用 **hash-CAS**（读时记 sha256、写前复核，`crctl.mjs:487` `CAS_CONFLICT`），防并发覆盖；审批强制 TTY（`crctl.mjs:652-653`），无旁路参数；审批时记录 `evidence-sha256-16`（`crctl.mjs:707`）。
- Agent↔Skill↔Pipeline 映射有机器可读源（`agent-skill-matrix.yml`，带 schema 版本与 updated-at）+ 人类可读视图（`AGENT-SKILL-MATRIX.md`）。`system-orchestrator` 在文档中有明确说明（不是可部署 Agent，是运行时编排组件，`AGENT-SKILL-MATRIX.md:14`），非漂移。

**评价：** "方法论即代码"的组织方式成立且执行质量高。两个注意点：
- 🟡 `controlled-shell/` 仅有 SKILL.md（提示词纪律），**无可执行强制**——gitguard 白名单的真正强制层在 P1 设计中规划由平台 daemon 承担，这个"现状=提示词、目标=确定性"的 delta 与 openwiki 的 shell 缺口同类，是平台自研层的核心职责，不能延期。
- 🟡 矩阵 md/yml 双源有漂移风险（md 是手写视图，31 行表格）。

## 二、文件组织

**符合最佳实践的部分：**
- multica：标准 turbo monorepo（apps/desktop|mobile|web|docs + packages/core|ui|views + server + e2e + scripts），pnpm catalog 统一 React 版本。
- tools：skills/ 按域分组（competitive/cr/develop/planning/requirement/review/spec/sync/writeback/shared），`_index.yml` 与实际文件数一致（均为 59）。
- openwiki：src/ 按域划分（agent/auth/connectors/okf/mermaid/telemetry）。

**问题清单：**

| 严重度 | 位置 | 问题 | 建议 |
|---|---|---|---|
| 🔴 高 | `C:\` 根目录 | **存在误建的 git 仓库**（`git rev-parse --show-toplevel` 返回 `C:/`），整个 C 盘处于一个仓库工作区内，`$Recycle.Bin`、`Program Files` 均显示为未跟踪文件。任何在此目录树内执行的 `git add -A` 都会试图暂存整个系统盘 | 确认 `C:\.git` 无有价值历史后删除（**删除前请人工确认**）；为 `AI First Platform` 目录单独 `git init` |

- `isRecord()` 重复 7 份且语义不一致（`agent/index.ts:1516` 不排除数组、`okf-middleware.ts:134` 排除）；`chmodIfExists` 等 fs 工具函数私有重写 2 处。

## 五、可扩展性与可维护性

### 5.1 fork Multica 的同步成本（平台最大的长期维护风险）

- 上游活跃演进 + 我们要动的恰是最大的几个文件（daemon.go / handler/daemon.go / service/task.go），三年期冲突成本不可忽视。
- **隔离策略**（fork 第一天就要立规矩）：
  1. 自研代码一律放**新包**（如 `server/internal/governance/`、`server/internal/collab/`），禁止在上游文件内散布业务逻辑；
  2. 对上游文件的必要修改收敛为**少量显式挂钩点**（middleware 注册、事件订阅、feature flag——上游已有 `featureflags/` 包可复用），每处挂钩留 `// AIFIRST:` 标记注释便于 rebase 时检索；
  3. 定期（建议双周）rebase 上游并跑全量测试，把同步做成例行小事而非季度大事；
  4. `openclaw` 已是上游支持的 agent 类型，OpenClaw 渠道接入优先走上游现成抽象，不另起炉灶。

### 5.2 tools 的规模化

- 新增 Skill 的边际成本低（目录 + SKILL.md + `_index.yml` 登记 + 矩阵 yml 归属），59 个规模下仍可维护。
- 风险在**双源漂移**：`_index.yml`、`agent-skill-matrix.yml`、`AGENT-SKILL-MATRIX.md`、README 中的数量/归属各自手写。建议加一个 20 行的校验脚本（列在 crctl 同级）：核对"每个 active skill 恰有一个 owns 归属、_index 与目录一致、md 表格由 yml 生成"，接入 CI 或 pre-commit。

### 5.3 openwiki 模式的移植边界

《Wiki子系统设计》借鉴的三个模式（写边界在工具层、三段式中间件、gitHead 增量 no-op）在源码中全部实测存在，移植方向正确。补一条从其缺口学到的**硬性验收项**：Wiki 任务的写白名单必须在 daemon 层同时拦截**文件工具路径和 shell 路径**，并配对抗性测试用例（重定向写、`..` 穿越、反斜杠路径）——建议追加进《Wiki子系统设计》§7 的 W2 验收标准。

### 7.2 性能优化建议

说明：本轮为静态评审，未做基准测量，以下是结构性建议而非热点修复。

- **multica**：任务 claim 用 `SKIP LOCKED` 已是高并发正确解法，公司内网百人规模无需改动；fork 后从 turbo CI 矩阵剔除暂不启用的 desktop/mobile 构建，缩短流水线。
- **仓库体积**：三个 clone 的 .git 共约 224 MB，日常参考用途可改浅克隆（`--depth 1`），或按 R1 改为 SHA 引用。
- **openwiki 经验移植**：其 checkpoint 裁剪、内容快照哈希做 no-op 短路的思路，直接对应《Wiki子系统设计》§3 的"no-op 判定在 daemon 层、任务下发前"——保持该设计，可省掉大量无效 LLM 调用（这是 Wiki 子系统最大的性能杠杆）。
- **crctl**：`spawnSync` 逐条调 git 在单 CR 操作粒度下无性能问题，不建议为速度引入依赖。

### 7.3 代码结构改进方案

- **平台自研层（Go）立规**：单文件 ≤800 行触发拆分评审；公共工具函数归口 `internal/util`；错误码统一注册（对标 crctl 的 `fail(CODE)` 模式）。
- **借 openwiki 反面教材**：禁止 monkey-patch 全局对象；禁止对第三方库内部存储写裸 SQL；API 参数不得静默忽略（`cwd` 教训）。
- **借 openwiki 正面教材**：确定性护栏一律做成"小文件 + 单一职责 + 可单测"的独立模块（对标 docs-only-backend 2.7 KB / okf-middleware 4.6 KB 的粒度）。
