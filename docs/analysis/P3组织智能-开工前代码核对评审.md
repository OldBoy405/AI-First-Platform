## 1. 为什么要做这一轮

P3 设计文档写于 2026-07-28，此后平台侧交付了 CR-2026-011（gate 投影）、CR-2026-045（architecture-design runner）等一批治理能力，multica 又做过一次 258 commit 的上游 merge。**设计文档里的「已有基础设施」清单是七月的快照，而实施要发生在八月**。

直接的动机是一条约束：**不要再造一套事务框架**。P1 已经交付了 outbox → 幂等账本 → 投影的完整链路，P3 若照着文档里"新增 2 张表 + 新采集通道"的字面描述实施，很可能平行造出第二套。

## 2. 方法

三条纪律，按顺序：

1. **每一条"某仓有/没有某能力"的断言都用命令核实**（`ls` / `grep` / 读函数签名 / 查调用点），不靠记忆也不靠文档互引。这是本仓 `AGENTS.md` 工程纪律 4 的直接应用。
2. **按 YAGNI 阶梯反问每个新增项**：这个东西需要存在吗 → 仓内已经有吗 → 能用现成机制拼出来吗 → 必须新建吗。
3. **把结论分三类**——事实错误（必改）、过度设计（砍）、顺序错误（重排）。混在一起讨论会让"文档写错了"和"设计得太重了"互相掩护。

调研分两路并行：一路清点 multica 仓的既有基础设施（调度/水位线/outbox/任务队列/skill 表/前端/迁移/仓规则八项），一路清点 P3 的 CR 注册状态与 P0/P1 契约的实际落地形态。

## 3. 关键发现（按杀伤力排序）

### 3.1 三处事实错误

| 断言 | 实际 | 危害 |
|---|---|---|
| `task_usage_daily`（日汇总表）、`task_usage_rollup_state`（水位线状态表） | **都不存在**。前者被迁移 `103_drop_legacy_daily_rollups` 故意删除；后者真名 `task_usage_hourly_rollup_state`。且现存 `task_usage_hourly` 的维度里**没有 user** | 实施者会去找一张不存在的表，找不到之后很可能"顺手补建"——而上游刚刚才把它删掉 |
| P3 卡在 Pipeline Runner 未实现 | **只有写侧 Runner 未实现，读侧投影已交付**。`governance/gate_projection.go`（CR-2026-011 TASK-02）的 `applyReview` 已向 `pipeline_node_run` 写 `attempt`/`status`，`pipelineForStatus` 已覆盖全 4 条 pipeline，文件头明写目的就是"不必等完整 Pipeline Runner 存在" | P3 会平白等一个不需要等的前置。这是**顺序错误里代价最大的一种：等待一个已经完成的东西** |
| `skill.visibility` 需要 `builtin` 枚举档 | builtin Skill 在 `skill` 表里**根本没有行**（`service/task.go:5851` 对 `id == ""` 现场合成 `"builtin:" + Name`） | 给不存在的行加枚举值是死代码；连带发现 `skill_usage_event` 用 UUID 外键记 skill 也记不住 builtin——而 56 个内置 Skill 的使用量恰好是最有价值的那部分数据 |

额外撞见的第四处（不在 P3 范围内但同源）：tools 实为 **56** 个 active Skill，本仓三处文档写 59。讽刺的是 `docs/references/tools.md` 那句"数量以 `_index.yml` 为准（已订正为 59）"本身就违反了它自己确立的权威源。已一并订正 `AGENTS.md:3`、`dir-graph.yaml:30`、`docs/references/tools.md`。

### 3.2 砍掉的九项

`spec_trace` 表 · 4 个子指标（AI 效率系数 / 规划转化率 / Cron-A2A 采用 / 超级个体占比推迟）· 2 个工坊 route · 2 个 LLM 巡检 · E9 整节移出。

其中三条的推理值得单独记：

- **`spec_trace`**：与 P0 §3.1.1 砍 `cr.checkpoints[]`/`merge_commits[]` 是同一条推理——事件行自带时间戳与完整 payload，二次拆列的快照表不多提供一个事实，只多一个会漂的副本。发现 `cr_sync_event.event_kind` **列上没有 CHECK 约束**后，"加第 7 个 kind"变成零迁移操作，表就更没有理由存在了。
- **两个 LLM 巡检**：七跳链路（sys_cron → 队列 → daemon 认领 → LLM → 写 git → outbox → 投影）+ "某台 daemon 恰好在线且恰好持有那个 spec 的 worktree"。任一跳断了都是静默无结果，而**"无结果"与"无漂移"在看板上长得一模一样**——这正是 P1 §B.4 关于 EVIDENCE_DRIFT 已经写过的警告（必须能区分"从未漂移过"与"从未测过"）。同一个陷阱在同一个项目里出现第二次。
- **两个工坊 route**：本仓技术栈下新增一条 route = 5 处改动（`core/paths` · view+barrel · web 页 · desktop 路由表 · sidebar 三处常量）。三个视图 = 15 处改动 + 3 个新导航入口，而其中两个的内容全是既有页面的重新排列。**导航栏多两项的认知成本比省下的两次点击更贵**；且其中真正缺失的能力（用户侧「待我审批」端点）并不需要新 route 才能提供。

### 3.3 一处"更懒且更可信"的改法

Skill 遥测的采集点，从"任务完成回调附带 `skills_used[]`"改为"服务端任务认领路径直写"。

原设计的前提是"Skill 物化信息只有 daemon 知道"——**这个前提是错的**。`handler/daemon.go:1982-2070` 显示服务端在认领时就算出了权威的 `skillRefs` 并**发给** daemon，只是没存（:3308 那次 marshal 仅用于日志字节数统计）。

改到认领侧后：`TaskCompleteRequest` 零改动，避开了 `sanitizeTaskCompleteRequest` 注释里明写的陷阱（新 string 字段漏加 sanitize → NUL 字节 → SQLSTATE 22P05 → 任务永久卡在 running，GH #7098）；"服务端重算 vs 信任 daemon"这个取舍本身消失了；name 反查与 workspace 边界问题一并消失。代价是时间戳含义从"完成时用了"变为"派发时物化了"，需在查询侧显式带 `status = 'completed'`。

**一个 `WHERE` 换掉了一条跨进程字段加一个任务卡死隐患。**

### 3.4 三条原文没写、遗漏会返工的约束

新迁移从 **375** 起（fork 自有迁移已占至 374）；**禁新增 FOREIGN KEY**；**每个索引必 `CREATE INDEX CONCURRENTLY` 且一个迁移文件一条**。前两条来自 multica `CLAUDE.md` 硬规则——上游自己就因为热表 `"user"` 上锁超时而用迁移 118 删掉了迁移 117 刚加的外键，而 P3 原 DDL 里有两个 `REFERENCES`。

另外补了 `drift_finding` 的幂等键。巡检是定时重复扫描，没有唯一索引，一个长期存在的 bypass 提交会每小时刷一条 finding，一周后治理板块只剩它。口径与 P1 §A.1 一致：at-least-once + 唯一索引去重，不在应用层"先查再插"——`webhook_delivery` 的代码注释已经把这个道理写成了仓内共识（"租约是调度优化，唯一索引才是最终保护"）。

## 4. 净结果

**砍**：1 张表、4 个子指标、2 个 route、1 个整节、2 个 LLM 巡检。
**加**：3 条实现约束、1 个幂等键、1 个查询过滤条件。
**纠正**：3 处与代码不符的事实断言（+1 处计数）。
**重排**：CR 从五个（作废编号）重切为四个（A 0.21 / B 0.22 / C 0.23 / D 0.24），其中 CR-D 的真实前置是**时间**（观察期 4 周）而非代码——捆在 CR-A 里会让 A 的归档被一个等待阻塞四周。

P3 最终新增的持久化面：**2 张表**（`maturity_snapshot`、`drift_finding`）+ `skill` 三列 + `skill_usage_event` + **1 个 event_kind（零迁移）**。其余全部读时聚合或复用现成机制。

## 5. 可复用的教训

1. **"已有基础设施"清单会过期**，且过期方式是危险的——它让人以为某个东西还不存在（于是重建），或以为某个东西存在（于是找不到时补建）。设计文档里凡是引用具体表名/函数名的地方，开工前都该重核一遍。
2. **同一个陷阱会在同一个项目里出现第二次**。P1 §B.4 已经写过"必须能区分从未漂移与从未测过"，P3 的 LLM 巡检又踩了一次同形状的坑。已知教训要主动去正文里找它的同构物，不能等它自己冒出来。
3. **"零新增探针"的说法要看落点，不看措辞**。原设计说 Skill 遥测"搭任务完成回调的便车，零额外探针"——听起来已经最省了，但它其实要新增一个跨进程字段。真正的零成本采集点在更上游、更权威的地方。**"我已经很省了"是停止优化的最常见理由，也是最不可靠的理由。**
4. **先把结论分类再讨论**。"文档写错了"和"设计得太重了"混在一起谈时，会互相提供掩护：砍一个功能时可以说"反正数据源也不存在"，而修一处事实时可以说"反正这功能也要砍"。分开之后每一条都得独立站住。
