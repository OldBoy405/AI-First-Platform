# Agent、Pipeline、Skill、crctl 与版本化脚本采用单向执行所有权

Tools 执行链同时采用不可绕过的极简约束：复用现有实现 > Node 标准库 > Git/文件系统原生能力 > 已安装依赖 > 一行实现 > 最小新增代码；不得为推测需求增加依赖、通用框架、接口层、类层级或配置面。本轮 crctl 重构最多新增 `durable-tx.mjs` 与 `workspace-transactions.mjs` 两个内部模块：前者只提供公共 journal envelope、lock/write-set/fault/recovery primitives，后者只保留 register/workspace/merge/writeback/archive 五个显式函数；不建通用 saga/phase engine/handler registry/plugin。只有至少三个处理器出现相同非平凡阶段控制或同一恢复缺陷需三处修复等实测证据后，才从真实调用点向 `durable-tx.mjs` 提炼最小 runner；核实条件与迁移方法登记 `tools/CUSTOM.md#CUSTOM-TODO-008`。目标 workspace 最低账本版本提升为 `cr-backlog/v2`；一次性 `migrate-backlog`、ghost cleanup、v1 status fallback 与 legacy warning 从主执行器删除，旧 workspace 必须在升级 tools 前用旧版本完成迁移，当前 crctl 对 v1 只返回 `UNSUPPORTED_BACKLOG_SCHEMA`。归档也只暴露单一幂等 `crctl archive`：状态转换、四账本/archive event、精确 commit/lease push、远端确认与受控 workspace/ref 清理均为 crctl 内部阶段；`cr-archive` Skill 只校验业务参数、调用一次并解释结构化结果，Pipeline 不展开归档算法。归档清理策略固定且不再接受 Skill `cleanup_branch` 开关：成功 `archived` 仅在 approved source/merge ancestry 已进入 trunk 后删除 clean worktree 与已合并 requirement refs；`rejected/withdrawn` 仅删除 clean 本地 worktree，dirty 则 cleanup-pending，未合并远端 refs 始终保留并在 `preservedRefs` 给出原因，未来删除需另作人工确认、按 SHA lease 的管理设计。origin 确认 archive commit 后 `archived` 即为不可反转的业务事实；后续清理失败只形成 journal `cleanup-pending` 和 `CR_ARCHIVE_CLEANUP_PENDING`，不回退状态/账本，`status/next` 优先指向同一 archive 续跑直到 cleanup done。Tools 执行链采用不可绕过的职责边界：Agent 只负责意图路由、职责判断及选择 Pipeline/Skill；Pipeline 只负责跨 Skill 的节点顺序、输入传递、review loop 与失败中止；Skill 负责业务判断、业务步骤、输入输出及失败语义，但只调用深原语；crctl 独占状态、门禁、CAS、受控账本写入、审计及 Git/workspace 事务；版本化脚本只做确定性文档转换；README 只提供人读总览。多个并列业务 Skill 必须拆为 Pipeline 中可观察的独立节点；只有单个主业务 Skill 调用 crctl、确定性脚本或校验器等支撑原语时，才允许保留在同一节点内部。CR 注册进一步收敛为单一公开、幂等的 `crctl register` 深原语；CR-ID 分配、受控账本写入、registration commit/push、参与仓 workspace ensure 与中断续跑均为其内部阶段，`requirement-register` Skill 只校验业务输入、调用该原语并解释结构化结果。每次注册使用运行时持久化并由各层透明传递的 `registration_key` 作为幂等标识：同 key 续跑同一 CR，不同 key 可创建业务输入相同的不同 CR，已绑定 key 的输入变化必须拒绝。`drafting` 只表示 CR 业务身份已存在，不代表参与仓 workspace 全部就绪；不新增技术性 `registering` 状态，未完成 register transaction 必须优先阻断 `status/next` 和下游节点，只有 workspace 全部 healthy 后才能产生成功注册执行上下文。注册失败默认 roll-forward：保留 journal 证明为 healthy 的已成功资源，相同 key 重跑只补齐缺失项；不得自动回收 CR-ID、revert registration commit 或删除已成功分支/worktree，清理只能经显式且受 containment/cleanliness 约束的入口执行。锁仅支持本机本地 Installation Workspace：以原子 mkdir 创建带 random token/pid/hostname/txId 的 operation/publish lock，无 TTL/force unlock；同 hostname 且 PID 不存在才自动回收（EPERM 视为存活、ESRCH 视为不存在），foreign hostname 或 token 不匹配硬阻断，宁可 PID 复用导致保守阻塞也不误删活锁。并发控制采用两级最小锁：按 registration key/CR-ID 的 operation lock 覆盖单项事务，Installation Workspace 级 publish lock 只覆盖共享账本写入、精确 stage、commit 与 push 的短临界区；不预先实现 per-repo publish lock，只有实测跨进程吞吐不足时再细分。merge finalize 后的写 authority 固定切换到 crctl 管理的专用 Transaction Workspace并持续到 archive；用户主 checkout 不因 clean 与否成为事务执行位置，CR worktree 同期只读。Transaction Workspace 固定为基于已确认 origin trunk SHA 的 detached HEAD，不创建私有事务分支；后续提交只以 journal 记录的精确 SHA 和 lease 发布到 trunk。所有 writeback 版本化脚本都只生成包含 after-images 与 before/after hashes 的 candidate bundle，不直接修改 baseline、delivery 或 traceability 权威文件；统一由固定枚举 `baseline|tasks|traceability` 的 `crctl writeback-apply` 校验路径并通过 recoverable write-set 应用候选、按阶段推进状态和发布 Git commit，不提供任意路径写入口。candidate manifest v1 只允许固定 stage allowlist 内 workspace-relative、无 symlink 的 regular file create/replace，按 POSIX path 字典序唯一排列，并绑定 signed input digest、generator SHA、before/after/blob SHA；blob 只能来自当前 tx 的 content-addressed candidate 目录，不支持 delete/rename/chmod/executable bit，staged set 必须与 manifest 精确相等。candidate manifest 是 crctl 与 Tools Root 中固定 stage 脚本之间的内部协议，不向 Skill/Pipeline 暴露 `--manifest`、脚本路径或输出目录；生产路径中每个 writeback Skill 只调用一次 `writeback-apply`。writeback stage candidate 是确定性派生物：push 前 knowledge-base trunk 前进且本 stage 尚无远端副作用时，丢弃旧临时 commit/candidate并在新 origin SHA 的 detached Transaction Workspace 重新生成、重验 snapshot/hash/allowlist 后以新 lease 发布，不 rebase/cherry-pick；origin 已包含 stage commit 则确认成功，journal 声称已发布但 origin 不再包含时返回 `WRITEBACK_REMOTE_HISTORY_REWRITTEN` 硬阻断。每个事务固定启动时的 repository graph digest：零副作用时发现 graph 变化可在同一 tx 自动丢弃旧 prepare 并按新 graph 重建；已有账本、workspace 或远端副作用后必须以 `GRAPH_CHANGED_DURING_TRANSACTION` 硬阻断，不得 force 或静默改变参与仓，需先恢复原 graph 完成事务。release snapshot 升级前由临时只读 `crctl upgrade-check` 从已 fetch origin trunk/active repo refs 统一分类 `safe|requiresReapproval|blocksUpgrade`，不读用户主 checkout、不创建 workspace、不写状态；block 或事实不确定时 exit 1，待所有安装完成协议切换后连同测试整体删除，删除条件登记 `tools/CUSTOM.md#CUSTOM-TODO-009`。release snapshot 升级采用硬边界：升级前若存在无 snapshot 的 partial merge/merging/writing-back CR，则阻止激活新版本并先用旧流程完成；无远端副作用的旧 `code-approved` 可升级，但首次 merge 经 `release-drift` 回 developing 重跑测试/评审/审批；developing 及更早状态直接进入新协议。本重构 CR 自身由旧版流程完成 merge/writeback/archive 后再激活新 crctl，不合成、补签或长期兼容旧 snapshot。release snapshot 不在审批时现取：`crctl review-record --stage code` 从真实已推送 worktree/ref 机器注入 `code.yml#release-subjects`（逐仓 reviewed source SHA 与 CRLF 规范化、路径排序后的 PRD/SDD/plan/TASK 集合 digest），模型 payload 不得提供或覆盖；既有 TTY/Ed25519 审批签整个 code evidence digest，approve 再核对 ref/HEAD/artifact 后原样复制到 `approval.yml#code.release-subjects`，不一致以 `RELEASE_SUBJECT_DRIFT` 零写入拒绝。merge 和 writeback 只消费 approval 中已签入 snapshot，不新建账本。merge source 不取移动分支的最新值，未经审批的新提交不得自动忽略或纳入；writeback 也不得读取与 snapshot 不一致的阶段产物。若 code/source/TASK drift 发生在任何 trunk publish 前，由 crctl 独占执行 proposed 状态转换 `code-approved -> developing`（trigger=`merge-feature-branch:release-drift -> implement-code`）、将原审批标记 stale 并返回对应结构化回退结果；PRD/SDD drift 返回 `APPROVED_ARTIFACT_DRIFT` 硬阻断，不以代码审批替代上游重新审批。Skill 只解释结果，Pipeline 只中止并在后续运行中显式重放测试/评审/审批，Agent 不决定或手写回退。若已有任一 trunk publish，则 crctl 返回 `MERGE_SOURCE_MOVED_AFTER_PUBLISH` 并保持 `code-approved`/blocked，不自动 reset、force-push、二次 merge 或纳入新提交；新提交必须拆到新 CR，管理员恢复原 ref 后原 tx 才能续跑。register/merge finalize/writeback/archive 复用 `workspace-transactions.mjs` 内唯一 `classifyRemoteCommit`，只按 remote SHA、expected base、candidate ancestry 与 journal published fact 分类为 `confirmed|pushable|rebuild|history-rewritten`；具体处理器各自重建业务 commit，helper 不接收 prepare/publish/compensate callback，history rewritten 一律硬阻断。跨机器恢复不新增远端事务账本；所有 crctl 事务 commit 由 crctl 追加固定 `AI-First-Op/Tx/CR` trailer，register 只追加 registration key 的 SHA-256，merge 另含 repo/base/approved-source，作为本地 journal 丢失后的 Git 原生恢复锚点；trailer 与远端事实冲突时硬阻断。事务临时产物按远端事实驱动清理而非 TTL：远端确认前保留完整恢复材料，单阶段确认后删除大体积 before/after images 并保留小型 journal 摘要，archive commit 远端确认后再幂等删除剩余 journal 与 Transaction Workspace；无法证明安全时不自动删除。该边界取代任何在 Agent、Pipeline 或 Skill 文本中复制底层算法的旧契约，因为重复实现会形成多份事实源，并把失败恢复错误地交给模型推理；例外必须重新作架构决策，不得以单个流程“特殊”为由绕过。
