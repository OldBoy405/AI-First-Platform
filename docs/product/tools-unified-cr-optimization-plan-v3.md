# Tools 统一优化实施方案 v3

> **状态：Ray 已确认方案边界。** 本版用于单个合并 CR 的需求登记及 PRD／SDD 输入，替代 v2《Tools 合并优化 CR 建议》的执行口径。方案确认不等于 CR 已注册、正式审批已完成或开发／部署已获授权。
>
> **本版收敛事项：** 一个 CR；G05/G06 一起实现；采用本地信任而非本地文档冻结；机器保证绑定；评审落盘与提交闭环；合法人类继续一次一 cycle；恢复保留原对象和事实。

## 1. 目标、范围和复用原则

建议 CR 名称：**CR 执行闭环与门禁减负修订**。不预分配 CR-ID，不另开 G05/G06 或小缺陷 CR。

目标：

1. 消除 AIFI-41 中重复出现的绑定、身份、提交、路由和线上合同不一致，避免完成一个节点后把同类收尾缺口交给下一位。
2. 删除重复人工确认和全文漂移造成的形式性阻断，同时保留真实失败、授权、签名、并发与发布安全边界。
3. 将代码源内容等价核验与同步后的最小重验放在同一工作项实现，避免重复算法和重复实现链。
4. 使用一份批准范围，内部独立提交、定点验证，最后沿现有整体评审和发布流程交付，不为每个工作包重走一套 CR 审批。

优先复用：现有 CR／Issue／task 关联、可信项目资源、workspace inspect、启动前绑定、crctl next、权限矩阵、durable transaction、CAS、controlledGit、审计、reviewLoop、Git tree、测试报告、checkpoint／发布事务和导入部署流程。

不新增：数据库、影子账本、权限框架、授权票据服务、万能恢复器、通用提交服务、新 CR 状态、多 Pipeline Runner、语义哈希、智能测试影响分析、后台重试服务或代码范围配置矩阵。

本方案不是上线后另一份长期执行事实源。批准后应把合同落实到权威实现、Skill、模板和实际线上消费者，不让方案散文与 crctl 长期各维护一套规则。

## 2. 已确认的 14 项决策

| 编号 | 确认结果 |
|---|---|
| Q1 | 绑定防漏必须由机器保证；已有可信 CR 关联的任务不能依赖每轮手工粘贴声明。普通无 CR 信号任务保持原行为。 |
| Q2 | **选择本地信任 B**：合法本地批准后的正文变化仅提示，由操作者判断是否需要重审，不采用 v2 的本地正文冻结口径。 |
| Q3 | review-record 提交失败回滚本次账本写入，保留评审 payload；恢复同一次操作，不重新判断、不额外消耗 attempt。 |
| Q4 | 已有权限的人类在目标唯一时可用普通“继续”恢复耗尽 loop；目标不唯一才询问，不要求固定措辞或完整命令。 |
| Q5 | 同一批准合同内，可同步调整相关调用者、现有测试和夹具，即使文件未逐一预列；新能力或安全承诺变化仍须正式确认。 |
| Q6 | 接受一次明确、合法、有边界的人工启动前置，不接受逐节点代跑；最终交付包含实际安装和生效验证。 |
| Q7 | 本地正文漂移提示规则贯穿审批、gate、validate、next 和合入，不能在后续入口重新因同一漂移阻断。 |
| Q8 | 独立代码仓按整个 Git tree 比较；README、配置、测试文件也属于该代码资源的内容，不加文档扩展名白名单。 |
| Q9 | 合法存量文档 PASS 缺 subject-sha256 可提示后继续，不仅为补摘要而强制重审；来源缺失或非法的批准不默认视为本地可信。 |
| Q10 | 当前 Issue 通过正式登记唯一关联某 CR 时，可复用该关联完成启动前绑定；不存在或多个关联时不得猜测目标。 |
| Q11 | 同一条人类继续指令只授权一次明确的 cycle 转换；重投不再次开轮，下一次耗尽需要新的指令。 |
| Q12 | 恢复保留原评审对象和原操作事实，不把旧 verdict 自动贴到新对象摘要上；无法安全恢复时停止报告。 |
| Q13 | TASK 集合增删或工具升级改变证据定义，只要当前必需产物齐全、结构合法，合法本地批准仅提示变化，不要求单独重签／重审。 |
| Q14 | 原代码源版本缺失或 Git 对象不可取得时，不用当前 HEAD 补造历史，不直接认定等价；尝试恢复原对象，否则沿既有测试、复评和必要代码确认建立新证据。 |

### 本地信任的明确含义

工具不再以全文／集合摘要变化替操作者撤销合法本地批准或推断业务范围变化。操作者负责判断是否需要业务重审，显式要求重审或撤销批准时走原流程。

它不允许：伪造批准、自动 PASS、忽略最新真实 BLOCK、隐藏测试失败、删除当前必需产物、写错工作区、绕过签名、把旧评审重新标成针对新对象，或在无法确定代码源时宣称等价。

## 4. 工作包 1：运行绑定、身份、提交和复评闭环

### 4.1 机器保证启动前绑定

按现有正式关联解析任务目标：

1. 消费 task 已有可信 CR 关联。
2. 没有直接关联时，可使用当前来源 Issue 的唯一正式 CR 关联。
3. 多个关联不猜测；无 CR 信号的普通任务保持原行为，不强制变成 CR 任务。
4. 对明确 CR 目标，复用当前任务的可信项目资源和 workspace inspect 核验 authority、真实路径及资源健康；不能把项目主 checkout 自动当成在途 CR 根。
5. 实际声明与正式关联或预检结果冲突时启动前停止，不静默覆盖。
6. 根据现有领取／Task 输入合同补最薄的字段接线，在进程启动前生成并注入完整上下文。数据关联不等于运行中重绑。

保留显式 execution_context 兼容，但正确性不再依赖协调者每轮复制。禁止扫描历史评论、用自由文本猜 CR、回退主机根列表或允许 Agent 运行中任意 rebind。

归档后新任务依据当前 inspect／阶段事实取得 authority；不继续引用已删除的 CR worktree。

### 4.2 保留 Git 身份

任务 trust 配置使用 Git 原生叠加方式，保留原有配置和身份加载链，不能为了 safe.directory 替换掉用户全局姓名／邮箱。

不改用户全局身份，不设置机器人身份兜底。提交所需身份不可用时，在账本写入前报告环境问题；已有未完成事务按恢复合同处理。

### 4.3 review-record 的成功必须包含隔离提交

统一正常 PASS／BLOCK 路径：

```text
前置核验 → payload/对象校验 → 构造本次 write-set
→ 既有 durable transaction + CAS
→ 仅本次实际 files[] 的隔离提交
→ 完成事务 → 发包含真实提交 SHA 的 outbox → 返回成功
```

- 无 bump 时提交实际 annotation、traceability；有 bump 时把 review-loop 一同纳入实际 write-set。
- 复用现有隔离检查，不能把“只 add 某文件”当作整个 index 已隔离；不得夹带或丢弃作者／其他任务的变更。
- 提交失败非零返回，回滚本次账本写入及本次暂存影响，保留 payload 和原操作恢复依据；不发成功事件，不推进后续。
- commit 后崩溃按既有事务完成事实恢复；不重复评审、不再次 bump，事件 SHA 必须对应真正包含评审账本的提交。
- 恢复固定原评审对象、结论及操作意图，不读取新对象摘要后把旧判断重新绑定。若原操作无法安全恢复，停止并报告，不伪造业务 verdict。
- 本地提交不自动变成远端发布。远端继续走 push-progress／checkpoint。
- advance 保持状态推进职责，不自动 add 评审文件或整个 CR 目录，不代提交作者代码；提交与事件完成事实必须一致。
- 上线前已有未提交评审承接原结果受控完成，不重跑 --bump-attempt。

具体恢复字段和接线在 SDD 中按已有 journal／intent／payload／recovery 能力定点设计，不新建“待提交评审”业务状态或影子账本。

### 4.4 作者收尾与普通 BLOCK 复评

作者回修使用既有链路：write-dev-plan → write-dev-tasks 增量同步／合法状态收尾 → 核验实际提交、status／next → Reviewer。

不要求全量重拆，不固定每轮提交次数，不让 write-dev-plan 冒用尚未完成的 write-dev-tasks 职责。

next 的普通 BLOCK 分支复用现有 subject/composite digest：

- upstream 优先走现有上游修订路线；
- 耗尽仍等待合法人类继续；
- 普通 BLOCK 对象变化且作者已收尾：建议复评，不自动 PASS；
- 对象未变：继续回修；
- 关键产物缺失／不可计算：原修复或技术失败；
- 无旧摘要：不推断作者已经修好。

工具、Skill、矩阵、模板、实际导入 instructions 同步，正式合同覆盖后收口临时例外，不再按 CR-ID／cycle 固定另一套路由。

## 5. 工作包 2：G01～G04 流程与门禁减负

### 5.1 G01/G02：本地信任规则贯穿各入口

仅对来源合法、stage／归属合法的本地批准应用本地信任；来源未知或非法不自动归入本地模式。服务端签名批准沿原严格校验。

本地路径：

| 事实 | 结果 |
|---|---|
| PRD／SDD／PLAN／TASK 正文变化 | 提示，不自动撤销批准或强制重审 |
| TASK 集合增删、证据定义升级，当前必需产物齐全且结构合法 | 提示，不为集合／定义变化单独重签或重审 |
| 合法存量文档 PASS 缺 subject-sha256 | 提示后继续，不伪造历史摘要或写新 PASS |
| 当前必需文件缺失、索引／依赖／记录结构非法 | 继续阻断 |
| 最新真实评审 BLOCK、blockers 非空、真实测试失败 | 继续阻断，不拿历史 PASS 覆盖 |
| 明确撤销批准或要求重审 | 执行既有合法路线 |

gate、validate、next、批准与合入结果必须一致。warning 不触发 onFail，不造成失败退出或隐藏的后续漂移阻断；有真实错误时 warning 不能覆盖它。

保持各接口既有字段类型；warning 使用现有可扩展形式，不统一重构返回结构，不新增 warning 专用提交／提示次数账本。

历史摘要、原批准及原 verdict 保留作追溯，不自动 resign，不改历史 subject 值来制造“仍相同”。进度仍优先使用现有 task done／索引，但不是以此替代已经确认的本地信任。

### 5.2 G03：取消默认开发启动重复人工确认

默认 coding 路径删除独立开发启动 human_approval／approve-dev-start 必经步骤。

首次 implement-code 前保留：合法设计批准、plan／TASK 完整性、最新计划评审 PASS／空 blockers、资源和实际 readiness；经现有 advance 合法进入 developing，不伪造 development-start 批准。

保留原审批调用与历史记录兼容，同步 developing gate、next、合法转换、Skill、模板／索引及当前平台消费者。验证真实存在的 comment 路径和 gate 投影，不因此实现完整 coding Runner，不为正在运行的旧图强行热换合同。

本 CR 自身仍按实施时合法有效的治理合同完成审批，不能提前用尚未批准／发布的新 G03 绕过自己。

### 5.3 G04：合法人类继续一次一 cycle

保留同一 cycle 的自动回修上限和历史 attempts。

耗尽后：

1. 使用已有权限判断和平台已认证人类触发事实，不能由 Agent 自报人类身份或仅加 --confirm。
2. 当前目标唯一时，普通“继续”可授权恢复；目标不唯一才询问，不要求固定措辞。
3. 固定来源、CR、loop、from-cycle、目标转换及原因到既有审计／操作恢复依据。
4. 同一指令仅授权一次明确的 cycle 转换；失败可恢复同一操作，重复成功投递不得再增 cycle。
5. 后续再次耗尽需新指令，不能重新解释旧评论为无限授权。
6. 新 cycle 不清真实 blockers，也不是业务批准；没有新的人类继续不得自行 reset。

复用现有 reset、事务和审计，不增加授权票据服务、权限数据库或新的常驻调度器。

## 6. 工作包 3：G05/G06 同一工作项实现

### 6.1 一个内容比较缝，两个消费目的

| 比较 | 用途 |
|---|---|
| 被评审／批准代码源 → 当前已提交源 | G05：额外 commit 是否改变实际代码内容 |
| 测试报告记录的源 → 同步后源 | G06：原测试是否仍对应当前交付内容 |

代码资源由既有仓库声明确定。独立代码仓比较整个 Git tree，不新增 codeRoot 配置、扩展名白名单、语义哈希或智能影响分析。

SHA 仍用于追溯和发布事务；不把内容等价解释成历史版本信息可以抹掉。知识仓其他 CR 的已提交账本变化，不作为当前代码资源变化；当前 CR artifact 按本地／服务端规则分别核验。

### 6.2 G05：合入对象核验

- 合法本地路径，代码仓 tree 相同：允许额外空提交等等价源推进，不因 HEAD 不同直接要求回实现。
- tree 不同：先更新测试／代码评审证据，必要时执行原代码确认；不能直接合入。
- 当前 CR artifact 正文、集合、证据定义漂移按 Q7/Q13 本地提示规则处理，不在 merge 阶段重新冻结；必需产物、结构和真实失败仍检查。
- server-approve 保留签名、摘要／源绑定及归属严格合同，不转成本地批准。
- workspace 健康、路径、仓集合、真实远端源同步、lease 等发布检查不放宽。
- 新发布事务固定此次实际发布的 source；已有产生副作用的 journal 按原意图和 source 恢复，不因后来的等价 HEAD 或文档提示改写进行中的发布对象。

批准入口、verifyReleaseSubjects、mergeCr 远端源预检及相关输出一同修改。不得只放宽一个 helper，而在后续 publish 再遇到同一 HEAD 相等条件。

### 6.3 G06：同步后的最小重验

保留已有 freshness 探测，减少无条件实现重放：

- 实施前合法同步完成：继续尚未开始的实施。
- 评审前同步后，代码 tree 与有效测试源相同：继续现有评审接续，不因同步重复实现／测试。
- tree 改变：先走已有测试报告与代码复评节点；真正测试／评审失败才回 implement-code。
- 树相等不代替报告、日志、真实退出码和 verdict 有效性，不把未执行的新验证宣称为已测。
- dirty、分叉、冲突、同步失败、环境不匹配：按已有相应失败合同处理，不猜测成功，不把技术中止计成业务失败。

复用现有节点、freshness 输出及必要消费者，不新增 CR 状态、完整执行器或后台重试。

### 6.4 无法确定原代码源

文档 PASS 缺摘要兼容，不能类推为代码源缺失也可等价放行。

先沿已有读取／同步恢复原 Git 对象。仍不可判时建立新测试、代码评审及必要代码确认事实，不以当前 HEAD 补造历史 source，不伪造原代码批准，不无理由重做实现。

## 7. 工作包 4：CI、小缺陷与实际生效

### 7.1 G07 与既有红例

合法逐文件用例数低于登记基线改为 warning；保留以下失败：

- 必需文件零有效执行、少跑／未登记文件、文件集合不一致；
- 加载失败、TAP 不可判或未收敛、真实未豁免失败；
- 登记 schema、基线字段或既有例外结构／期限非法。

沿用 manifest、suite report 和 exceptions，显式维护登记，不自动改基线，不建数量变化审批流程。摘要不能把有效例外中的实际失败说成所有测试均通过。

对已有四个 summary 宿主环境例外定点复现，复用 baseEnv 隔离测试子进程，根因转绿后撤销对应例外；不在生产任务全局清绑定变量，不靠数量 warning 隐藏红例。

已完成的 D 两处 fixture 修复保留回归，不重复实施。

### 7.2 Windows chainCheck

复用 node:path.basename 替换本机路径的 split("/") 文件名提取，增强 docCount 与原生嵌套路径断言，避免空扫描假通过。

不加路径助手／依赖，不改 gate 表达式，不扩建文档链类型或规则体系；使用现有测试入口验证。

### 7.3 发布和生效

复用实际维护来源的导入／发布流程，核对 CLI、daemon、Skill／instructions 和必要平台消费者的实际取用版本。生产者先兼容新合同，再切消费者；核验桌面监督恢复后的版本事实。

源码合入、成功构建或仓库镜像更新不单独算实际交付完成。所需人类动作、责任方与窗口在 plan 中提前列明，不到后续节点才发现。

## 8. 实施顺序及避免再次回退的约定

```text
现有计划评审内完成合同／验收可达性核对
→ 工作包 1：运行、提交和复评闭环
→ 工作包 2：流程与本地信任减负
→ 工作包 3：G05/G06 合并内容比较与最小重验
→ 工作包 4：CI／小缺陷收敛和实际生效
```

夹具与测试随各自功能同步，不机械等到最后才允许修；工作包 4 汇总收敛，不新增一道流程。

执行约定：

1. 先确认本次实际命令、入口、模式、执行者、资源、测试夹具和人工前置可达；复用已有计划评审，不新增预评审阶段。
2. 本 CR 正式治理使用已发布、已验证入口；候选 CLI 在隔离 fixture 或明确受控测试上下文使用。若稳定入口本身不可用，接受一次明确合法前置，不盲目重投，不逐节点人肉代跑。
3. 一開始把四个工作包、相关消费者／测试／夹具及部署边界纳入同一批准范围。文件清单是预计修改面，不是穷尽式辅助文件授权清单。
4. 工具不凭文档哈希推断范围扩展。操作者判断确需改变需求、安全承诺或批准范围时，走原正式确认路线；不能把不相干新能力塞进“相关夹具调整”。
5. 同一合同域可检查的问题在同一轮尽量列全，不在首个 blocker 后停止所有相关检查；不规定必须一次 PASS，也不新增评审计数层。
6. 技术中止修环境／同一事务，不重写业务 verdict，不重复 bump；真实业务 BLOCK 仍走正常回修。
7. 交接依赖实际产物、必要账本、状态、提交及规定的发布完成事实，而不是单个命令 exit=0。
8. 证据 ID 稳定，不为删除／调整命令全局重编号；验证与当前变更相关行为，既有发布 CI 做集成核验，不要求尚未存在的完整 coding Runner 回放。
9. 内部独立提交与测试，不按工作包重开 CR／重新登记批准链；最终按现有整体评审、代码确认和发布合同交付。

正式登记时，由既有流程填写三角色 owner、实际目标仓库和版本；本文不代分配人员、不预写治理账本。

## 9. 最小验收矩阵

下列 AC 是方案内的验收标识，后续登记时映射到正式工件，不是已经写入 CR 的账本。

| ID | 场景 | 必须结果 |
|---|---|---|
| AC-01 | 可信 task CR 关联；实际评论无手工声明 | 启动前自动生成／核验正确绑定，合法首调成功 |
| AC-02 | 仅有当前 Issue 的唯一正式 CR 关联 | 可复用；多个目标不猜测；普通无 CR 信号任务不退化 |
| AC-03 | 正式关联、显式声明、项目资源或真实根冲突 | 启动前拒绝，无业务写入，不静默覆盖 |
| AC-04 | Git 身份仅在原全局配置中 | task trust 不掩蔽身份；用户全局配置不被修改 |
| AC-05 | review-record PASS／BLOCK；无 bump／有 bump | 实际两／三账本隔离提交后成功；HEAD 与事件包含真实完成事实 |
| AC-06 | commit 失败，或有不相关暂存／作者变更 | 不夹带、不丢弃他人内容；本次写入回滚、payload 保留，无成功事件 |
| AC-07 | commit 后崩溃、同操作重投 | 按已提交事实恢复，不重评、不重复 attempt，事件引用正确提交 |
| AC-08 | 恢复期间被评审对象发生变化 | 不用新摘要重标旧 verdict；原对象事实保留，无法恢复则停止报告 |
| AC-09 | 作者增量回修完成；旧普通 BLOCK 对象已变 | 收尾后建议复评；对象未变继续回修；upstream／耗尽优先 |
| AC-10 | 合法本地正文／TASK 集合／证据定义变化 | 各入口仅 warning，批准有效，不在 merge 阶段再次漂移阻断 |
| AC-11 | 合法存量文档 PASS 缺摘要 | 提示继续；不补造历史摘要或 PASS；非法批准来源不自动放宽 |
| AC-12 | 必需产物缺失、结构非法、最新 BLOCK／测试失败 | 继续硬阻断，历史 PASS 与 warning 不覆盖失败 |
| AC-13 | server-approve 摘要／签名／归属变化 | 保持原严格拒绝，不伪装为本地批准 |
| AC-14 | 首次实施满足批准／计划评审／readiness | 无重复 dev-start 人工确认，合法进入 developing，不伪造批准 |
| AC-15 | 耗尽后有权限人类说“继续”，目标唯一 | 合法开下一 cycle，历史保留；目标不唯一才询问 |
| AC-16 | 同一继续指令重复处理、或后续再次耗尽 | 原指令不能再次开轮；无新指令不得 reset；失败可恢复原操作 |
| AC-17 | 代码仓 HEAD 改变而 Git tree 相同 | 本地路径可继续；版本追溯保留，签名／远端发布合同不被替代 |
| AC-18 | 代码、测试、README 或配置改变 tree | 先重验／代码复评，真实失败才回实现；不能直接合入 |
| AC-19 | 同步后 tree 与有效测试源相同／不同 | 相同继续；不同最小重验；不因同步无条件重做实现 |
| AC-20 | 原代码源／Git 对象不可取得 | 不以当前 HEAD 补历史，不直接认定等价；沿原路径恢复或建立新证据 |
| AC-21 | KB 其他 CR 已提交变化／当前本地 artifact 漂移 | 不当成当前代码仓源变化；本地 artifact 依 AC-10，健康／授权仍核验 |
| AC-22 | 已部分 publish 后再出现等价 HEAD 或文档变化 | 原 journal 意图及实际 source 固定，不追随后来对象 |
| AC-23 | 合法数量下降；少跑／零有效执行／加载／TAP／真实失败 | 数量下降提示，其他真实失败仍拒绝；例外仅按既有有效合同消费 |
| AC-24 | Windows 文档及嵌套目录；实际部署后新 run | basename 真扫描且断言数量；新 run 使用已验证 CLI／daemon／线上合同 |

使用现有测试文件、fixture 和原生入口，先固化错误场景再最小修改。测试覆盖安全边界与行为，不冻结无关措辞，不建设额外测试平台。

## 10. 交付与文档效力

交付应包括：批准范围内实现、相关行为／合同回归、真实测试与未测事项说明、必要索引／模板／Skill／线上消费者同步，以及现有发布流程下的实际生效证据。

本方案不承诺绝无业务回退。它承诺先消除可提前发现的合同矛盾和重复收尾，不用门禁放宽掩盖真实失败，不用临时例外代替正式路由。

**本版最终口径：一个 CR，机器保证绑定；本地批准及合法文档 PASS 不因正文／集合／定义漂移被自动撤销；评审提交失败回滚并恢复原事实；人类继续一次一 cycle；G05/G06 同一任务以代码树内容和可信源事实决定继续或最小重验。**
