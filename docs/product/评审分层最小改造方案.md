# 评审分层最小改造方案

> 本文合并《技术设计评审提速最小优化方案》和《SDD评审前移校验方案》。
>
> 本文是 AI First Platform 的平台级方案依据，不是某个业务 CR 的交付物，也不直接修改 `../tools/`。后续实施应在 sibling `../tools/` 仓库单独注册一个 tools CR，并严格遵守本文确定的最小范围。

## 1. 目标与结论

当前问题不是 `crctl` 写入慢，也不是缺少事务框架，而是两层评审的事实边界和回修组织不够清晰：

- SDD 评审以 FR 级映射为主，可能漏掉 AC 级不可达、SDD 自己引用的既有代码事实错误；
- plan/TASK 评审可能在 SDD 已审批后才发现设计落点不可实施，同时对 TASK 新造的代码事实、责任边界和假绿风险约束不够明确；
- BLOCK 回修时可能重复建立上下文，或把原本同一轮可以发现的独立 blocker 分批暴露。

本方案将两项优化合并为一个“评审分层最小改造” CR：

1. `review-tech-design` 前移检查 AC 设计落点、可达性、可观测验收和 SDD 自引用的既有代码事实；
2. `review-dev-plan` 聚焦 SDD/AC 到 plan/TASK 的翻译增量，核查 TASK 新造事实、真实责任边界和无关短路假绿；
3. 首次技术设计评审全量完成全部维度后统一形成结论，回修评审优先核对上一轮 blocker 和本轮变化；
4. 保留现有独立 reviewer task、Pipeline `reviewLoop`、UPSTREAM 路由、`crctl review-record`、三账本和 `maxAttempts=3`；
5. 不新增状态、Pipeline 节点、账本、缓存、索引、digest、事务框架或评审 Agent。

### 1.1 统一职责原则

| 层次 | 应拥有 | 不应拥有 |
|---|---|---|
| Agent | 路由、职责判断、选择 Pipeline/Skill | 状态机、Git 算法、受控文件写入 |
| Pipeline | 节点顺序、输入传递、`reviewLoop`、失败中止 | 复制 Skill 算法、手写账本操作 |
| Skill | 业务判断、步骤编排、输入输出、失败语义 | 手写原子账本逻辑、重复实现 `crctl` |
| `crctl` | 状态、门禁、CAS、受控账本写入、审计、原子提交 | 业务设计判断、LLM 评审结论 |
| 版本化脚本 | PRD/SDD/TASK/traceability 等确定性转换 | 状态推进、人工审批 |
| README | 面向人的流程总览 | 另一份可执行细节事实源 |

方案和实施均采用以下 ponytail 优先级：

```text
复用现有能力 > 标准库 > 原生 Git/文件 API > 已有依赖 > 一行代码 > 最小新增代码
```

## 2. 已解决的基础设施：保持不动

本 CR 只补业务规则、输入传递和授权合同，不再建立第二套事务或评审框架。

| 能力 | 现有事实 | 本方案处理 |
|---|---|---|
| reviewer 独立性 | `dev-agent` 将技术设计、开发计划和代码评审委派给独立 `quality-reviewer-agent` task/run | 保持每轮新建独立 reviewer，不复用作者会话 |
| Pipeline 编排 | architecture/code Pipeline 已有节点顺序、输入传递、`reviewLoop`、`replayNodes`、`onFail=abort` | 不新增节点，不改顺序和回放机制 |
| review 回修 | 已有 `review_feedback`、`self_repair_attempt`、`maxAttempts=3` | Skill 明确消费这些已有输入 |
| 评审落盘 | `crctl review-record` 已负责 schema 校验、CAS、annotation、attempt、traceability 和临时 payload 清理 | 不新增 payload、账本或写入器 |
| 状态与门禁 | 状态机、`gates.json`、人工审批和 UPSTREAM 转换已经存在 | 不改状态、门禁、审批或回边 |
| worktree 解析 | `crctl workspace inspect` 已返回 `operationalWorkspace` 和 `resources` | Pipeline 原样传递 `resources`，Skill 不猜路径 |
| 受控 Git | `controlled-shell` 已有只读 Git 白名单和 `crctl git` 适配 | 只补 reviewer 的只读调用授权，不扩展命令白名单 |
| 历史证据 | `review-annotations`、`review-loop.yml`、`traceability.yml` 已保存评审历史 | 历史 CR 不迁移、不追溯重审 |

### 3.3 范围冲突的最终裁决

原两份方案曾存在以下范围差异：

- “技术设计评审提速”方案建议只改 `review-tech-design/SKILL.md`；
- “SDD 评审前移校验”方案要求同时改 `review-dev-plan`、`write-tech-design`、两个 Pipeline 和结构测试。

合并后的裁决是：**使用一个 CR，但采用 8 个文件的最小闭环范围**。原因是：

- 只改 `review-tech-design` 无法让 SDD 产出 AC 设计落点，也无法给下游 plan 评审划清新增事实边界；
- 只改 Skill 而不传递 `resources`，代码事实核验不可执行；
- 只传递 `resources` 而不补 reviewer 的只读授权，输入合同会变成不可执行的提示词愿望；
- 以上改动均复用现有能力，不引入新事务框架。

## 4. 评审分层

核心原则：**前道做实、后道查增量；后道保留 UPSTREAM 安全网。**

```text
PRD
  -> review-requirement / approve
  -> SDD
  -> review-tech-design（强化） / approve
  -> plan / TASK
  -> review-dev-plan（职责澄清）
  -> 编码
```

| 校验 | SDD 阶段 | plan 阶段 |
|---|---|---|
| AC 设计落点 | 检查每个 AC 在设计层有可达、可观察的实现落点 | 检查 AC 落点是否完整继承到 TASK |
| 既有代码事实 | 只核 SDD 明确引用或依赖的既有实现事实 | 核 TASK 新造或细化的实现断言；新证据反证 SDD 时走 UPSTREAM |
| 验收可行性 | 检查设计结果和验收位置在设计层成立 | 检查 TASK 验收步骤能否证明 AC，是否落在真实责任边界，是否存在假绿 |
| plan 独有结构 | 不检查 | 依赖拓扑、估算结构、范围极简性、风险与回滚 |

plan 阶段不做无差别全量 SDD 重审，但任何维度发现 SDD 设计缺陷、上游变化或新事实反证设计时，仍必须报告 `repair-target=write-tech-design`。

## 5. `review-tech-design` 优化规则

### 5.1 输入合同

除现有 `cr_id`、可选 `reviewer`、`self_repair_attempt` 外，明确声明：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `cr_id` | string | 是 | 目标 CR-ID |
| `workspace` | string | 是 | `workspace inspect` 返回的 `operationalWorkspace` |
| `resources` | array | 是 | Pipeline 原样传入的 `{repo, worktreePath}` 清单 |
| `review_feedback` | object | 否 | 上一轮 blocker 和回修目标 |
| `self_repair_attempt` | number | 否 | 当前 reviewLoop 轮次，首次为 0 |

Skill 只能消费 Pipeline 传入的 `resources[].worktreePath`，不得：

- 拼接 `.rayai-worktrees/...` 路径；
- 回退主工作区；
- 使用会话中最近读取的其他仓库替代目标仓；
- 自行发现仓库或建立路径解析器。

### 5.2 首次评审

首次评审保持现有 8 个维度，并必须完成全部适用维度后再形成 verdict：

1. PRD↔SDD 对齐；
2. 架构合理性；
3. 数据模型完整性；
4. 接口契约；
5. 多仓架构约束；
6. 性能与安全；
7. 可测试性，收紧为可观测验收可行性；
8. Prompt 采纳影响，继续按既有条件触发。

评审者不得发现第一个 blocker 后立即结束。独立 blocker 应在同一轮完整汇总：

- 一个 blocker 只表达一个可执行问题；
- 同一根因的多个位置合并；
- 不同根因分别列出；
- 当前 CR 必须处理的问题进入 `blockers`；
- 普通建议、未来优化进入 `suggestions`。

### 5.3 回修评审

当存在 `review_feedback`、上一轮 `review-annotations/sdd.yml` 为 BLOCK，或 `self_repair_attempt > 0` 时进入回修模式：

1. 读取上一轮 annotation 和 `review_feedback.blockers`；
2. 优先读取本轮 SDD 变化；若运行时无现成 diff，使用上一轮 annotation、`review_feedback` 和当前 SDD 做定点复核；
3. 逐条判断旧 blocker 为已解决、部分解决、未解决或因设计范围变化需重新判断；
4. 受本轮变化影响的维度重新评审；
5. 未受影响的维度仍在本轮 `dimensions` 中给出结论，只能做有依据的快速复核，不能无证据继承 pass；
6. 新的独立 blocker 在本轮一并列出；
7. 不由 Skill 自动 reset cycle；
8. 同一 cycle 达到 `maxAttempts=3` 后停止自动回修，交由人工处理。

### 5.4 AC 级设计闭环

在现有 `PRD↔SDD 对齐` 维度中增加：

- 每条 FR 有对应技术方案；
- 每个 AC 有设计落点；
- 设计落点能产出 AC 要求的可观测结果；
- 关键前置条件不会提前过滤掉 AC 所要求的目标对象、状态、字段、行为或原因；
- 发现闭环断裂时记 blocker。

不新增 `ac-reachability` 维度，不改变现有 annotation payload schema。

### 5.5 可观测验收可行性

在现有“可测试性”维度中增加以下硬检查：

- 每个 AC 是否有可观察结果；
- 观察结果是否有明确的设计层验收位置；
- SDD 自己提出的断言能否基于其依赖的既有代码事实成立。

不提前编写完整 TASK 验收步骤。TASK 步骤的责任层、组合证明能力和假绿风险由 `review-dev-plan` 检查。

### 5.6 SDD 自引用代码事实

只核验 SDD 明确引用或依赖的既有实现事实，例如：

- 现有函数、类型、事件、数据库结构或配置；
- 现有模块行为、调用顺序或责任边界；
- 现有 API、OpenAPI 或协议约定；
- 方案成立所依赖的现有代码路径。

纯绿地设计允许明确记录：

```text
N/A（本 CR 无既有实现依赖）
```

不能用 `N/A` 掩盖已写入 SDD 的既有事实。

事实证据写入现有 `dimensions` 或 `blockers` 文本，不新增字段。明确依赖既有实现时，证据至少包含：

```text
repo / commit SHA / relative path / stable symbol / 核实结论
```

行号只能作为辅助定位，不能作为唯一证据。

## 6. `review-dev-plan` 职责边界

`review-dev-plan` 继续保留现有八类维度和双轨路由，不改 payload schema。

### 6.1 保留的 plan 独有检查

- SDD→plan 覆盖；
- plan→TASK 覆盖；
- TASK 可执行性；
- 依赖拓扑；
- 接口契约一致性；
- 验收可验证性；
- 范围与极简性；
- 风险与回滚。

### 6.2 新增的职责说明

- `sdd-to-plan`：检查 AC 设计落点是否完整继承到 plan/TASK，不做无差别 SDD 重审；
- `task-executability`：核 TASK 新造或细化的代码事实是否有权威 worktree 依据，目标、责任层、输入、输出和完成标志是否明确；
- `interface-contracts`：核函数名、参数、返回类型、事件、SQL 和 nil 责任层等 TASK 新事实；
- `acceptance-verifiability`：核验收步骤组合能否证明 AC，是否放在真实责任边界，是否会被无关依赖短路形成假绿；
- 其余 plan 独有维度继续执行，不因前移而删除。

TASK 新造或细化的实现断言应在权威 worktree 中定点核实。资源缺失、symbol 不存在或行为不符不得猜测，也不得静默写 `N/A`。纯绿地且无既有实现依赖时可以明确写 `N/A`。

### 6.3 UPSTREAM 安全网

以下情况继续使用现有 `repair-target=write-tech-design`：

1. plan 阶段发现 SDD 的设计断裂；
2. 新依赖、新路径或 TASK 新事实反证 SDD；
3. SDD 评审后发生 PRD 修订或代码基线变化。

同轮同时存在 SDD blocker 与 TASK blocker 时，不拆分状态或账本：保留全部 blocker，先修 SDD，再按现有 `replayNodes` 重新生成并评审 plan/TASK。

## 7. `write-tech-design` 输出约束

不新增 SDD 文件或索引。只在现有第 6 节“FR 到技术实现映射”中补充 AC 级信息：

```text
AC-xx
设计落点：负责产生结果的模块、流程、接口或数据字段
可观测结果：评审或测试时能观察到的状态、字段、事件或行为
可达性说明：关键前置条件不会提前过滤掉目标对象
```

只有依赖既有实现的断言才附代码事实证据。回修时优先依据上一轮 blocker 定点修订，不重写已确认的整体方案，除非 blocker 明确要求替换。

## 8. Pipeline 与只读取证授权

### 8.1 Pipeline

`architecture-design.pipeline.json`：

- `workspace inspect` 继续取得 `operationalWorkspace` 和 `resources`；
- `review-tech-design` 调用时原样传入 `workspace`、`resources`、`review_feedback`、`self_repair_attempt`；
- 不新增节点，不修改 `reviewLoop`、`replayNodes` 和 `maxAttempts`。

`code-implementation.pipeline.json`：

- 继续从 node-1 的 `execution_context` 获取 `resources`；
- `review-dev-plan` 调用时原样传入 `workspace`、`resources`、`review_feedback`、`self_repair_attempt`；
- 不新增节点，不修改现有双轨路由和回放顺序。

Pipeline 只负责输入传递，不复制 AC 判断、代码事实核验或 blocker 合并算法。

### 8.2 受控只读取证

由于 reviewer 需要核实既有代码事实，本 CR 同步补齐最小授权合同：

- `agent-skill-matrix.yml` 将 `controlled-shell` 加入 `quality-reviewer-agent.can-call`；
- `controlled-shell/SKILL.md` 将 `review-tech-design` 和 `review-dev-plan` 纳入只读 Git 取证调用者说明；
- 不修改 `rules.json`，不扩展 Git 子命令白名单；
- reviewer 只使用原生文件读取和已有 `crctl git` 只读能力；
- 不允许任意 shell、写操作、状态推进或受控账本写入。

允许的取证方式遵循已有能力：

- 文件读取：读取 `resources[].worktreePath` 下的目标文件；
- commit：通过已有 `crctl git rev-parse HEAD` 获取当前 worktree SHA；
- 必要时：使用已有只读 `diff`、`log` 能力；
- 不执行 lint、build 或测试；这些属于后续阶段。

## 9. 失败语义

### 9.1 技术失败：中止且不写评审记录

以下情况不得写临时 payload 或调用 `crctl review-record`：

- `resources` 缺失、结构非法或 worktree 不可读取；
- 必须读取的文件无法访问；
- 只读取证工具不可用；
- 无法确认明确依赖事实所需的 commit SHA；
- reviewer task 创建或绑定失败；
- 临时 payload 不存在或格式无法解析；
- `crctl review-record` 写入失败。

返回结构化错误，禁止退回“请在终端手工运行命令”。

### 9.2 业务 blocker：完成本轮并正常落盘

以下情况属于评审结论，完成全部适用维度后写入现有 `review-record`：

- AC 设计落点不可达；
- SDD 引用的既有代码事实不存在、行为不符或无法支持设计断言；
- TASK 新造事件、函数、SQL、nil 或责任层事实不符；
- TASK 未继承 AC 设计落点；
- 验收步骤放错责任层或可能被无关依赖短路；
- plan/TASK 事实反证 SDD，需要 UPSTREAM。

区分原则是：**环境不能完成评审属于技术失败；证据证明设计或翻译错误属于业务 blocker。**

## 10. 验收标准

### 10.1 文档与合同

- 两个 reviewer Skill 明确声明 `workspace`、`resources`、`review_feedback`、`self_repair_attempt`；
- 明确首次全量评审、回修增量评审和一次性 blocker 汇总；
- 明确 AC 设计落点、可达性和可观测验收；
- 明确 SDD 只核自身引用事实、plan 核 TASK 新造事实；
- 明确未受影响维度不能无证据继承 pass；
- 明确 `maxAttempts=3` 后停止，Skill 不自动 reset；
- 明确技术失败与业务 blocker 的不同处理。

### 10.2 结构与权限

- 两条 Pipeline 原样传递 `resources[].worktreePath`；
- reviewer 不拼接私有 worktree 路径，不回退主工作区；
- `quality-reviewer-agent` 只能通过既有受控只读能力取证；
- 不新增状态、节点、账本、索引、缓存、digest 或事务框架；
- `review-record`、attempt、traceability 和状态推进继续使用现有 crctl/Pipeline 路径；
- reviewer 每轮仍使用独立 task/run；
- `rules.json`、`crctl.mjs`、`gates.json` 和状态机无修改。

### 10.3 固定场景行为检查

至少人工复核以下场景：

1. 上游条件提前过滤目标对象，导致 AC 要求的结果不可达：SDD 评审 BLOCK；
2. SDD 明确引用的既有实现事实与 worktree 不符：SDD 评审 BLOCK；
3. TASK 新造事件、函数、nil 或 SQL 事实与代码不符：plan 评审 BLOCK；
4. TASK 验收放错责任层或存在无关短路假绿：plan 评审 BLOCK；
5. 同轮存在 SDD blocker 和 TASK blocker：保留全部 blocker，走 UPSTREAM；
6. 回修后旧 blocker 已解决：无变化时不得重复升格；
7. 回修引入新 blocker：不得因增量模式静默忽略；
8. 资源、worktree 或只读取证能力缺失：技术失败中止，不写 canonical review；
9. 首次评审存在多个独立问题：完成全部维度后一次性汇总，而不是逐个轮次暴露。

### 10.4 自动检查

在 tools 仓执行：

```text
lint-prompts.mjs --mode enforce
check-skill-matrix.mjs
node --test skills/shared/crctl/scripts/test/pipeline-structure.test.mjs
```

并运行相关 crctl 测试及 Pipeline JSON 解析检查。测试重点是输入合同、资源传递、权限关系、禁止事项、节点顺序、reviewLoop、UPSTREAM 和 `maxAttempts` 不回归。

不新增 LLM runner、评审缓存或行为遥测；LLM 评审组织行为通过 Skill 合同和固定人工场景验证。

## 11. 兼容、回滚与实施顺序

### 11.1 兼容范围

- 历史 CR 的 `sdd.yml`、`dev-plan.yml`、`review-loop.yml` 和 `traceability.yml` 不迁移、不重审；
- CR-2026-054 不追溯应用本规则；
- tools CR 合入并安装后，新进入对应评审节点的 CR 才使用新规则；
- 历史 payload schema 和现有 `review-record` 继续兼容；
- plan 评审仍保留八维度和双轨路由。

### 11.2 回滚条件

出现以下任一情况时暂停合入并回滚或提交修复：

- reviewer 无法获得已授权的只读文件/Git 能力；
- `resources` 被误解析、串读仓库、回退主工作区或拼接私有路径；
- reviewLoop、UPSTREAM、`review-record` 或三账本行为回归；
- 静态检查或现有 crctl 测试失败；
- 新规则无法形成合法 payload；
- 任一 Skill 开始直接写受控账本或自行推进状态。

回滚只使用普通 Git 回退或修复提交，不手工修改 CR 状态，不新增补偿事务。

### 11.3 实施顺序

```text
1. 在 ../tools/ 单独注册一个 tools CR
2. 按本文 8 文件范围编写 PRD/SDD/TASK
3. 先补 Skill 输入、评审职责和失败语义
4. 再补 Pipeline resources 原样传递和只读授权合同
5. 更新现有结构测试，不新增测试框架
6. 运行 lint、权限矩阵检查、Pipeline 测试和相关 crctl 测试
7. 验证首次全量、回修增量、AC 不可达、事实错误、混合 blocker 和技术失败场景
8. 合入 tools 后，仅由后续 CR 使用新规则
```

## 12. 最终决策

两份原方案不存在目标冲突，冲突主要是实施范围和职责落点的表达不一致。合并后的最终决策如下：

1. 用一个 tools CR 完成评审分层最小改造；
2. SDD 评审前移 AC 可达性、可观测验收和 SDD 自引用事实；
3. plan 评审核查 TASK 翻译增量、新造代码事实、责任边界和假绿；
4. 保留 UPSTREAM 作为安全网，不拆分混合 blocker；
5. 首次评审全量完成后统一结论，回修优先 blocker 和变化；
6. Pipeline 只传递输入，Skill 做业务判断，controlled-shell 提供受控只读取证，crctl 继续负责确定性落盘和状态事务；
7. 不新增状态、节点、账本、缓存、索引、digest、事务框架或 Agent；
8. 历史 CR 不迁移、不重审，CR-2026-054 不追溯套用新规则。
