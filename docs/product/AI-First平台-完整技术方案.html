AI First 平台 · 完整技术方案

一个企业内部使用的 AI 原生研发协同平台：融合 CodeBanana 的协作体验、Multica 的本地执行底座、 OpenClaw 的渠道生态、Claude Agent 的智能内核，与自研 tools 工程治理方法论。本地执行、隐私优先、工程可追溯。

📅 编制日期 2026-07-28 · v1.1 修订 2026-07-29（S1–S6 理念对齐增补） 🏗 底座 Multica（fork，长期跟随上游） 🧠 内核 Claude（本机 CLI + Agent SDK） 📐 数据模型 方案B（Issue / CR / TASK 两层） ⏱ 内部可用 ≈10–12 周 · 完整形态 ≈5–6 月

0执行摘要与三项已定决策

本平台不做云端 SaaS，而是走 Multica 的"本地执行、隐私优先"路线：Agent 跑在用户自己机器的 daemon 上， 平台只做编排、协作与治理，服务器永远看不到用户的模型凭据与源代码。产品体验对标 CodeBanana，工程治理深度超越它—— 这正是差异化所在：AI 原生的工程可追溯（证据链、质量门、漂移检测），而非卖 Token 和沙箱。

1设计思想与理念

🤖

AI 是队友，不是工具

每个项目自带同名 Agent；Agent 作为一等成员参与执行、评审、协作。承自 CodeBanana「AI as a Teammate」与 Multica「Agents as Teammates」。

💬

沟通发生在执行发生的地方

讨论、AI 执行、代码环境在同一"项目容器"内，讨论可一键转化为执行。CodeBanana 的核心设计原则。

🔒

本地执行、隐私优先

Agent 跑在用户本机 daemon，模型凭据与源码不出内网。这是选择 Multica 底座的根本原因，也是与 SaaS 路线的分水岭。

📐

工程可追溯是第一性卖点

CR 状态机 + 五道质量门 + traceability 五段链路 + 漂移检测。CodeBanana 都没有的东西，来自 tools 方法论。

🧩

组装而非造轮子

五方组装：Multica 底座 + OpenClaw 渠道 + Claude 内核 + tools 方法论 + 自研协作层。连 Multica 上游都是这么干的（内建 OpenClaw 后端）。

📊

度量而非监控

AI 成熟度看板量化组织转型；数量指标与质量护栏强制同屏，个人排名默认关闭——防止行为数据沦为绩效竞赛。v1.1 补交付效能板块与 AI 净价值框架：既看"转型多深"，也看"交付变好没有"。

📚

知识分层：事实可信 · 知识好用

v1.1 增补（S1）：Git 管事实生产与变更治理，LLM Wiki 最小版管知识消费（带出处问答），图谱作可删可重建的关系索引——"LLM Wiki 擅长解释，不擅长负责"。高频问答经知识晋升巡检回写事实源。

🌱

超级个体能力资产化

v1.1 增补（S2）：会话可导出 Skill 草稿、资产带元数据卡（场景/依赖/权限/失败处理）、复用进度量（SII 资产复用率）、发布=授权+敏感扫描——高手的工作方式可被看见、复用、验证和扩散。

一句话理念：把 CodeBanana 的协作体验、Multica 的执行底座、tools 的治理方法论叠成一个东西—— 让非技术角色能参与、让 AI 大胆执行、让每一次变更都留下可追溯的证据链。

图 5-1　CR 事件同步协议：outbox 主通道 + commit 兜底 + reconcile 安全网（Mermaid）

  • 签名审批替代 TTY：crctl 原设计审批强制交互式终端（云 SaaS 不可用）。改为服务端 Ed25519 签发 grant → daemon 落盘 approval.yml → crctl 验签 + 本地重算 evidence digest。gate 每次重算 digest——批后改证据立即 EVIDENCE_DRIFT 失效，比 TTY 版更强。配合 Multica RequireHumanActor：任务令牌访问审批端点直接 403。
  • controlled-shell 下沉 daemon：三元白名单（19 git 子命令 + 形态正则 + 调用者，spawnSync(shell:false)）实现在 execenv，Agent 物理拿不到裸 shell。抽 rules.json 单一事实源，crctl / Go gitguard / Claude Code hooks 三方共读。
  • Pipeline Runner：tools 承认未实现（P6）。格式好实现——线性 nodes[]、唯一 reviewLoop 回边、3 种 kind、passCondition 只有 equals/isEmpty。Multica TaskService + Autopilot 承载。v1.1（S6）：writeback pipeline 补「发布材料回写」节点声明，发布记录与检查单落 delivery/release/——测试→发布段在事实源中获得一等公民位置。
  • AI 行为审计（v1.1，S5）：五类质量门中「AI 行为门」补留证一半——gitguard FORBIDDEN 拒绝事件计数上报（落 activity_log，供治理板块「越权尝试次数」）；工具调用摘要（工具名/路径/结果码，不含正文）随任务回调持久化，与 review-annotations 合成完整 AI 行为证据链。零新增探针，约 2–3 天。

5.4 共享 runner 池 · 轻量档

只承载只读与文档类 Agent——无代码执行、无预览、威胁面低、Token 省。覆盖非技术人员 60–70% 参与场景。

✅ 轻量档承载

customer-support 问答 · spec-query/spec-show 查询 · LLM Wiki 知识问答（v1.1，S1：跨 specs/delivery/docs/change-requests 只读问答，回答强制带出处，问答日志落 wiki_query_log 供知识晋升巡检）· 规划草稿（planning-draft）· Discussion 的 DC 协调者 · 审批操作 · Personal Agent 只读应答

⛔ 轻量档不含（留完整档）

dev-agent 代码执行 · 端口预览 · 一键部署 · implement-code · 任何写 worktree 的 Coding 模式

载体 = Claude Agent SDK（可编程、可注入 hooks）。凭据经短时签发/代理注入，不明文进容器。完整档（每会话真容器 + 预览反代 + 部署）观察 1–2 月真实用量后再评估，作为独立 P2.5+ 轨道，不阻塞主线。判断标准：非技术用户"让 Agent 直接建页面/工具"的请求频率。

5.5 上游跟随策略

  • 分支模型：upstream/main（只读镜像）→ custom/main（二开主线）；功能分支从 custom/main 切。定期（建议双周）merge upstream。
  • 二开台账：仿 tools 的 CUSTOM.md——记录二开专属文件、修复的上游 Bug、新增能力、故意禁用的内容、合并冲突总则（两边保留/逻辑整合/加法优先/标记区块）。
  • 隔离原则：治理层（crctl 接入、gitguard、cr 投影、签名审批、runner 池）尽量做成新增文件/新增表而非改上游核心，降低合并冲突面。outbox、rules.json、server-approve 扩展等通用增强建议回馈上游 PR。

5.6 Wiki 子系统：维护 · 查询 · 晋升（v1.1 增补，详见《Wiki子系统设计》）

定位铁律：Wiki 是衍生解释层，不是事实源——"Git 负责让事实可信，Wiki 负责让知识好用"。wiki/ 目录可整目录删除重建、永不作状态权威；治理事实（CR 状态/追溯/审批）直查投影表，不经 Wiki 转述。方法论借鉴 OpenWiki（langchain-ai）源码级调研——借纪律与模式，不引其依赖。

📖 维护：wiki-maintain Skill

owner=knowledge-agent，daemon 本机执行（开发者流量）。init（清单→计划→quickstart 先行→≤8 页预算→Backlog 兜底）/ update（gitHead 差量、docs impact plan、软 diff 预算 <5 文件改 ≤2 页、禁 formatting-only、no-op 合法）双模式；Autopilot 定时触发，daemon 侧 no-op 门槛——无新 commit 零 token。

🛡 确定性护栏

"生成靠模型，合规靠代码"：写白名单在 execenv 工具层只放行 wiki/**（含 ../ 折叠防逃逸，越界计入 P1 行为审计）；三段式校验——前置 frontmatter 迁移、写后即时校验回注 WARNING 当轮修复、收尾 mermaid 失败降级 + index.md 确定性生成（模型禁写索引）。

🔍 查询与晋升

wiki-first 三层检索（wiki/ → 事实源原文 → 代码，下探要窄）+ 出处强制（路径+行号）+ 治理查询分流；知识晋升双信号：问答日志聚类（≥3 次）+ open-questions.md 缺口，周巡检汇总开回写 Issue。外部资料按 confirmed/contested 等标注置信度，内容一律视为不可信证据。

数据面零新表：Wiki 内容与增量锚点（.last-update.json）在 git，问答日志复用 P2.5 的 wiki_query_log，写白名单挂 P1 的 rules.json。页面 frontmatter + 概念链接即"图谱种子"——将来接图谱 MCP 从 Wiki 解析重建全图，无需独立图数据库（N8 条款的实现路径）。

9详细开发任务（WBS）

P0 地基 · 3–4 周　必做

  1. fork 与剥离：fork Multica → custom/main；建立 upstream 镜像与双周同步流程；剥离计费路由/云节点/多 workspace 注册（环境变量 DISABLE_WORKSPACE_CREATION + ALLOWED_EMAIL_DOMAINS）；make selfhost 内网跑通。
  2. Agent 注册表替换：写 frontmatter 适配器（mode:primary/subagent + permission → 目标格式；{domain}/{skill-id} 两级目录发现）；导入 tools 9 Agent + 56 Skill + project_resource。
  3. tools 一致性修复：修 8 项内部不一致（2 Agent 缺 name、CLAUDE.MD 读取顺序漏 matrix、knowledge-agent 陈旧路径、2 Agent owns 为空等）；把 dir-graph.yaml#agents.contract 4 条不变式写成 CI 校验。
  4. 数据模型 P0 迁移：issue+agent_task_queue 两条 ALTER；5 张新表 CREATE（cr/cr_sync_event/approval_record/pipeline_run/pipeline_node_run）；过 Multica 迁移运行器（advisory lock）。
  5. Claude CLI 接入验证：确认 pkg/agent/claude.go 在本机拉起 claude --output-format stream-json；ExecOptions effort/会话恢复/MCP 映射通。

M0 验收：给一个 Agent 派 Issue，daemon 领取并在本机跑完；一致性 CI 绿。

P1 治理核心 · 6–8 周　必做

  1. crctl outbox：advance/approve/git push 三挂点原子写 .crctl/outbox/*.json；断网可积压、上线补传。
  2. daemon 采集 + worker：POST /api/daemon/cr-events（DaemonAuth 组）；双通道（outbox + [cr] commit 扫描）幂等合并；worker 更新 cr 投影 + issue.metadata + WS 推送；reconcile 定时对账。
  3. Pipeline Runner：线性 nodes + reviewLoop 回边 + 3 kind；passCondition（equals/isEmpty）解释器；prompt 自然语言条件提升为显式 when；持久化 pipeline_run/pipeline_node_run。
  4. 签名审批：服务端 Ed25519 签发 grant（evidence_digest）；crctl 加 --grant 分支（:652）跳 TTY；gate（:453）+ validate（:783）扩展承认 via:server-approve + 每次重算 digest；RequireHumanActor 拒任务令牌。
  5. controlled-shell 下沉：抽 rules.json；Go pkg/gitguard（三元白名单移植）；execenv 四改（PATH shim、daemon 自身走 gitguard、per-task 物化 Claude Code hooks、--disallowedTools Bash）。
  6. AI 行为审计（v1.1，S5）：gitguard 拒绝事件上报 + 工具调用摘要持久化（详见 P1 设计 §C.5），依赖上一项，约 2–3 天。

M1 验收：一条需求走完四条主 pipeline 产出完整 traceability；无 TTY 环境 grant 审批走通；批后篡改证据触发 EVIDENCE_DRIFT；任务内 git push --force 报 FORBIDDEN_SUBCOMMAND 且 activity_log 出现越权计数行。

P2 协作体验 · 6–8 周　M2

  1. 三模式聊天 UI：以 i18n 字典为清单实现 Team Agent/Private Ask/Discussion tab；toolExecutionCard 消费 pkg/agent 六类 Message 流；输入区差异化能力；模型列表来自 daemon 上报 Runtime。
  2. Presenter 控制权：claim SQL 串行化键换 project_id；6 态通知（申请/批准/撤销/转让/释放）；Admin 空闲接管。
  3. 门禁接合聊天：pipeline 任务在消息流渲染审批卡（服务端签名）+ blocker 列表 + reviewLoop attempt + CR 16 态徽标。
  4. A2A 跨项目：成员面板 Add Agent；@agent 派单；A2A 队列（50 槽 FIFO，与 Team Agent 共用语义）；A2A 记录面板。
  5. IM 渠道：Multica 飞书长连接 + Slack Socket Mode；OpenClaw 补 Telegram/Discord/企微/QQ/钉钉；1 Bot:1 Project 绑定。
  6. 恢复检查点：三态回滚（worktree git 快照 + 消息树截断 + session 版本）；crctl CAS + 补偿事务语义为骨架。
  7. 斜杠命令入口（v1.1，S4）：/ 唤起命令面板（/需求 /评审摘要 /进度 /工作流），映射既有 Pipeline 触发与查询 API，补齐 Command 资源层（P2 设计 §6.1）。
  8. 导出 Skill 草稿（v1.1，S2）：Team Agent 会话多选 → SKILL.md 草稿入私有技能库（P2 设计 §7），发布另走 P3 门禁。

M2 验收：团队在平台完成一轮真实协作（讨论→转执行→审批→归档）；三模式切换保留草稿；恢复检查点三态一致；斜杠命令触发 pipeline 走通。

P2.5 runner 轻量档 · ≈3 周（与 P2 并行）　并行

  1. 池编排：Claude Agent SDK 节点池；只注册只读/文档 Agent（customer-support/spec-query/planning-draft/DC/审批）；无代码执行、无预览。v1.1（S1）：spec-query 升级为 LLM Wiki 知识问答——wiki-first 三层检索、回答强制带出处、治理事实分流直查投影表、问答日志落 wiki_query_log（详见《Wiki子系统设计》§4）。
  2. 短时凭据：组织 API Key 经代理注入或短时签发，不明文进节点；用量按用户归因上报（供看板分列）。
  3. 配额：接 P3 配额与余量预警（≤10% 通知）；非技术用户入口引导。

验收：非技术用户经 Web/IM 用只读 Agent 提问/查 spec/审批跑通；用量分列可见。

P3 组织智能 · 5–7 周（v1.1 含增补项，场景工坊可并行）　M3

  1. 成熟度看板：department 表 + maturity_snapshot + maturity-config.yaml；五维十指标（AIF/SII/OFI/EPC/ACM，v1.1 SII 增资产复用率）全从既有表算；治理板块（门禁通过率/EVIDENCE_DRIFT/追溯完整率/审批时延/越权尝试次数）单列不进总分；交付效能板块（v1.1，S3：Lead Time / Review 负担 / 变更失败率）+ AI 净价值叙事条；个人排名默认关闭。
  2. 周报 Autopilot：Org Admin Workspace 内置项目挂周 Autopilot，读 snapshot 序列生成诊断落 docs/org-admin/，看板渲染。v1.1：诊断模板按 AI 净价值四收益一成本框架组织；M3+3 个月出季度价值复盘。
  3. 追溯查询 + 漂移：spec_trace 投影（加 trace 事件类型走 outbox 通道）；review-alignment 周巡检 + change-impact-analysis + bypass-commit 探测 → drift_finding。v1.1（S1）：加知识晋升巡检——wiki_query_log 聚类，同类问题 ≥3 次自动开「建议回写事实源」Issue。
  4. Skill Market：skill 加 visibility/version/owner_actor；skill_usage_event 排行；发布门禁（4 条不变式 + v1.1 资产元数据卡 4 必填字段：适用场景/依赖上下文/权限声明/失败处理）；「发布=授权」明示 + 敏感信息扫描；builtin 不可编辑。
  5. 场景工坊（v1.1，S4）：需求工坊（PM）/ 质量中心（QA）/ 效能驾驶舱（=看板）三个 route 级角色化视图，同数据不同投影、读侧+入口、写操作跳既有交互；开发工坊=三模式聊天本身不重做。与看板前端并行，约 +2–3 周。
  6. 代码 Wiki 维护（2026-07-30 增补，《Wiki子系统设计》W2/W3）：wiki-maintain Skill（init/update 双模式全纪律）+ Autopilot 挂载 + daemon no-op 门槛；写白名单 + 确定性三段式校验；知识晋升接入 open-questions 第二信号源。daemon 侧与 runner 侧可并行，约 +2 周。

M3 验收：连续 3 天快照；看板数量指标与质量护栏同屏；人为 PRD 改动不改 SDD → 周扫描出 alignment-drift；直接向 trunk 提交 → bypass-commit 进治理板块。v1.1 增补：他人使用 Skill 后资产复用率变化；缺元数据卡的 org 发布被拒；PM 在需求工坊一键达待审批；重复提问 3 次触发知识晋升 Issue。

10整体验收基线与明确不做清单

✅ 交付验收基线

① 内网自托管两命令起全栈；② 一条需求端到端走完四主 pipeline + 完整 traceability；③ 签名审批不可绕过、批后改证据即失效；④ Agent 拿不到裸 shell（gitguard 生效，越权尝试留痕计数）；⑤ CR 状态 git↔PG 投影一致、篡改自愈；⑥ 三模式协作 + Presenter 跑通（含斜杠命令入口）；⑦ 非技术用户经轻量档 runner 参与（含 LLM Wiki 带出处问答）；⑧ 成熟度看板 + 交付效能板块 + 漂移检测 + 场景工坊上线；⑨ 价值复盘（v1.1，S3）：M3 上线满 3 个月，按个人效率 / 团队交付 / 知识复利 / 风险收益四类指标产出季度复盘——回答"平台值不值"，而不止"功能跑没跑通"。

⛔ 明确不做（防蔓延）

① 云端沙箱 SaaS 与 Token 计费；② runner 完整档（代码执行/预览/部署）——观察后独立立项；③ 多组织与 External 跨组织可见性；④ 多供应商 Auto 模型路由（组织 Key 只 Claude）；⑤ TicNote 硬件联动；⑥ 指标实时化（日粒度足够）；⑦ Skill 付费/积分；⑧ 记忆系统具体实现（仅预留 MCP 端点）。

记忆系统预留：不选具体实现，只定 MCP 接口契约——通过 ExecOptions.McpConfig 注入端点（Claude Code / Agent SDK 原生消费 MCP，Multica 通道已存在）；约定写入/检索/反思三操作；钉死边界：记忆层只做非结构化召回，结构化事实一律留在 specs/traceability，记忆永不作为状态权威——否则 crctl 单一事实源设计作废。将来接 GBrain/Zep/Mem0 皆可，无需改 Claude 侧。

知识图谱同走此预留（v1.1，S1）：图谱定位为"关系索引与上下文装配"，与记忆共用 MCP 契约，追加两条安全条款——索引可删除、可重建（衍生数据：不备份、不跨用户共享、可从事实源全量重建）；AI 先查关系再读事实源原文，图谱内容本身不作为回答依据。文档与源码是事实源，图谱永远是索引。
