# Tools 合并优化 CR 建议 v2：基于 AIFI-41 过程日志

> 本版替代上一轮“3 个近期 CR + 1 个条件后续 CR”的拆分建议。按 Ray 本轮要求：**建议合成 1 个 CR；G05/G06 明确一同实现，不再作为观察后另立项的事项。** 本文是分析与实施范围建议，不是已注册 CR、开发授权或审批记录。

## 一、先给结论

上一轮按技术主题分成四个 CR，便于隔离风险，但低估了当前 CR 流程本身的成本。对这组高度关联的工具改造，拆四次就意味着重复登记、设计/计划评审、批准、部署和交接，不划算。

建议一个 CR，暂拟名：**CR 执行闭环与门禁减负修订**。内部按依赖分批实现、独立提交、定点测试，不为每批重新启动需求和设计审批。

核心顺序：

```text
先核对合同、入口与验收是否真的可执行
→ 修启动绑定、身份、评审提交和旧 BLOCK 复评
→ 做流程/门禁减负，G05+G06 共用内容比较一同交付
→ 修 CI/Windows 小缺口并完成真实发布生效验证
```

AIFI-41 的曲折并不主要来自“实现写得复杂”，而是 **新旧组件混用、工具/Skill/线上指令互相矛盾、验收要求不可达、文件授权清单漏掉必需夹具、评审成功没有提交完成事实**。如果这些不先修订，新的 CR 即便减少审批节点也仍会曲折。

## 二、过程日志复核范围

本轮通过 Multica CLI，读取 AIFI-41 的根线程概览，并展开 **19 个关键线程、160 条去重评论**，覆盖旧 BLOCK 卡住、cycle reset、实现/夹具阻断、计划与 SDD 回退、部署桥、提交身份失败、临时例外、cycle 4、归档续清。

不是完整穷举所有运行日志，不能给出“多少百分比时间浪费”的统计结论。以下判断引用可追溯的具体事件；不把所有 BLOCK 都说成误阻断。

基线仍为上轮核查的已合并 tools/multica 源码。本轮只分析过程，未修改代码、Issue、CR 状态或部署。

## 三、真正导致反复绕行的六条因果链

### 1. 新 CLI 先被节点消费，旧 daemon 仍发布旧字段

评论 `01a10341-9187-7188-8294-3872a519d718` 独立复现：

- 新 tools 的 bindTaskWorkspace 要求绑定三元组完整；
- 在跑 daemon 仍发布旧 CRCTL_WORKSPACE/AUDIT，缺 OPERATIONAL；
- 节点实际入口已解析到本 CR tools worktree，而不是稳定发布版；
- 同一问题在 reviewer 和 coordinator 都复现，重投不会改变生产者版本。

**根因不是作者还没改对 plan，而是生产者/消费者和发布顺序没有闭合。**

应先修订：当前 CR 的治理入口与候选待测 CLI 分开；生产者先满足新合同，再切换消费者。运行入口、安装版本、线上 Skill、桌面监督来源都沿已有发布维护方式检查，不建立版本注册服务。

### 2. 机器存在回退边，但没有任何被授权的 Agent/Skill 能执行

评论 `01a102e4-3531-7933-b886-50aeed365e95`、`01a102e9-8fe4-7b9e-b360-4967499a8cd4`：

- status 为 developing，尚无 test-report；next 是 implement-code → write-test-report；
- legalNext 却包含 review-code:plan-blocker → write-dev-plan；
- reviewer 的 Skill 限定 code 阶段 BLOCK 回 implement-code，明文禁止 write-dev-plan；
- coordinator 承认委派前提错误，“有状态转换”不等于“有合法执行者”。

后续 `01a10824-10d0-73e7-a32a-b12408be7509` 又出现：Skill 本身支持 upstream 分支，但线上临时例外不覆盖该动作。

**根因是工具、Skill、线上 instructions 三份合同漂移，不是 reviewer 不愿推进。**

应先修订：只检查本 CR 会触及的 next/转换、Skill owner、实际线上消费者，确保有一条真正可执行的路线。复用 next 和现有权限矩阵，不新增编排器、万能回退 Skill 或授权框架。没有执行合同的分支不拿来派单。

### 3. 验收要求本身互斥，作者回修文档无法实现

评论 `01a1080e-a3d0-7bd5-90f8-4067f431e3c8`、`01a10813-0884-75ca-8247-b78a7a573bab` 证明 B-10 所要求的组合入口构造性不可达：

```text
节点收到有效 execution_context
AND 两个绑定键都 absent，处于旧显式 CLI 模式
AND 使用登记的新 tools 入口
```

但新版启动合同恰恰会给该节点注入绑定，首调缺 workspace 会合法自动归一。不能既要求有效绑定自动生效，又要求同一个首调返回 WORKSPACE_REQUIRED。

`01a10966-7c3a-76c0-a293-a196adfffc76` 的技术设计评审因此提出 B-10/B-11：受控入口/授权边界缺失，以及起草依赖快照被当成本次 HEAD 核验事实。

**这部分是有效业务阻断，不应靠 warning 或临时例外放行。**

应先修订：

- 新绑定模式与旧显式模式分开做现有黑盒测试，不要求不可能的复合环境；
- 已存在真实执行入口才要求节点集成验收，不能把未来完整 Runner 的能力列成本期必需证据；
- 基线 SHA 作为追溯事实保留，区分当前依赖事实，不把所有依赖永久冻结在起草快照；
- 只对本次实际修改的关键行为建立验收，不新增测试框架。

### 4. 要求证据跑绿，却不允许修其必需夹具

评论 `01a10182-cfe2-7c4e-842d-ad491b5e4307`：

- merge-fixture 继承宿主半绑定，需约三行隔离环境；
- fault-harness 用非 Git 临时目录，但新的锁内恢复取样要求真实 HEAD，需初始化并提交基线；
- 它们是必跑证据，却都不在 TASK 允许修改文件清单中；剩余任务挂在追加裁决之后。

这两处已随 075 合入，**不是新 CR 的待实现项**，但暴露的规划方式必须改。

应先修订：批准范围以行为/模块/安全边界为主，同时明确“相关调用者与现有测试、夹具可为满足同一合同同步调整”。文件清单可以列预计修改位置，不把每个辅助文件变成单独追加审批。新增业务能力、权限扩大、发布协议变化仍必须升级范围。

另一个同类摩擦：评论 `01a10cef-8261-76b2-9838-acda949ccb2c` 核查 156 处 cmd-NN 引用，删除/调整命令后产生机械顺移和假指针风险。**证据 ID 应稳定，不因删一条命令给后面的全部重新编号。** 保留既有命令表即可，不建证据管理服务。

### 5. 评审已经落盘，又被身份/提交收尾打断

评论 `01a106b4-54d3-7c2d-a66b-70768ec42383`、`01a106b8-c97a-73d0-8cac-126ba64ec90c`：BLOCK 已落盘，但 task 的 GIT_CONFIG_GLOBAL 掩蔽原全局邮箱，commit 报 Author identity unknown。

评论 `01a10966-7c3a-76c0-a293-a196adfffc76` 再次实测：review-record exit=0，三份证据未提交，HEAD 不变，KB 变 dirty。后续节点的 clean 前置因此不能通过。

这与上轮临时 Git fixture 的黑盒复现相互印证。

应优先实现：review-record 在既有事务内完成实际 files[] 的隔离提交，成功后才发真实 SHA 的 outbox；失败恢复不重复 bump。保留原 Git 配置/身份加载链，不修改用户全局身份。advance 不扫整个 CR 目录，review-record 不自动 push。

### 6. 用临时例外治路由，例外又写死轮次，形成第二套流程

评论 `01a10ea7-8ae4-726f-b165-e921001bcbd0`、`01a10eb3-bb52-701f-abd7-6b89a0efbd6f`：

- owner 已开启 cycle 4，尚有 attempt 额度；
- 线上例外仍把条件写死为 current-cycle:3；
- cycle 4 的复评零写入中止，又要 Ray 修改例外条款。

**这个中止来自例外文本，而不是三次自修复上限。** 仅增加非 TTY reset 不能解决它。

应先修订：根治 next 的普通 BLOCK 对象变化复评分支；正式合同覆盖回修、upstream、耗尽后的合法继续。临时例外不成为常驻路由副本，不固定 cycle 字面值，不再为每轮补授权文本。授权失败时 reviewer 停止是正确行为，问题应由合同维护方修。

## 四、最需要先修订的项目排序

| 顺位 | 项目 | 为什么在前 |
|---|---|---|
| **0：定稿前** | 合同可执行性：入口版本、真实验收、责任方/路由、夹具范围、必要人工部署前置 | 075 最昂贵的往返来自“计划已批准但执行不了”。应在审批前发现，不到 developing 再回退 SDD |
| **1：实现首批** | 绑定/声明防漏、Git 身份、评审隔离提交、真实 outbox SHA、失败不重复计数 | 同时影响作者、reviewer 和 coordinator；没修好，每次转交都可能再次被 dirty/权限/身份挡住 |
| **2：实现首批** | 普通旧 BLOCK 对象变化转复评、plan→TASK 增量收尾、工具/Skill/线上指令同版本 | 去掉“作者已改完却还被指回修”的循环，替代按 CR/cycle 追加的临时例外 |
| **3：实现中批** | G03，收窄后的 G01/G02，G04 的合法人类继续 | 取消重复 dev-start 确认；减少进度噪声；真实变更仍受评审，技术中止不能被记成业务失败 |
| **4：实现中批** | **G05+G06 同一工作项** | 本 CR 明确实现。共用源内容比较，避免各写一套 freshness/发布算法；但本轮日志不能证明它们是 075 的主要曲折来源，不能挤到提交/路由修复之前 |
| **5：收敛交付** | G07、现有 summary 夹具例外、Windows basename、部署生效验证 | 先修真实测试/环境根因，再让数量下降只提示；Windows 小修独立测试即可，不独立开 CR |

runtime 启动失败、provider 失败等不要混入业务 BLOCK，也不要为其反复改 plan。沿已有运行配置/故障处理入口处理，必要时先做不含 CR 写入的轻量探针；不建设新诊断服务。

归档后续清的任务也要取当前 authority，不能继续复制已删除 worktree 的声明。评论 `01a110e2-88c9-7456-9d3b-afe2f1147e79` 的启动错误是 `workspace resource is missing`。复用 inspect 和当前阶段事实生成新任务上下文，不开放运行中任意重绑。

## 五、一个 CR 的最小实施范围

建议只用一份 PRD/SDD/plan、一轮正常的批准链，下面是同一 CR 内的工作包，不是四个新 CR。

### 工作包 1：运行与评审闭环

- 在 075 已有启动前绑定上补声明防漏/必要的已有关联透传，普通无 CR 信号任务不退化。
- Git trust 配置保留原有身份。
- review-record 复用 durable transaction，隔离提交两/三份实际账本，提交后才成功/outbox；崩溃恢复不再 bump。
- 普通 BLOCK 摘要变化转 review-dev-plan；upstream 与耗尽判断优先。
- 作者按既有 write-dev-tasks 收尾；交接只读消费真实 status/next、提交和资源健康事实。

### 工作包 2：流程和门禁减负

- G03：默认取消开发启动重复人工确认，保留设计批准、计划独立评审及实施前 readiness。
- G01/G02：先消除进度、无关记录导致的重复校验；进度优先使用现有 tasks/_index/task done。需求/设计/任务范围变更仍要正式处理，不凭“本地记录”放行一切漂移。
- G04：复用已有人类确认或平台已认证触发来源开启下一 cycle，并在现有 audit 中留下原因/来源。不清历史，不允许 Agent 仅加 --confirm 自证授权，不新增授权票据服务。
- 工具、gate、next、Skill、实际线上 instructions、当前平台投影一起更新；不为这项工作实现完整 coding Runner。

### 工作包 3：G05/G06 合并实现

二者在本 CR 同一任务、同一内容比较缝内实现，不独立设计两套 helper，不留给后续观察 CR。

| 被比较对象 | 比较目的 | 结果 |
|---|---|---|
| 被评审代码源 → 当前已提交源 | G05：代码批准是否仍覆盖当前代码内容 | 内容相同允许额外 commit；内容变了更新测试/评审 |
| 测试报告记录的源 → 同步后源 | G06：原测试是否仍对应当前交付 | 内容相同继续；内容不同先重测/复评，真正失败才重做实现 |

最小规则：

- 独立代码仓先比较整个 Git tree，复用原生 Git 和现有 repo map；不加 codeRoot 配置、扩展名白名单或语义影响分析。
- 继续记录原 SHA 作追溯，内容比较不抹掉版本信息。
- 实际代码/测试内容变了必须重验；未知测试源、Git 对象缺失、比较失败不能当成等价。
- PRD/SDD/关键 artifact 的批准边界不随整树等价一起放松。
- server-approve 签名/归属、dirty/路径、远端源同步、lease 与已启动 journal 的固定发布对象保持严格。
- verifyReleaseSubjects 与 mergeCr 的源预检消费者一起调整，不能只修 helper 后在后续 publish 再被同一个 SHA 条件拦住。
- 复用现有 write-test-report/review-code、freshness 输出和恢复流程，不新增执行器、数据库或后台重试。

### 工作包 4：小缺陷、CI 和实际生效

- G07：合法用例数下降提示；必需文件零有效执行、少跑文件、加载/TAP 失败和真实红例继续阻断。
- 四个 summary 例外按宿主绑定环境定点复现，复用 baseEnv 修根因，转绿后撤对应例外；不靠 G07 掩盖。
- Windows chainCheck 用 basename，增强 docCount/嵌套路径断言。
- D 已完成的两个 fixture 只保留回归，不再次实现。
- 使用已有导入/部署流程核对 CLI、daemon、实际 Skill/instructions 的生效版本，以及桌面监督后的版本事实。

## 六、如何让这个新 CR 不重演 075

不增加新的门禁清单系统，只在现有计划里提前说清以下规则。

### 1. 不让待开发工具管理自己的正式审批

本 CR 的正式状态/审批默认使用已发布、已验证的治理入口。候选 CLI 在隔离 fixture 或明确的受控测试上下文验证。需要真实部署验证时，先让生产者满足新合同，再切消费者。

不能再出现“TASK 完成后自动让下一 reviewer 使用未部署配套 daemon 的新 CLI”。若当前环境连合法登记/评审提交都做不到，先明确一次必要前置与责任方，不盲目重投。

本 CR 也不能拿尚未批准/发布的 G03 或其他新门禁来绕过自己的当前审批。

### 2. 首轮计划评审先检查可达性，不先追求表格齐全

复用已有计划评审，先确认：命令存在、入口模式自洽、必要资源可用、真实执行者可调用、夹具可同步修订、必要人工部署动作已有责任方。发现矛盾一次列出同一合同域的问题，不让作者补完 A 后才首次检查紧邻的 B。

不新设一个“预评审阶段”，不新增评审次数账本。

### 3. 只对真正的范围/安全变化回到上游

- 同一合同内的测试夹具、调用者兼容和文档错误更正，在预先批准的边界内处理。
- 新业务能力、审批/签名承诺变化、权限扩大、发布协议变化才升级范围。
- 技术中止修环境或完成同一事务，不记新的业务 verdict，不重评、不 bump。
- 已评审对象真正改变才进行相应复评；源树改变先重验，不直接重做实现。

这不是取消 SDD 的约束，而是把“有价值的范围边界”与“逐文件、逐措辞审批”分开。

### 4. 节点完成必须是可承接的事实

业务产物、必要账本、状态、提交及规定的发布完成事实齐全才交接。由已有工具和恢复承担确定性收尾，不再每轮让 Agent 自行补一段相同的提交脚本。

局部提交/发布失败按既有事务恢复，不以重新评审来恢复 Git。节点确有真实 BLOCK 时仍保留正常回修。

### 5. 内部分批提交，不分批重新审批

一开始就把四个工作包及相关夹具、消费者、部署边界纳入同一批准范围。每包独立可验证；后包依赖前包；最终走一次整体代码评审/代码批准及现有发布流程。

如果实施中发现真正改变安全承诺的新增需求，仍需按正式流程确认，不能预先承诺“绝不回退”。目标是消除可提前发现的无效往返，不是保证所有评审永远 PASS。

## 最终建议

**合成一个 CR；G05/G06 一同实现；优先修可执行合同、版本接线、提交完成和复评路由。**

不要再把“将来某节点应能运行”写成当前硬验收，不要把已批准方案中的矛盾交给作者反复盲修，也不要用不断追加临时例外替代正式合同修复。
