## 0. P3 的四个交付物与一条设计主线

1. **AI 成熟度看板**——回答管理层「AI 原生转型进行到哪了」+「交付系统有没有变好」（转型仪表盘与价值仪表盘互补，见 §1.2）。
2. **跨 CR 追溯查询 + 漂移检测**——回答工程侧「这个功能是谁、经哪个 CR、什么证据落地的；基线和现实漂了没有」。
3. **内部 Skill Market**——把个人工作流沉淀为组织资产的流通面（含复用授权元数据，防止复用变成新一轮口口相传）。
4. **场景工坊（角色化视图）**——同一份数据按角色投影（§4），AI 内嵌在工作场景里而非旁挂聊天入口。

设计主线：**P3 不新增采集管道，只做已有事件的聚合与呈现**。P0–P2 落地后，每一次任务执行（task_usage）、每一次状态推进（cr_sync_event）、每一次审批（approval_record）、每一轮 reviewLoop（pipeline_node_run.attempt）、每一次点踩（P2 反馈）、每一次越权拦截（P1 §C.5 行为审计）都已经是结构化行——P3 是这些行的读侧。场景工坊同样是读侧：不新增页面数据源，只做既有 route 的角色化重组。**仅有的两条新数据流**：Skill 使用遥测（§3.4，搭任务完成回调的便车，零额外探针）与 `wiki_query_log`（§2.3，随 P2.5 落库，P3 只读）——其余全部为读侧聚合。

## 1. AI 成熟度看板

### 1.1 呈现结构（对齐快照还原的原产品布局）

```
┌ 顶部：日期区间选择 · Owner mode 标记 · 「每日 00:30 更新前一天数据」──┐
│ 统计条：活跃成员 | Token 总消耗 | (可选)估算成本                        │
│ Token 趋势图（按日，可下钻 项目/个人/模型）                           │
│ 排名区：[项目排名 | 个人排名] 切换 Tab（个人榜默认关闭，见 §1.5）       │
│ 五维雷达图：总分 + AIF/SII/OFI/EPC/ACM                                  │
│   └ 每维展开：子指标卡片 + 环比箭头                                     │
│ AI 净价值叙事条（S3）：时间/质量/知识/风险四收益 − 成本，各挂真实指标   │
│ 「AI 原生组织建议」：LLM 生成的诊断与建议（含历史版本）                 │
├─ 治理板块（不进总分）：门禁一次通过率 · 证据漂移 · 追溯完整率 · 越权尝试 ┤
└─ 交付效能板块（S3 增补，不进总分）：Lead Time · Review 负担 · 变更失败率 ┘
```

与原产品的两处架构差异：**不做独立子域名 iframe**（内部平台没有隔离发布的需要，做成主应用的一个 route，复用 `packages/views` 体系）；**成本列可选**（本地执行模式下平台不代付 Token，成本 = token × 价目表估算，价目表是一个可编辑的 `model-prices.yaml`，不精确、仅供量级参考，UI 上明确标注"估算"）。

### 1.2 五维指标定义（本平台公式，全部可从既有表算出）

总分 = Σ(维度分 × 权重)，权重与阈值集中在一个版本化配置 `maturity-config.yaml`（不硬编码，改配置即改口径——沿用 crctl 的"改声明不改代码"哲学）。每个子指标归一化到 0–100：`score = clamp(100 × (x - floor) / (target - floor))`，`floor/target` 在配置中按组织基线设定并随季度调整。**观察期**：看板上线后前 4 周为基线校准窗口——快照照常生成，但看板只呈现原始值与趋势，雷达图总分显示「基线校准中」；观察期结束后用实测分布的分位数规则（floor ≈ P10、target ≈ P75，规则写入配置）自动生成第一版基线，此后正式计分。

| 维度 | 子指标 | 公式（分子/分母均为真实列） | 数据源 |
|---|---|---|---|
| **AIF**·AI First | Token 强度 | Σtokens / 活跃成员数 / 天 | `task_usage_daily` ÷ `member` 活跃数 |
| | AI 渗透率 | 当期发起过 ≥1 个 Agent 任务的成员 / 全体成员 | `agent_task_queue.initiator_user_id` distinct |
| | AI 效率系数 | Σtokens / 归档 CR 数（越低越好，反向计分） | `task_usage` join `cr(status=archived)` |
| **SII**·超级个体 | 超级个体占比 | 当期独立驱动 CR 跨 ≥3 个阶段（需求/设计/编码任占其一即计）且有归档产出的成员 / 活跃成员 | `cr.owners` 三角色 + `cr_sync_event` 的 trigger 归因 |
| | 人均 CR 吞吐 | 归档 CR 数 / 活跃成员数 | `cr` |
| | 资产复用率（S2 增补） | 成员发布的 org 可见 Skill 被**他人发起**的任务使用的次数 / 该成员发布的 Skill 数——排除条件 = 任务发起人 ≠ 作者（同项目同事使用是健康的扩散信号，不排除）；分母为 0（未发布过 Skill）的成员该子指标记「不参与」，维度内其余子指标重新加权、不惩罚——度量"沉淀被扩散"，只发不被用不加分 | `skill_usage_event` join `agent_task_queue.initiator_user_id` / `skill.owner_actor` |
| **OFI**·组织扁平化 | 项目协作规模 | 平均每 CR 的参与人数（owners ∪ 评论者 ∪ 任务发起者；越小越"扁"，目标区间计分而非越小越好——低于 2 不加分，防止指标惩罚协作） | `cr.owners` + `comment` + `agent_task_queue` |
| | 项目活跃率 | 近 14 天有任务或状态推进的项目 / 全部项目 | `agent_task_queue` + `cr_sync_event` |
| **EPC**·原型直出 | 原型直出率 | 全部质量门 reviewLoop 一次通过（attempt=1）的归档 CR / 归档 CR | `pipeline_node_run(attempt)` |
| | 规划转化率 | 由规划报告 source 或 Issue 升级产生的 CR / 全部 CR | `cr.source_path` + `issue.cr_id` |
| **ACM**·Agent 协作成熟度 | Team Agent 使用深度 | 经共享队列（有 cr_id/issue_id 归属）的任务 / 全部任务（对照 Private Ask 纯私聊） | `agent_task_queue` 来源键 |
| | 流程完整率 | 走完 4 条必跑 pipeline 归档的 CR / 归档 CR（有 CR 却绕过 pipeline 的是治理缺口） | `pipeline_run` 覆盖 4 个 pipeline_id |
| | Cron/A2A 采用 | 有 ≥1 个活跃 autopilot 或跨项目 Agent 调用的项目占比 | `autopilot_*` |

**治理板块**（第六组，本平台独有，不进总分、单独呈现——它们是质量护栏，不是竞赛项）：门禁一次通过率（gate 首次即过 / gate 总次数）、`EVIDENCE_DRIFT` 发生次数（证据摘要漂移，TTY 与 grant 两条审批路径均计入，非仅签名失败；数据源 P1 §B.4 的 `activity_log` 行，上线前置依赖 P1 D7）、追溯完整率（`traceability.yml` 五段齐全的归档 CR 占比）、审批时延 P50/P90（review 通过 → approval_record 的间隔，暴露人工瓶颈）、**越权尝试次数**（S5 增补：gitguard FORBIDDEN 拒绝计数，数据源 P1 §C.5 的 `activity_log` 行——读作"护栏工作量"而非个人污点，持续增长才提示某 Agent/Skill 在漂移）。

**交付效能板块**（第七组，2026-07-29 增补，S3；不进总分、单独呈现）——治理板块回答"AI 干活守不守规矩"，本板块回答"交付系统有没有变好"。全部从既有表计算，零新增采集：

| 指标 | 公式 | 数据源 |
|---|---|---|
| CR Lead Time | `drafting` 首事件 → `archived` 的时长 P50/P90，可按 spec/项目下钻 | `cr_sync_event` 时间戳序列 |
| Review 负担 | reviewLoop 平均 attempt 数（越接近 1 越好）；与治理板块"审批时延"并排呈现 | `pipeline_node_run.attempt` |
| 变更失败率 | 归档后 14 天内出现 `cr.md#origin` 显式指向本 CR 的修复类 CR 的占比——`origin` 为 cr.md frontmatter 新增可选字段（登记时由 requirement-register 提示填写）；不用「同 spec_id」启发式：specs 基线是累积文档，同 spec 多 CR 演进是常态，启发式会系统性虚高 | `cr` + origin 归因 |

**AI 净价值叙事条**（看板顶部信息架构，不是新指标）：按 `净价值 = 时间收益 + 质量收益 + 知识收益 + 风险收益 − 成本` 组织既有指标——时间收益 ← Lead Time 趋势；质量收益 ← 门禁一次通过率 + 变更失败率趋势；知识收益 ← 资产复用率；风险收益 ← EVIDENCE_DRIFT / bypass-commit / 越权尝试下降趋势；成本 ← token × 价目表估算（沿用 §1.1 的"估算"标注）。这是管理口径框架而非财务核算，改的是呈现层不是数据管道。

### 1.3 数据管道与新增表（2 张 + 1 配置）

```sql
CREATE TABLE maturity_snapshot (
    bucket_date  DATE NOT NULL,
    scope        TEXT NOT NULL CHECK (scope IN ('org','user','project')),
    scope_id     TEXT NOT NULL,              -- org 固定 '·'；user/project 为其 id
    metrics      JSONB NOT NULL,             -- {aif:{token_intensity:…,…}, sii:{…}, …, governance:{…}}
    scores       JSONB NOT NULL,             -- 归一化后各维分 + total
    config_rev   TEXT NOT NULL,              -- maturity-config.yaml 的版本号（口径可追溯）
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (bucket_date, scope, scope_id)
```

计算任务挂 `sys_cron_executions`（Multica 现成的分布式 DB 调度器）：每日 00:30 本地时区跑前一天快照，模式照抄 `task_usage_rollup_state` 的**水位线增量**（该表就是现成范本）。历史快照不可变——口径变更只影响 `config_rev` 之后的新行，趋势图跨口径处标注断点。观察期内（§1.2）`scores` 不计算（无基线可依），`metrics` 照常落库。

### 1.4 「AI 原生组织建议」= Org Admin Workspace 项目的 Autopilot（吃自己的狗粮）

原产品把 LLM 建议做成独立 API（`/api/ai-maturity/llm-score`、`llm-suggestions` + history）。我们更进一步：**建议由平台自身的一个真实项目产出**——

- 内置项目 **Org Admin Workspace**（对应快照里的 org-admin-avatar 内置 Agent），其 Agent 挂一个每周 Autopilot：读取最近的 `maturity_snapshot` 序列 + 治理板块异常 → 生成诊断报告落盘 `docs/org-admin/maturity-review-{YYYY-Www}.md`（**落盘 = Org Admin Workspace 项目工作区内的普通目录，不经 git**——报告是易逝的运营叙事而非基线资产，避免与 §2.2 提交治理冲突；「历史」即目录内的历史文件序列）→ 经 inbox 通知 Owner。诊断模板按 **AI 净价值四收益一成本**框架组织（S3）：个人效率 / 团队交付 / 知识复利 / 风险收益四节 + 成本一节，每节引用对应板块指标——季度末的同模板扩写版即 §5 的价值复盘报告。
- 看板的「建议」区直接渲染该目录最新文件；历史 = 目录里的历史文件（免费获得原产品的 suggestions/history 能力）。
- 好处：建议的生成过程本身走 Team Agent 消息流，可追问、可继续对话（"为什么 EPC 掉了？"），而不是一个只读 API；同时这是对平台自身能力的持续验证。

### 1.5 隐私与反 Goodhart（内部工具必须先说清楚的两条）

- **个人排名默认关闭**。项目聚合默认开；个人榜需 Owner 显式开启（对应快照的"Owner mode"），且开启动作对全员可见（通知公告）。Token 消耗是行为数据，把它变成绩效排名会立刻诱发刷量。
- **数量指标必须与质量护栏成对呈现**：Token 强度旁边永远并排门禁一次通过率——"用得多"不等于"用得好"，看板布局上强制这对指标同屏。指标定义页明写每个指标的已知可刷性（如 Token 强度可用无意义长对话刷高），管理层按趋势与横向对比读数，不做个人考核依据。此立场写进看板页脚。

## 2. 跨 CR 追溯查询与漂移检测

### 2.1 追溯查询：spec_trace 投影

P0 定了 baseline 级 `specs/{spec_id}/traceability.yml` 由 `writeback-traceability` 生成（git 权威）。P3 把它投影进 PG 以支撑查询：

```sql
CREATE TABLE spec_trace (
    spec_id      TEXT NOT NULL,
    version      TEXT NOT NULL,
    cr_id        TEXT NOT NULL,               -- 每次回写一行（同 spec 多版本多行）
    owners       JSONB NOT NULL,
    tasks        JSONB NOT NULL,              -- [{id,file,status}]
    code_repos   JSONB NOT NULL,              -- [{repo,trunk,merge_commit,source_sha,merged_at}]
    tests        JSONB NOT NULL,              -- {status,commands,uncovered_risks}
    reviews      JSONB NOT NULL,
    projected_commit TEXT NOT NULL,
    projected_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (spec_id, version, cr_id)
);
```

同步方式复用 P1 §A 通道：`writeback-traceability` 完成时 crctl outbox 发一个 `trace` 事件（event_kind 枚举加一项），payload 即 traceability.yml 内容。**回答的问题**（spec 详情页 + 全局搜索接入）：这个功能（FR）由哪些 CR 演进而来 → 时间线；这次上线的 merge commit / 测试证据 / 评审记录在哪 → 一跳直达；某个人经手过哪些 spec → 按 owners 反查。

### 2.2 漂移检测：把 tools 的两个 review Skill 变成定时巡检

tools 已备好两把刀，但原设计只在 pipeline 内手动触发。P3 把它们接上 Autopilot：

| 巡检 | 执行 Skill | 触发 | 产出与路由 |
|---|---|---|---|
| 基线对齐扫描 | `review-alignment`（检测 PRD↔SDD↔TASK↔代码 drift） | 每周日夜间，每个活跃 spec 一个任务（服务端 `sys_cron_executions` 枚举活跃 spec 派发 → 共享队列 → daemon 侧 quality-reviewer-agent 认领执行，只读；某周期无 daemon 在线则顺延到下一周期，不补跑不积压） | drift 写 `traceability.yml#drift`（git，经 crctl）→ outbox → `drift_finding` 投影 → 严重项进 Owner inbox |
| 变更影响扫描 | `change-impact-analysis` | trunk 有非 CR 流程的直接提交时（服务端 sys_cron 按 `dir-graph.yaml#repositories` 声明的全部仓扫描 trunk 提交：前缀不在白名单 `wip:`/`[cr] `/`merge(` 且不属于该仓特许格式（如 tools 仓 conventional commits）即计为 bypass，severity `warn`） | 下游 `reviews.*.result` 置 stale + change-log；同时这是「绕过流程写代码」的检测器，计入治理板块 |

```sql
CREATE TABLE drift_finding (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    spec_id TEXT NOT NULL, cr_id TEXT,
    kind TEXT NOT NULL CHECK (kind IN ('alignment-drift','impact-stale','bypass-commit','wip-on-trunk')),
    severity TEXT NOT NULL CHECK (severity IN ('info','warn','block')),
    summary TEXT NOT NULL, evidence JSONB NOT NULL DEFAULT '{}',
    status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open','acknowledged','resolved','wontfix')),
    found_at TIMESTAMPTZ NOT NULL DEFAULT now(), resolved_at TIMESTAMPTZ
);
```

drift 数量与解决时延进看板治理板块；`bypass-commit` 是本平台特有的"影子工程"探测——本地执行模式下没人能从平台侧强制所有代码经 CR，但可以让绕过变得**可见**。trunk 上出现 `wip:` 前缀单独记 `wip-on-trunk`（severity `info`，不计入 bypass 计数但进治理板块可见）。**前缀合规 ≠ 通路合规**（前缀可手写伪造）；通路层对账（controlled-shell 审计行 ↔ trunk 提交）需把本地审计投影到服务端，属新采集，明确延后 P3+（见 §6）。

### 2.3 知识晋升巡检（2026-07-29 增补，S1；2026-07-30 扩为双信号源）

"当一个问题被反复问到，就应该推动它回到事实源，而不是永远停留在问答记录里。"P2.5 轻量档的 spec-query / LLM Wiki 问答产生日志（**只记问题文本与命中文件路径，不记答案正文**——答案是衍生物，问题才是信号），P3 加第三个巡检，晋升信号来自**两路**：

| 信号源 | 抓什么 | 来源 |
|---|---|---|
| 信号一：问答日志聚类 | **被反复问的**——近 30 天同类问题 ≥3 次且命中文件分散（说明事实源没有一处权威回答；「同类」由周巡检时 knowledge-agent 对 30 天问题列表做语义分组现场判定，零新基建） | `wiki_query_log` |
| 信号二：open-questions 条目 | **生成时就答不上的**——`wiki-maintain` Skill 维护 Wiki 时发现的缺口记入 `wiki/open-questions.md` 的 Active 节（缺口在生产侧被记录，不用等有人来问） | Wiki 维护运行产物（《Wiki子系统设计》§5） |

| 巡检 | 执行 | 触发 | 产出与路由 |
|---|---|---|---|
| 知识晋升扫描 | knowledge-agent（只读；执行模型同 §2.2：服务端 sys_cron 派发 → 共享队列 → daemon 侧执行，周期内无 daemon 在线则顺延不补跑） | 每周，与 review-alignment 同批 | 两路信号汇总去重 → 自动开普通 Issue：「建议将〈主题〉回写事实源」，附问题样本 / open-question 条目与建议落点（specs/ 或 docs/）——**只开 Issue 不动文件**，回写仍走人审的正常 CR/文档流程；被回写解决的 open-question 移入 Answered 节并链接落点。幂等：同一主题 30 天内已开且未关闭的 Issue 不重复开（幂等键 = 主题归一化文本，Issue 内记录样本问题 id） |

这补全了知识层的回路：事实源（git）→ 消费（Wiki 问答）→ 晋升（高频问答与生产缺口回写事实源）。问答日志表复用 `skill_usage_event` 的形制（`wiki_query_log`：question_text、hit_paths JSONB、asked_by、asked_at），随 P2.5 落库，P3 只读。

## 3. 内部 Skill Market

### 3.1 复用与增量

Multica 已有 `skill` + `skill_file` 表且兼容 Anthropic Agent Skills 标准；tools 有 59 个 Skill + 唯一 owner 矩阵。Market 的增量只有三块：

```sql
ALTER TABLE skill
  ADD COLUMN visibility TEXT NOT NULL DEFAULT 'private'
      CHECK (visibility IN ('private','org','builtin')),   -- 对齐 CodeBanana 的 私有/组织可见；builtin=tools 包内置
  ADD COLUMN version TEXT NOT NULL DEFAULT '0.1.0',
  ADD COLUMN owner_actor TEXT;                              -- 对齐 agent-skill-matrix 的唯一 owns

CREATE TABLE skill_usage_event (                             -- 排行与"哪些技能真的被用"
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    skill_id UUID NOT NULL REFERENCES skill(id) ON DELETE CASCADE,
    task_id UUID REFERENCES agent_task_queue(id) ON DELETE SET NULL,
    project_id UUID, used_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 3.2 生命周期（对齐 CodeBanana 的市场交互，去掉"公开发布"）

`创建（与 Agent 对话打包 / 上传 / P2 §7 会话导出草稿）→ 私有库 → Add to Project → 发布到组织（选可见范围，内部版只有 org 一档）→ 版本更新（新版本号）`。列表带作者、版本、使用量排行（`skill_usage_event` 聚合）、`Bot` 类标签的等价物 = **运行时要求标签**（该 Skill 需要哪些本机 CLI/网络/TTY——从 SKILL.md 的前置要求半自动提取）。

**发布 = 授权**（2026-07-29 增补，S2）：Skill 从 private 升 org 的发布动作，即视为作者对"团队复用该工作方法"的显式授权，发布确认框明示此含义。个人隐私边界：发布校验含**敏感信息扫描**（API Key / 内网凭据 / 个人路径等模式匹配，复用平台内部敏感判定能力）——命中即拦截；作者可对命中项提交误报申诉，由 Owner 逐条确认后放行，放行记录落 `activity_log`（谁、何时、对哪个命中项）——拦截是默认，放行是留痕的例外。团队沉淀的是工作方法与判断框架，不是把个人日志与隐私直接抽走。

### 3.3 治理钩子（tools 不变式落地为发布门禁）

发布/更新时服务端校验（把 `dir-graph.yaml#agents.contract` 的 4 条不变式变成代码）：`name`+`description` frontmatter 必填；org 可见的 Skill 必须指定唯一 `owner_actor`；SKILL.md 需通过 `validate-doc` 结构校验（daemon 侧跑）；内置 59 个 `builtin` Skill 只随 tools 包版本更新，Market 内不可编辑（防止方法论被局部魔改后漂移）。

**资产元数据卡**（2026-07-29 增补，S2）：org 可见的 Skill 在上述校验外增加 4 个必填 frontmatter 字段——复用者不该靠口口相传弄清一个资产怎么用：

| 字段 | 回答的问题 | 示例 |
|---|---|---|
| `applicable-scenarios` | 适用什么场景 | "Node 服务的 API 契约评审；不适用于前端组件" |
| `context-dependencies` | 依赖什么上下文 | "需要 specs/{id}/sdd.md 已存在；需要本机 pnpm" |
| `permission-declaration` | 能读写哪些目录 | "读 specs/**；写 change-requests/{CR}/review-annotations/" |
| `failure-handling` | 失败后怎么办 | "校验失败输出 blockers[]，回 reviewLoop；连续 3 次失败找 owner_actor" |

四字段渲染为 Market 详情页的"使用说明卡"；`permission-declaration` 与 P1 `rules.json#protectedPaths` 做一致性提示（声明写 protected 路径的 Skill 发布时警告）。builtin Skill 的四字段由 tools 包一次性补齐（其内容本就散落在各 SKILL.md 正文，此处是结构化提升）。

### 3.4 使用量遥测的采集点

daemon execenv 物化 Skill 时已知道任务用了哪些 Skill（`skill_frontmatter`/`sidecar_manifest` 机制现成）——任务完成回调里附带 `skills_used[]`，服务端落 `skill_usage_event`。零额外探针。

### 3.5 过程记录资产化（可选，P3+）

对接 P2 §7 的「导出为 Skill 草稿」：Team Agent 会话多选 → SKILL.md 草稿 → 私有库 → 人工修订 → 经 §3.3 门禁发布。P3 侧只需保证导出的草稿带 `source: session-export` 标记（Market 列表可筛），供后续评估"会话导出"这条沉淀路径的实际转化率。不单独排期，随 Market 前端顺带。

## 4. 场景工坊：角色化视图（2026-07-29 增补，S4）

不同角色关注的不是同一组信息——产品关心 CR 与审批，QA 关心质量门与漂移，管理者关心效能与成本。平台要有统一底座，也要有按角色组织的视图；**同一份数据，不同投影**。本节做三个 route 级视图（复用 `packages/views` 体系与既有 API，与 §1.1 看板同一实现模式，零新增数据源）：

| 工坊 | 面向 | 内容组装（全部为既有端点的重组） |
|---|---|---|
| **需求工坊** `/workshop/requirement` | PM / 需求方 | 我相关的 CR 按 16 态分组（`cr` 投影）· 待我审批卡片（`approval_record` pending）· PRD 快捷入口 · `/需求` 斜杠命令入口（P2 §6.1） |
| **质量中心** `/workshop/quality` | QA / Tech Lead | 治理板块四+一指标（§1.2）· 当前 blocker 列表（`pipeline_node_run` blocked）· `drift_finding` 流（open 优先）· 越权尝试趋势 |
| **效能驾驶舱** `/workshop/dashboard` | 管理者 | 即 §1 成熟度看板 + 交付效能板块 + AI 净价值叙事条（归入工坊概念，不重复开发） |

**开发工坊 = 三模式聊天本身**（P2 已交付，开发者的工作现场就在那里，不重做）。设计约束：工坊是**读侧 + 入口**，一切写操作（审批、触发 pipeline）跳转到既有交互（审批卡、聊天窗），不开新的写通路——保证权限与审计路径唯一。排期：与 E2 看板前端同一技术栈，作为 P3 并行前端轨道，约 +2–3 周。

## 5. 交付切分与验收

| 序 | 交付物 | 验收 |
|---|---|---|
| E1 | maturity-config.yaml + 快照 rollup 任务（scope 仅 org/user/project） | 连续 3 天快照生成；改 config 权重后新快照 config_rev 变化、旧快照不变；观察期语义生效（§1.2/§1.3：scores 不计算、metrics 照常落库） |
| E2 | 看板前端（趋势/雷达/排名/治理板块） | 项目聚合默认可见；个人榜开关行为符合 §1.5；数量指标与质量护栏同屏；观察期内雷达图总分显示「基线校准中」 |
| E3 | Org Admin Workspace 内置项目 + 周报 Autopilot | 周报落盘 docs/org-admin/ 并在看板渲染；对报告内容可在 Team Agent 里追问 |

| E6 | Skill Market（可见性/版本/排行/发布门禁/遥测/元数据卡/发布=授权+敏感扫描） | 无 owner 的 Skill 发布被拒；builtin 不可编辑；排行随使用量变化；缺任一元数据卡字段的 org 发布被拒；含模式匹配敏感串的发布被拦截；被拦截的发布可经误报申诉由 Owner 逐条确认放行，放行留 activity_log 审计 |

| E8 | 场景工坊三视图 + 斜杠命令（§4，S4；斜杠命令实现在 P2，此处验收入口整合） | PM 在需求工坊看到自己的待审批并一键进审批卡；QA 在质量中心看到 open 的 drift_finding；工坊内无独立写通路 |

依赖：E1→E2→E3 一条线；E4→E5 一条线（都走 P1 outbox 通道，E4 只需加一个 event_kind）；E6 独立；E7 依赖 E1（快照管道）与 E6（usage_event）；E8 依赖 E2（同前端体系）；E9 依赖 P2.5 的 `wiki_query_log` 落库。增补项（E7–E9 + E6 扩展）合计约 +3–4 周，其中 E8 可与 E2 并行——原 4–6 周路线图相应放宽为 5–7 周，或将 E8/E9 列为 P3.5 尾批。E7 的变更失败率另依赖 `cr.md#origin` 新字段——实施前需先在 tools 仓完成 cr.md 模板 + requirement-register 提示词变更（纯 prompt/模板变更，免 CR 流程）。本节的 5–7 周为早期估算，以已注册的 CR-2026-013~017 拆分台账（目标版本 0.20→0.24 顺序递延）为准。

**价值复盘（S3，验收之后的验收）**：M3 上线满 3 个月，用 §1.4 的周报模板扩写为季度价值复盘——按个人效率 / 团队交付 / 知识复利 / 风险收益四类回答"平台值不值"：PRD 起草与方案起草时长有没有降、Lead Time 与 Review 负担有没有降、资产有没有被复用而非停在作者手里、越权与返工有没有减少。这些问题没有改善，说明只是买了工具；持续改善，平台才算真正落地。

## 6. 明确不做（防蔓延）

- 不做跨组织对标（单组织内部平台，没有可比对象）；
- 不做个人绩效导出/API（见 §1.5 立场）；
- 不做指标实时化（日粒度足够，实时化会把 rollup 复杂度翻倍而决策价值为零）；
- 不做 Skill 的付费/积分机制（内部资产，流通靠可见性与排行即可）；
- 不做 bypass 通路层对账（controlled-shell 审计行 ↔ trunk 提交交叉核对）：需把本地审计投影到服务端，属新采集，延后 P3+；P3 只做前缀层探测（§2.2）。
