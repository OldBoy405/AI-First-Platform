## 0. P3 的四个交付物与一条设计主线

1. **AI 成熟度看板**——回答管理层「AI 原生转型进行到哪了」+「交付系统有没有变好」（转型仪表盘与价值仪表盘互补，见 §1.2）。
2. **跨 CR 追溯查询 + 漂移检测**——回答工程侧「这个功能是谁、经哪个 CR、什么证据落地的；基线和现实漂了没有」。
3. **内部 Skill Market**——把个人工作流沉淀为组织资产的流通面（含复用授权元数据，防止复用变成新一轮口口相传）。
4. **场景工坊（角色化视图）**——同一份数据按角色投影（§4），AI 内嵌在工作场景里而非旁挂聊天入口。

设计主线：**P3 不新增采集管道，只做已有事件的聚合与呈现**。P0–P2 落地后，每一次任务执行（task_usage）、每一次状态推进（cr_sync_event）、每一次审批（approval_record）、每一轮 reviewLoop（pipeline_node_run.attempt）、每一次点踩（P2 反馈）、每一次越权拦截（P1 §C.5 行为审计）都已经是结构化行——P3 是这些行的读侧。

**仅有的一条新数据流**：Skill 使用遥测（§3.4）——且它落在**服务端任务认领路径**上，零跨进程字段、零 daemon 改动、零额外探针。`wiki_query_log` 与知识晋升巡检（原 §2.3）**整节移出本文**，归《 Wiki 子系统设计》——它们的生产者与消费者都在 Wiki 子系统内，拆在两份文档里只会产生一个跨文档循环依赖（§7 R-12）。

读侧也有边界：场景工坊（§4）从三个新 route 砍到一个，另两个降级为既有视图的筛选器；唯一真存在的缺口是缺一个用户侧「待我审批」端点（§4）。

## 1. AI 成熟度看板

### 1.1 呈现结构（对齐快照还原的原产品布局）

```
┌ 顶部：日期区间选择 · Owner mode 标记 · 「每日 00:30 更新前一天数据」──┐
│ 统计条：活跃成员 | Token 总消耗 | (可选)估算成本                        │
│ Token 趋势图（按日，可下钻 项目/个人/模型）                           │
│ 排名区：[项目排名 | 个人排名] 切换 Tab（个人榜默认关闭，见 §1.5）       │
│ 五维雷达图：总分 + AIF/SII/OFI/EPC/ACM                                  │
│   └ 每维展开：子指标卡片 + 环比箭头                                     │
│   └ 观察期内本区域不出雷达图，改为指标切换 + 趋势 + 项目横向排序（§1.2）│
│ AI 净价值叙事条（S3）：时间/质量/知识/风险四收益 − 成本，各挂真实指标   │
│ 「AI 原生组织建议」：LLM 生成的诊断与建议（含历史版本）                 │
├─ 治理板块（不进总分）：门禁一次通过率 · 证据漂移 · 追溯完整率 · 越权尝试 ┤
└─ 交付效能板块（S3 增补，不进总分）：Lead Time · Review 负担 · 变更失败率 ┘
```

与原产品的两处架构差异：**不做独立子域名 iframe**（内部平台没有隔离发布的需要，做成主应用的一个 route，复用 `packages/views` 体系）；**成本列可选**（本地执行模式下平台不代付 Token，成本 = token × 价目表估算，价目表是一个可编辑的 `model-prices.yaml`，不精确、仅供量级参考，UI 上明确标注"估算"）。

### 1.2 五维指标定义（本平台公式，全部可从既有表算出）

总分 = Σ(维度分 × 权重)，权重与阈值集中在一个版本化配置 `maturity-config.yaml`（不硬编码，改配置即改口径——沿用 crctl 的"改声明不改代码"哲学；落点与生成器见 §1.4）。每个子指标归一化到 0–100：`score = clamp(100 × (x - floor) / (target - floor))`，`floor/target` 在配置中按组织基线设定并随季度调整。

**观察期（4 周）**：看板上线后前 4 周为基线校准窗口——快照照常生成（`metrics` 落库，`scores` 不计算），看板只呈现原始值与趋势。**观察期不出雷达图**：无基线时雷达图的形状没有意义，一个画着「基线校准中」的空雷达只会诱导读者去比绝对值大小。改用三件既有组件拼成的布局：`dim-segmented` 切换指标 + `usage-trend-card` 看时间趋势 + `leaderboard` 看项目横向排序（均在 `packages/views/dashboard/components/` 下现成）——观察期能回答的只有「在消长吗」与「谁高谁低」两个问题，布局就只回答这两个。观察期结束后用实测分布的分位数规则（floor ≈ P10、target ≈ P75）生成第一版基线建议，由 §1.4 周报在第 4 周自算并提请人审（**不自动写入配置**）；雷达图在基线入库后才作为 `dim-segmented` 的「总览」档出现。

子指标共 **9** 项（原 13 项砍 4，理由逐条见 §7 R-2～R-5）；其中资产复用率依赖 Skill Market 遥测，**CR-A 首版上线 8 项，第 9 项随 CR-D 补入**（§5）。

| 维度 | 子指标 | 公式（分子/分母均为真实列） | 数据源 |
|---|---|---|---|
| **AIF**·AI First | Token 强度 | Σtokens / 活跃成员数 / 天 | `task_usage` join `agent_task_queue.initiator_user_id` ÷ `member` 活跃数（**不走 `task_usage_hourly`——该表无 user 维，见文头与 §7 R-1**） |
| | AI 渗透率 | 当期发起过 ≥1 个 Agent 任务的成员 / 全体成员 | `agent_task_queue.initiator_user_id` distinct |
| **SII**·超级个体 | 人均 CR 吞吐 | 归档 CR 数 / 活跃成员数 | `cr` |

**砍掉的四项**（不是延后，是取消；唯一例外是超级个体占比）：**AI 效率系数**（Σtokens/归档 CR 数反向计分——与 Token 强度方向相反，同一行为在同一维度内既加分又减分，合并后接近噪声）、**规划转化率**（两个数据源 `cr.source_path` 与 `issue.cr_id` 都不存在——后者已随 ADR-0001 废止且从未实施）、**Cron/A2A 采用**（测的是平台功能开通率而非组织成熟度，管理员看完不会产生任何动作）、**超级个体占比**（公式需从 `cr_sync_event.trigger` 序列反推「独立驱动跨 ≥3 阶段」，是全文最重的一个查询，**推迟到 CR-D** ——它也是最该在有真实数据后再定义的一项）。

**治理板块**（第六组，本平台独有，不进总分、单独呈现——它们是质量护栏，不是竞赛项）：门禁一次通过率（gate 首次即过 / gate 总次数）、`EVIDENCE_DRIFT` 发生次数（证据摘要漂移，TTY 与 grant 两条审批路径均计入，非仅签名失败；数据源 P1 §B.4 的 `activity_log` 行，上线前置依赖 P1 D7）、追溯完整率（`traceability.yml` 五段齐全的归档 CR 占比）、审批时延 P50/P90（review 通过 → approval_record 的间隔，暴露人工瓶颈）、**越权尝试次数**（S5 增补：gitguard FORBIDDEN 拒绝计数，数据源 P1 §C.5 的 `activity_log` 行——读作"护栏工作量"而非个人污点，持续增长才提示某 Agent/Skill 在漂移）。

**交付效能板块**（第七组，2026-07-29 增补，S3；不进总分、单独呈现）——治理板块回答"AI 干活守不守规矩"，本板块回答"交付系统有没有变好"。全部从既有表计算，零新增采集：

| 指标 | 公式 | 数据源 |
|---|---|---|
| CR Lead Time | `drafting` 首事件 → `archived` 的时长 P50/P90，可按 spec/项目下钻 | `cr_sync_event` 时间戳序列 |
| Review 负担 | reviewLoop 平均 attempt 数（越接近 1 越好）；与治理板块"审批时延"并排呈现 | `pipeline_node_run.attempt` |
| 变更失败率 | 归档后 14 天内出现 `cr.md#origin` 显式指向本 CR 的修复类 CR 的占比——`origin` 为 cr.md frontmatter 新增可选字段（登记时由 requirement-register 提示填写）；不用「同 spec_id」启发式：specs 基线是累积文档，同 spec 多 CR 演进是常态，启发式会系统性虚高 | `cr` + origin 归因 |

**AI 净价值叙事条**（看板顶部信息架构，不是新指标）：按 `净价值 = 时间收益 + 质量收益 + 知识收益 + 风险收益 − 成本` 组织既有指标——时间收益 ← Lead Time 趋势；质量收益 ← 门禁一次通过率 + 变更失败率趋势；知识收益 ← 资产复用率；风险收益 ← EVIDENCE_DRIFT / bypass-commit / 越权尝试下降趋势；成本 ← token × 价目表估算（沿用 §1.1 的"估算"标注）。这是管理口径框架而非财务核算，改的是呈现层不是数据管道。

### 1.3 数据管道与新增表（**1 张表** + 1 配置）

**只有一张表落库，其余全部读时聚合**。快照表存在的唯一理由是**历史不可变**：口径（权重/阈值）会随季度改，而“当时那套口径下的分数”必须能重现——这是读时聚合做不到的唯一事情。不是为了查询性能（不需要）也不是为了避免重算（日粒度的量级下无意义）。

```sql
-- 迁移编号从 375 起（fork 自有迁移已占至 374）；禁新增 FOREIGN KEY（multica CLAUDE.md 硬规则）
CREATE TABLE maturity_snapshot (
    bucket_date  DATE NOT NULL,
    scope        TEXT NOT NULL CHECK (scope IN ('org','user','project')),
    scope_id     TEXT NOT NULL,              -- org 固定 '·'；user/project 为其 id
    metrics      JSONB NOT NULL,             -- {aif:{token_intensity:…,…}, sii:{…}, …, governance:{…}}
    scores       JSONB NOT NULL,             -- 归一化后各维分 + total；观察期内 '{}'
    config_rev   TEXT NOT NULL,              -- 本仓 maturity-config.yaml 所在 commit 的 SHA（见 §1.4）
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (bucket_date, scope, scope_id)
);
-- 迁移中每个索引必须 CONCURRENTLY 且单独一个迁移文件（同上硬规则，包括全新表）
```

计算任务挂 `sys_cron_executions`（Multica 现成的分布式 DB 调度器，唯一键 insert + `lease_token` 轮换 + 重试 + 心跳全备）：每日 00:30 本地时区跑前一天快照。**JobSpec 参数（照抄 `jobs_autopilot.go` 而非 `jobs_task_usage.go`）**：`Cadence: 0` + `PlansForScope` hook（固定 cron 表达式 `30 0 * * *`，经现成的 `service.NextOccurrencesUTC(expr, "Asia/Shanghai", after, now)` 求解——时区转换与夏令时已被封装，不自己算）、`CatchUpMode: CatchUpEveryPlan`（**不用 `CatchUpLatestOnly`**：快照是按天分桶的，服务器停 3 天后只补最后一天会永久缺 2 行）、`MaxPlansPerTick: 7`、`CatchUpWindow: 7×24h`、`Scopes: StaticScopes(global)`（一个任务内部遍历三个 scope 写多行，**不把 scope 展开成调度器级的 Scope**——否则每新增一个用户就多一行 cron 执行记录）。

水位线口径照抄现成范本 `rollup_task_usage_hourly()`（`pg_try_advisory_xact_lock` + 有界窗口 + 单事务内 upsert 与水位推进同时提交），**但不复用其状态表**（真名 `task_usage_hourly_rollup_state`，属上游 hourly 管道）——快照任务的水位就是 `MAX(bucket_date)`，自带在表里，不需第二个状态表。历史快照不可变——口径变更只影响 `config_rev` 之后的新行，趋势图跨口径处标注断点。观察期内（§1.2）`scores` 不计算，`metrics` 照常落库。

### 1.4 「AI 原生组织建议」= Org Admin Workspace 项目的 Autopilot（吃自己的狗粮）

原产品把 LLM 建议做成独立 API（`/api/ai-maturity/llm-score`、`llm-suggestions` + history）。我们更进一步：**建议由平台自身的一个真实项目产出**——

**口径配置的落点与消费方式**（新增决议，§7 R-8）：`maturity-config.yaml` 放**本仓**（knowledge-base）而非 multica 仓，因为改口径是治理动作而非发版动作，它属于声明所在的仓。消费方式照抄 multica 已有的唯一先例 `governance/gen/generate-transitions.mjs`：生成器读声明 → 吐只读 Go 副本（文件头记源 commit SHA）→ 副本提交入库 → `--check` 模式在 CI/pre-commit 重生成并 diff，漂移则非零退出。**关键收益与该先例一致：构建 multica 永远不需要 checkout 本仓**（否则服务器就多了一个运行时跨仓文件依赖）。`config_rev` = 该 yaml 所在 commit 的 SHA（**不手维版本号**——手维的版本号一定会忘记改，而 SHA 改不了也忘不了）。因此改口径的完整路径是：本仓改 yaml 走 CR → multica 重跑生成器提交 → 部署。比“改个配置就生效”重，但口径变更本就应该重——它会重算所有人的分数。

- 内置项目 **Org Admin Workspace**（对应快照里的 org-admin-avatar 内置 Agent），其 Agent 挂一个每周 Autopilot：读取最近的 `maturity_snapshot` 序列 + 治理板块异常 → 生成诊断报告落盘 `docs/org-admin/maturity-review-{YYYY-Www}.md`（**落盘 = Org Admin Workspace 项目工作区内的普通目录，不经 git**——报告是易逝的运营叙事而非基线资产，避免与 §2.2 提交治理冲突；「历史」即目录内的历史文件序列）→ 经 inbox 通知 Owner。诊断模板按 **AI 净价值四收益一成本**框架组织（S3）：个人效率 / 团队交付 / 知识复利 / 风险收益四节 + 成本一节，每节引用对应板块指标——季度末的同模板扩写版即 §5 的价值复盘报告。
- 看板的「建议」区直接渲染该目录最新文件；历史 = 目录里的历史文件（免费获得原产品的 suggestions/history 能力）。
- 好处：建议的生成过程本身走 Team Agent 消息流，可追问、可继续对话（"为什么 EPC 掉了？"），而不是一个只读 API；同时这是对平台自身能力的持续验证。

### 1.5 隐私与反 Goodhart（内部工具必须先说清楚的两条）

- **个人排名默认关闭**。项目聚合默认开；个人榜需 Owner 显式开启（对应快照的"Owner mode"），且开启动作对全员可见（通知公告）。Token 消耗是行为数据，把它变成绩效排名会立刻诱发刷量。
- **数量指标必须与质量护栏成对呈现**：Token 强度旁边永远并排门禁一次通过率——"用得多"不等于"用得好"，看板布局上强制这对指标同屏。指标定义页明写每个指标的已知可刷性（如 Token 强度可用无意义长对话刷高），管理层按趋势与横向对比读数，不做个人考核依据。此立场写进看板页脚。

## 2. 跨 CR 追溯查询与漂移检测

### 2.1 追溯查询：不建投影表，只加一个 event_kind

P0 定了 baseline 级 `specs/{spec_id}/traceability.yml` 由 `writeback-traceability` 生成（git 权威）。P3 需要的是查询能力。

**原设计的 `spec_trace` 表已砍**（§7 R-10）。只保留同步通道：`writeback-traceability` 完成时 crctl outbox 发一个 `trace` 事件，payload 即 traceability.yml 内容，落进现成的 `cr_sync_event.payload`（JSONB）——**`event_kind` 列无 CHECK 约束，加第 7 个值零迁移**，`UNIQUE (cr_id, commit_sha, event_kind)` 自动提供幂等。查询直接打该表，必要时加一个表达式索引（`(payload->>'spec_id') WHERE event_kind='trace'`）。

理由与 P0 §3.1.1 砍 `cr.checkpoints[]`/`merge_commits[]` 是同一条推理：事件行自带时间戳与完整 payload，二次拆列的快照表既不多提供一个事实，又多一个会漂的副本。上限量级也不支持建表：一个 spec 一年几十行 trace 事件。

**回答的问题不变**（spec 详情页 + 全局搜索接入）：这个功能（FR）由哪些 CR 演进而来 → 时间线；这次上线的 merge commit / 测试证据 / 评审记录在哪 → 一跳直达；某个人经手过哪些 spec → 按 owners 反查。

### 2.2 漂移检测：只做服务端确定性扫描，LLM 巡检推迟

原设计把 tools 的两个 review Skill（`review-alignment` / `change-impact-analysis`）接上定时 Autopilot。**该方案已推迟**（§7 R-11），P3 只交付一个服务端确定性扫描：

| 巡检 | 执行 Skill | 触发 | 产出与路由 |
|---|---|---|---|
| **提交前缀扫描**（入 CR-C） | 无（**服务端纯 Go，不走 Agent**） | 每小时，`sys_cron` 按 `dir-graph.yaml#repositories` 声明的全部仓扫 trunk 新提交：前缀不在白名单且不属该仓特许格式即计 bypass（severity `warn`）；`wip:` 单独记 `wip-on-trunk`（`info`） | 直写 `drift_finding` → 治理板块 |
| 基线对齐扫描（`review-alignment`） | quality-reviewer-agent | **推迟（§7 R-11）** | — |
| 变更影响扫描（`change-impact-analysis`） | — | **推迟（同上）** | — |

**为何只留前缀扫描**：后两个巡检需要“服务端 sys_cron 派发 → 共享队列 → daemon 认领 → LLM 跑 Skill → 写 git → 经 crctl outbox 回流 → 投影”七跳，且依赖“某台 daemon 恰好在线且恰好持有那个 spec 的 worktree”——七跳里任何一跳断了都是静默无结果，而“无结果”与“无漂移”在看板上长得一模一样（同 P1 §B.4 对 EVIDENCE_DRIFT 的警告：必须能区分“从未漂移过”与“从未测过”）。前缀扫描是服务端一次 `git log`，无 daemon 依赖、无 LLM 不确定性、结果确定，而它提供了 `bypass-commit` 这个真正无可替代的信号（影子工程探测）。对齐巡检的价值不否，但它应当在有 daemon 在线率的真实数据后再立项。

**白名单的单一事实源**：各仓允许的提交前缀写进本仓 `dir-graph.yaml#repositories[].commit_prefixes`，经同一套生成器（§1.4）吐 Go 副本——不把 `wip:`/`[cr] `/`merge(`/conventional commits 硬编码在 Go 里，否则新增一个仓或改一条约定就要发一次服务端。

```sql
CREATE TABLE drift_finding (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    spec_id TEXT NOT NULL, cr_id TEXT,
    kind TEXT NOT NULL CHECK (kind IN ('alignment-drift','impact-stale','bypass-commit','wip-on-trunk')),
    severity TEXT NOT NULL CHECK (severity IN ('info','warn','block')),
    summary TEXT NOT NULL, evidence JSONB NOT NULL DEFAULT '{}',
    status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open','acknowledged','resolved','wontfix')),
    found_at TIMESTAMPTZ NOT NULL DEFAULT now(), resolved_at TIMESTAMPTZ
);
-- 幂等键（新增，§7 R-13）：巡检是定时重复扫描，同一提交不得每小时新开一行
CREATE UNIQUE INDEX CONCURRENTLY drift_finding_dedup_idx
    ON drift_finding (kind, spec_id, (evidence->>'commit_sha'));
```

没有这个唯一索引，任何一个长期存在的 bypass 提交会每小时刷一条 finding，一周后治理板块就只剩它。P1 §A.1 的口径在此照旧适用：**at-least-once 交付 + 唯一索引去重**，不在应用层做“先查再插”（`webhook_delivery` 的注释已把这个道理写成了仓内共识：租约是调度优化，唯一索引才是最终保护）。

drift 数量与解决时延进看板治理板块；`bypass-commit` 是本平台特有的"影子工程"探测——本地执行模式下没人能从平台侧强制所有代码经 CR，但可以让绕过变得**可见**。trunk 上出现 `wip:` 前缀单独记 `wip-on-trunk`（severity `info`，不计入 bypass 计数但进治理板块可见）。**前缀合规 ≠ 通路合规**（前缀可手写伪造）；通路层对账（controlled-shell 审计行 ↔ trunk 提交）需把本地审计投影到服务端，属新采集，明确延后 P3+（见 §6）。

### 2.3 知识晋升巡检——**已整节移出本文**

> 原 §2.3（2026-07-29 增补 S1，2026-07-30 扩为双信号源）已于 2026-08-19 整节迁至 **《Wiki 子系统设计》**，原交付项 E9 从 P3 删除。

理由（§7 R-12）：该巡检的两个信号源都在 Wiki 子系统内（`wiki_query_log` 表与 `wiki/open-questions.md`），执行体是 Wiki 的 knowledge-agent，产出是回写事实源的 Issue——生产者、消费者、执行体全在 Wiki 侧，P3 对它的唯一贡献只是“挂在定时巡检上”。拆在两份文档里产生的是一个跨文档循环依赖（P3 E9 依赖 Wiki W2，Wiki 又靠 P3 提供巡检基建），而 Wiki 子系统自身尚未立项——把未立项系统的一个特性挂在已立项系统的交付列表里，只会让 P3 的验收永远差一项。

本文仍保留的关联：知识晋升产生的 Issue 与回写 CR 会照常进入 §1.2 的各项指标（作为普通 CR），不需特殊处理。

## 3. 内部 Skill Market

### 3.1 复用与增量

Multica 已有 `skill` + `skill_file` 表且兼容 Anthropic Agent Skills 标准；tools 有 56 个 Skill + 唯一 owner 矩阵。Market 的增量只有三块：

```sql
ALTER TABLE skill
  ADD COLUMN visibility TEXT NOT NULL DEFAULT 'private'
      CHECK (visibility IN ('private','org')),              -- 对齐 CodeBanana 的 私有/组织可见
  ADD COLUMN version TEXT NOT NULL DEFAULT '0.1.0',         -- 纯展示用（见下）
  ADD COLUMN owner_actor TEXT;                              -- 对齐 agent-skill-matrix 的唯一 owns

CREATE TABLE skill_usage_event (                             -- 排行与"哪些技能真的被用"
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    skill_ref TEXT NOT NULL,                                 -- workspace skill 的 uuid 文本，或 'builtin:<name>'
    task_id UUID,                                            -- 无 FK（仓硬规则）
    project_id UUID,
    used_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

三处偏离原设计，都是被仓内事实逼出来的：

1. **`visibility` 删 `builtin` 档**（§7 R-14）——builtin Skill 在 `skill` 表里**根本没有行**（`service/task.go:5851` 对 `id == ""` 的内置 Skill 现场合成 `"builtin:" + Name`），给一个不存在的行加枚举值是纯粹的死代码。"builtin 不可编辑"（§3.3）自动成立：没有行可改。
2. **两个 `REFERENCES` 删光**——multica `CLAUDE.md` 硬规则禁新增 FK 与级联（上游自己就因为热表 `"user"` 上锁超时而用迁移 118 删掉了 117 刚加的 FK）。清理在应用层；遥测事件本质是 append-only 审计行，指向已删除 Skill 的历史行本就应该保留。
3. **`skill_id UUID` → `skill_ref TEXT`**——同理：builtin 没有 uuid，不能用 UUID 列记录它的使用量；而 59 个内置 Skill 的使用量恰好是最有价值的那部分数据。

**`version` 只是展示字段，不是内容身份**（§7 R-15）：内容是否真的变了，用现成的 `pkg/skillbundle.BuildManifest(skill).Hash`（内容哈希，`handler/daemon.go:3382` 已在用它判定包变更）。人手维的 `0.1.0 → 0.2.0` 只能回答“作者觉得改大了吗”，对“我上次用的是哪个版本”无用——两者不要混。

### 3.2 生命周期（对齐 CodeBanana 的市场交互，去掉"公开发布"）

`创建（与 Agent 对话打包 / 上传 / P2 §7 会话导出草稿）→ 私有库 → Add to Project → 发布到组织（选可见范围，内部版只有 org 一档）→ 版本更新（新版本号）`。列表带作者、版本、使用量排行（`skill_usage_event` 聚合）、`Bot` 类标签的等价物 = **运行时要求标签**（该 Skill 需要哪些本机 CLI/网络/TTY——从 SKILL.md 的前置要求半自动提取）。

**发布 = 授权**（2026-07-29 增补，S2）：Skill 从 private 升 org 的发布动作，即视为作者对"团队复用该工作方法"的显式授权，发布确认框明示此含义。个人隐私边界：发布校验含**敏感信息扫描**——**复用 `server/pkg/redact` 的同一份 `patterns`（现有 16 条：AWS/GitHub PAT 两形制/OpenAI sk-/Slack 两形制/GitLab/Google/Stripe/JWT/Bearer/PEM/连接串嵌密码/通用 KEY=VALUE），仅新增一个 `Findings(s string) []Finding` 入口与第 17 条个人路径模式**（§7 R-17）。该包现有 `Text()`/`InputMap()` 只能掉包不能定位，而发布拦截需要告诉作者“第几行命中了什么”。**不得另写一份正则表**——该包注释记了三次“少一条就泄漏”的补丁史（fine-grained PAT / `xapp-` / Stripe `sk_live_`），平行一份就是把这段历史重跑一遍；作者可对命中项提交误报申诉，由 Owner 逐条确认后放行，放行记录落 `activity_log`（谁、何时、对哪个命中项）——拦截是默认，放行是留痕的例外。团队沉淀的是工作方法与判断框架，不是把个人日志与隐私直接抽走。

### 3.3 治理钩子（tools 不变式落地为发布门禁）

发布/更新时服务端校验（把 `dir-graph.yaml#agents.contract` 的 4 条不变式变成代码）：`name`+`description` frontmatter 必填；org 可见的 Skill 必须指定唯一 `owner_actor`；SKILL.md 需通过 `validate-doc` 结构校验（daemon 侧跑）；内置 59 个 `builtin` Skill 只随 tools 包版本更新，Market 内不可编辑（防止方法论被局部魔改后漂移）。

**资产元数据卡**（2026-07-29 增补，S2）：org 可见的 Skill 在上述校验外增加 4 个必填 frontmatter 字段——复用者不该靠口口相传弄清一个资产怎么用：

| 字段 | 回答的问题 | 示例 |
|---|---|---|
| `applicable-scenarios` | 适用什么场景 | "Node 服务的 API 契约评审；不适用于前端组件" |
| `context-dependencies` | 依赖什么上下文 | "需要 specs/{id}/sdd.md 已存在；需要本机 pnpm" |
| `permission-declaration` | 能读写哪些目录 | "读 specs/**；写 change-requests/{CR}/review-annotations/" |
| `failure-handling` | 失败后怎么办 | "校验失败输出 blockers[]，回 reviewLoop；连续 3 次失败找 owner_actor" |

四字段渲染为 Market 详情页的"使用说明卡"；`permission-declaration` 与 P1 `rules.json#protectedPaths` 做一致性提示（声明写 protected 路径的 Skill 发布时警告）。builtin Skill 的四字段由 tools 包一次性补齐（其内容本就散落在各 SKILL.md 正文，此处是结构化提升）。

### 3.4 使用量遥测的采集点（**采集点已改，§7 R-16**）

原设计：任务完成回调里由 daemon 附带 `skills_used[]`。**改为：在服务端任务认领路径直写 `skill_usage_event`**。

因为原设计的前提——“Skill 物化信息只有 daemon 知道”——是错的。`handler/daemon.go:1982-2070` 显示服务端在认领时就算出了权威的 `skillRefs`（`AgentSkillRefData{ID, Source, Name, Hash, …}`）**并发给** daemon，只是没存（:3308 处那次 marshal 仅用于日志字节数统计）。改到认领侧后：

- `TaskCompleteRequest` 零改动 → 不必碰 `sanitizeTaskCompleteRequest`，避开了该函数注释里明写的陷坑（新 string 字段漏加 sanitize → NUL 字节 → SQLSTATE 22P05 → 任务永久卡在 running，GH #7098）；
- 无需“服务端重算 vs 信 daemon”的取舍（`ToolCalls` 字段先例就是服务端重算的）——采集点本身就在权威处；
- 无需按 name 反查 skill 行，也无 workspace 边界问题（`agent_task_queue` 没有 `workspace_id` 列，但认领 handler 本身持有上下文）；
- builtin 的 `"builtin:"` 合成 id 天然可识别。

**代价（必须写进指标定义页）**：时间戳含义从“完成时用了”变为“**派发时物化了**”，失败/取消的任务也会计一条。因此一切复用类指标的查询必须显式带 `agent_task_queue.status = 'completed'`（§1.2 已标注）——否则一个反复重试的失败任务能把复用次数刷上去。这是查询侧的一个 `WHERE`，换掉了采集侧的一条跨进程字段与一个任务卡死隐患。

### 3.5 过程记录资产化（可选，P3+）

对接 P2 §7 的「导出为 Skill 草稿」：Team Agent 会话多选 → SKILL.md 草稿 → 私有库 → 人工修订 → 经 §3.3 门禁发布。P3 侧只需保证导出的草稿带 `source: session-export` 标记（Market 列表可筛），供后续评估"会话导出"这条沉淀路径的实际转化率。不单独排期，随 Market 前端顺带。

## 4. 场景工坊：角色化视图（2026-07-29 增补，S4）

不同角色关注的不是同一组信息——产品关心 CR 与审批，QA 关心质量门与漂移，管理者关心效能与成本。**同一份数据，不同投影**——但“投影”不等于“新 route”。原设计的三个 route 级视图**已砍到一个**（§7 R-18）：

| 工坊 | 面向 | 落地形态（**已从三个新 route 砍到一个**，§7 R-18） |
|---|---|---|
| **效能驾驶舱** `/workshop/dashboard` | 管理者 | **保留为新 route**：即 §1 成熟度看板 + 交付效能板块 + AI 净价值叙事条。它本身就是 E2，不额外开发 |

## 6. 明确不做（防蔓延）

- 不做跨组织对标（单组织内部平台，没有可比对象）；
- 不做个人绩效导出/API（见 §1.5 立场）；
- 不做指标实时化（日粒度足够，实时化会把 rollup 复杂度翻倍而决策价值为零）；
- 不做 Skill 的付费/积分机制（内部资产，流通靠可见性与排行即可）；
- 不做 bypass 通路层对账（controlled-shell 审计行 ↔ trunk 提交交叉核对）：需把本地审计投影到服务端，属新采集，延后 P3+；P3 只做前缀层探测（§2.2）。

2026-08-19 新增的不做项：

- **不做通用 Pipeline Runner**——P3 所需的 `pipeline_node_run.attempt/status` 已由 `governance/gate_projection.go` 写入，读侧零阻塞（它是 M1/A2 的事，不是 P3 的前置）；
- **不做 LLM 对齐巡检**（`review-alignment` / `change-impact-analysis` 定时化）：七跳链路 + daemon 在线依赖，静默无结果与无漂移不可区分（§2.2）；
- **不做 `spec_trace` 投影表**：`cr_sync_event.payload` 已是完整事实，二次拆列只多一份会漂的副本（§2.1）；
- **不做需求工坊 / 质量中心两个新 route**：内容全是既有页面重排，降级为筛选器（§4）；
- **不把 Skill `version` 用作内容身份**：用现成的 `skillbundle.BuildManifest().Hash`（§3.1）；
- **不新建任何事务/队列/outbox 抽象**：仓内已有三套可用机制（crctl 文件 outbox + `cr_sync_event` 幂等账本、`webhook_delivery` 租约投递、`agent_task_queue` 的 `FOR UPDATE SKIP LOCKED`），P3 一行也不自建。
