## 2. 改造的表（加列，不改既有语义）

### 2.1 `issue` —— 挂 CR 指针（**已废止，未落地**，ADR-0001）

> 2026-08-07 敲定：以下 `issue.cr_id` 方案从未实施，正式废止。落地形态为 `cr` 表的
> `shell_issue_id` 反向引用列（语义=CR 关联 Issue，由 crsync 从 `cr.md#origin={type:issue}`
> 回填），CR 与项目经该列关联。废止理由与备选方案见 `docs/adr/0001-废止cr壳issue设计.md`。

```sql
-- （历史设计，未落地，保留仅作追溯）
-- 不用 metadata JSONB 存 cr_id（8KB cap 是防滥用的，且要索引和唯一性）
ALTER TABLE issue ADD COLUMN cr_id TEXT NULL;
CREATE UNIQUE INDEX issue_cr_id_unique ON issue(cr_id) WHERE cr_id IS NOT NULL;
-- 语义：cr_id 非空 ⇒ 该 Issue 是某 CR 的壳（1:1）；TASK 子 Issue 的 cr_id 为空，
-- 通过 parent_issue_id 归属。metadata 仍可自由放展示性键（如 cr_status_bucket）。
```

git 侧对应：`cr.md#origin: {type: issue, ref: <issue.id>}`（tools 既有字段，双向指针）。

### 2.2 `agent_task_queue` —— 任务归因到 CR 与 pipeline 节点

```sql
ALTER TABLE agent_task_queue
  ADD COLUMN cr_id TEXT NULL,                       -- 与 issue_id/chat_session_id/autopilot_run_id 平级的可选来源
  ADD COLUMN pipeline_node_run_id UUID NULL
      REFERENCES pipeline_node_run(id) ON DELETE SET NULL;
CREATE INDEX atq_cr_id_idx ON agent_task_queue(cr_id) WHERE cr_id IS NOT NULL;
```

沿用既有模式：`issue_id` 早已可空（chat/quick-create/autopilot 任务皆然），`cr_id` 是同族的第 4 个可选外键。claim 串行化不变（仍按 `agent_id` + 来源键）。

### 2.3 `workspace` —— 无改动

单组织即一行。**不删多 workspace 能力**（删比留贵，且未来可能要多事业部）。

## 3. 新增表（5 张）

### 3.1 `cr` —— CR 投影（只读镜像，git 为权威）

```sql
CREATE TABLE cr (
    cr_id            TEXT PRIMARY KEY,              -- 'CR-2026-001'，权威=git _index.yml 自增
    workspace_id     UUID NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    issue_id         UUID NOT NULL UNIQUE REFERENCES issue(id) ON DELETE RESTRICT,
    title            TEXT NOT NULL,
    status           TEXT NOT NULL CHECK (status IN (
                       'drafting','requirement-reviewing','requirement-approved',
                       'tech-designing','tech-design-review-pending','tech-design-reviewed',
                       'task-breakdown','developing','code-reviewing','code-approved',
                       'merging','writing-back','archived','rejected','withdrawn')),
    status_trigger   TEXT,                          -- 最近一次转移的 trigger 原文
    spec_id          TEXT,
    target_version   TEXT,
    owners           JSONB NOT NULL DEFAULT '{}',   -- {requirement:{id,assigned_at}, development:{...}, test:{...}}
    source_path      TEXT,                          -- 规划报告 source（可空）
    remote_ref       TEXT,                          -- origin/requirement/{CR-ID}
    checkpoints      JSONB NOT NULL DEFAULT '[]',   -- [{repo,branch,sha,pushed_at}]（_backlog.yml 镜像）
    merge_commits    JSONB NOT NULL DEFAULT '[]',
    review_summary   JSONB NOT NULL DEFAULT '{}',   -- {requirement:{verdict,blockers_n}, sdd:{...}, code:{...}, test:{status}}
    last_push_at     TIMESTAMPTZ,
    last_push_by     TEXT,
    projected_commit TEXT NOT NULL,                 -- 本行反映的 knowledge-base commit SHA（对账锚点）
    projected_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX cr_status_idx ON cr(workspace_id, status);
```

#### 3.1.1 落地形态修订（2026-08-07，对照代码核实后追认，ADR-0002）

实际落地列为：`cr_id / workspace_id / title / status / owners / target_version /
projected_commit / needs_reconcile / shell_issue_id / 时间戳`。上表设计的 14 列中
10 列**不补**，去留如下：

| 设计列 | 处置 | 理由 |
|---|---|---|
| checkpoints[] / merge_commits[] | 由 `cr_sync_event` 事件账本承载（event_kind=checkpoint/merge） | 事件行自带时间戳，P3 Lead Time 直接可算，快照列反而做不到 |
| review_summary | 由 gate_projection 的 pipeline_run/node_run 投影承担 | 门禁评审状态的权威投影路径已另建 |
| status_trigger / remote_ref / last_push_at / last_push_by / source_path / projected_at | 不落地 | 无消费方；需要时查 cr_sync_event |
| spec_id | 挂「待 P3 按需评估」 | P3-F3 追溯若走 spec_trace 表则不需要；届时需在 cr 表按 spec 直接过滤再补列 |
| shell_issue_id（新增，设计稿无） | 已落地 | CR 关联 Issue（ADR-0001），project_gates 项目级 CR 列表的唯一关联锚点 |
| needs_reconcile（新增，设计稿无） | 已落地 | 乱序/非法转移标记，reconcile 对账消费 |

原则：投影表职责是「当前状态可查」，历史细节属事件账本；不起 migration 补历史列。

字段来源对照（git → 投影）：

| git 权威位置 | `cr` 列 |
|---|---|
| `_backlog.yml#backlog[].status` / `cr.md#status`（双写，crctl CAS） | `status` |
| `_backlog.yml#remote-ref / last-push-at / last-push-by / checkpoints[] / merge-commits[]` | 同名列 |
| `cr.md#owners.{role}.{id,assigned-at}`（顶层 `owner` 仅兼容字段，忽略） | `owners` |
| `review-annotations/{requirement,sdd,code}.yml#verdict/blockers` + `test-report.md#status` | `review_summary` |
| `[cr] status X -> Y` commit 的 SHA | `projected_commit` |

### 3.2 `cr_sync_event` —— 同步入站账本（幂等）

```sql
CREATE TABLE cr_sync_event (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cr_id        TEXT NOT NULL,
    event_kind   TEXT NOT NULL CHECK (event_kind IN
                   ('status','owners','checkpoint','merge','archive','inbox')),
    from_status  TEXT, to_status TEXT, trigger TEXT,
    commit_sha   TEXT NOT NULL,                    -- 携带该变更的 git commit
    actor        TEXT,                             -- crctl --caller（自报身份，仅记录不信任）
    payload      JSONB NOT NULL DEFAULT '{}',
    reported_by  TEXT NOT NULL CHECK (reported_by IN ('daemon','webhook','reconcile')),
    processed_at TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (cr_id, commit_sha, event_kind)         -- 幂等键：重复上报静默去重
);
```

触发链：`crctl advance/approve/git push` → daemon 检出 `[cr] `/`merge(` 前缀 commit → 上报（复用 `/api/daemon/*` 回调族新增一个 `/api/daemon/cr-events`）→ worker 消费 → 更新 `cr` 投影 + `issue.metadata.cr_status_bucket` + 触发 WS 推送。对账兜底：定时 `reconcile` 任务对比 `cr.projected_commit` 与 `origin/requirement/{CR-ID}` HEAD，漂移则整行重投影。

### 3.3 `approval_record` —— 服务端签名审批（替代 crctl 的 TTY 审批）

```sql
CREATE TABLE approval_record (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cr_id            TEXT NOT NULL,
    stage            TEXT NOT NULL CHECK (stage IN
                       ('requirement','tech-design','dev-start','code')),
    decision         TEXT NOT NULL CHECK (decision IN ('approve','reject')),
    approver_user_id UUID NOT NULL REFERENCES member(user_id),  -- RequireHumanActor 保证非 mat_ 令牌
    evidence_digest  TEXT NOT NULL,   -- 审批时刻 review-annotations + test-report 的 sha256（防"批完再改证据"）
    signature        TEXT NOT NULL,   -- 服务端 Ed25519 签名(cr_id|stage|decision|evidence_digest|ts)
    reject_reason    TEXT,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (cr_id, stage, decision, evidence_digest)
);
```

闭环方式：daemon 把签名凭据写入 worktree 的 `approval.yml`（新增 `via: server-approve` + `signature`），crctl 的 gate 校验扩展为承认 `via: crctl-approve | server-approve`（后者验签，公钥随 tools 包分发）。**审批强度不降级**：签名由服务端私钥签发，模型与本地脚本都无法伪造；`reject` 走状态机既有的显式回退转移。（2026-08-07 落地形态注：stage 四阶段枚举为代码侧校验，DB 列无 CHECK；唯一约束为部分唯一索引 `(cr_id, stage, evidence_digest) WHERE decision='approve'`，reject 不限条数；真人校验将统一到 `RequireHumanActor` 中间件，见 P1 §B）

### 3.4 `pipeline_run` / `pipeline_node_run` —— Runner 状态（tools 的 P6 缺口）

```sql
CREATE TABLE pipeline_run (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id  UUID NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    pipeline_id   TEXT NOT NULL,           -- 'requirement-authoring' 等 8 个
    cr_id         TEXT NULL,               -- 规划类 pipeline 无 CR
    issue_id      UUID NULL REFERENCES issue(id) ON DELETE SET NULL,
    status        TEXT NOT NULL DEFAULT 'running' CHECK (status IN
                    ('running','waiting_approval','completed','failed','cancelled')),
    inputs        JSONB NOT NULL DEFAULT '{}',
    execution_context JSONB NOT NULL DEFAULT '{}',  -- node-1.md 末尾 YAML 块的镜像（cr_id/branch/worktrees）
    started_by    UUID NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at  TIMESTAMPTZ
);
CREATE TABLE pipeline_node_run (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    run_id        UUID NOT NULL REFERENCES pipeline_run(id) ON DELETE CASCADE,
    node_id       UUID NOT NULL,           -- pipeline JSON 里的节点 UUID
    ref           TEXT,                    -- skill id；human_approval 为 NULL
    kind          TEXT NOT NULL CHECK (kind IN ('skill','human_approval','code_generation')),
    seq           INT NOT NULL,            -- nodes[] 数组序
    status        TEXT NOT NULL DEFAULT 'pending' CHECK (status IN
                    ('pending','running','passed','blocked','skipped','failed')),
    attempt       INT NOT NULL DEFAULT 1,  -- reviewLoop 轮次；权威副本按 AGENTS.md 回写 git review-loop.yml
    approval_id   UUID NULL REFERENCES approval_record(id),
    output_note   TEXT,                    -- node-N.md 的 worktree 相对路径
    started_at    TIMESTAMPTZ, completed_at TIMESTAMPTZ,
    UNIQUE (run_id, node_id, attempt)
);
```

Runner 语义直接采 tools 的既有声明：线性 `nodes[]`、唯一回边 `reviewLoop`（`replayNodes[]` 按序重放）、`passCondition` 只有 `allOf` + `equals`/`isEmpty`、`maxAttempts=3`、`onFail: abort|skip`。条件分支从 prompt 自然语言提升为节点级 `when` 字段（P0 只在 runner 侧支持，pipeline JSON 逐步补写）。

> 或 project 直接挂载）。以下表格保留作历史设计记录。

### 4.2 CR-ID 与 Issue 编号并存

两套编号都保留、互不侵入：`CR-2026-001` 权威在 git（`_index.yml` 自增）；`AIF-42` 式 Issue 编号权威在 PG（`workspace.issue_counter`）。不统一编号——两个自增源合并需要分布式协调，收益为零。（2026-08-07 核实修正：落地形态中 `cr` 表持 `cr_id` + `shell_issue_id`（CR 关联 Issue，可空），无 `issue_id` 列；双标并列展示未实施，随壳 Issue 废止一并悬置）

### 6.1 目录契约扩展（2026-07-29 增补，S1/S6）

tools 的 `dir-graph.yaml` 目录语义声明在既有 `specs/ · delivery/ · change-requests/ · docs/` 之上补两类位置约定——**只改声明文件，无 DDL、无实体关系变化**：

**① 探索型/横向知识目录（S1）**——给"不进强治理基线、但应可被知识问答消费"的知识一个家：

| 目录 | 放什么 | 治理属性 |
|---|---|---|
| `docs/research/` | 竞品资料、用户访谈、市场洞察 | 不受 `protectedPaths` 保护；可被 LLM Wiki 最小版（P2.5 轻量档）消费 |

**② 发布材料位置（S6）**——测试→发布段在事实源中补一等公民位置：`delivery/release/release-{version}.md`（发布记录：版本、日期、包含 CR 列表、回滚方式）+ `delivery/release/checklist-{version}.md`（发布检查单）。`writeback` pipeline 增补"发布材料回写"节点的**文档级约定**（pipeline JSON 属 P1 Runner 落地时逐步补写，P0 只锁目录位置，与"pipeline 条件补写"走同一节奏）。

**③ Wiki 衍生解释层（2026-07-30 增补，S1）**——`wiki/` 目录：由 `wiki-maintain` Skill 生成维护的代码 Wiki（quickstart.md 入口 + 章节目录 + open-questions.md + `.last-update.json` 增量锚点）。治理属性：**衍生层，不是事实源**——不受 gate 保护（不是证据）、可整目录删除重建、git 版本化；Wiki 维护任务的写白名单**只含**此目录（`rules.json#taskWriteAllowlist`，边界在 execenv 工具层）。页面格式（frontmatter/链接即边/反薄页）与全部纪律详见《Wiki子系统设计》。

## 7. 实体关系总览

workspace(=组织) 1─n project(=平台项目) ── project_resource ↔ dir-graph#repositories
       │                    │ 1:1 约定
       │                    └─ agent(项目 Agent) ←─ agent_skill ←─ skill(59)
       1─n issue(统一入口：反馈/杂事/咨询/CR壳)
              │ parent_issue_id
              ├─ issue(TASK 子 Issue)  ← 投影自 tasks/TASK-NN.md
              │
              │ issue.cr_id (1:1, 部分唯一索引)
              └─ cr(投影) ←──同步 worker──← git: _backlog.yml + cr.md + review-annotations/*
                    │                              ▲
                    │ cr_id                        │ crctl advance/approve (CAS)
              pipeline_run 1─n pipeline_node_run   │
                    │                    │ approval_id → approval_record(服务端签名)
                    │                    └─ 1:1 agent_task_queue(执行) ── task_message(流式)
                    └─ cr_sync_event(幂等入站账本)
```
