## 0. 对照 CodeBanana 的设计对齐结论

### 0.1 核对为忠实、按原样落地

| 设计点 | 快照证据 | 落点 |
|---|---|---|
| 三模式 = 同一聊天窗口头部**三个平铺 tab**（激活项加粗 + 滑动下划线），不是三个页面 | `#chat-control-panel-header` 实物 | D2 |
| 工具执行卡：工具名 + 耗时毫秒 + 参数摘要 + 状态徽标，可折叠 | 消息流实物（read_file/run_terminal_cmd 卡片） | D3 |
| presenter 全套通知/申请/转让/撤销流；"管理员可直接对话但 Agent 忙时需等待" | i18n 文案全套 | D4 |
| Discussion 输入区**无**模式/模型下拉、无上下文用量——纯人类输入仅留 @ | 项目 Discussion 页实物 | D6 |
| 队列提示（"请求排队中"、"{count} 条排队"）全员可见 | i18n 文案 | D3（后端已由 D1 交付） |

### 0.2 吸收的额外设计（v1 未列，低成本高价值）

1. **三 tab 空态问候语 + 模式教程气泡**（"点击在协作 Agent、私有 Agent 和团队讨论之间切换"）→ D2。
2. **Team Agent tab「只看 Agent 请求」过滤开关**（tab 旁迷你开关，快照实物）——吸收 CodeBanana
   "项目/消息双入口"的设计动机（人类讨论不被 Agent 过程消息淹没），但**不做双入口本体**，
   一个过滤开关达到同等效果 → D3。
3. **满队同步反馈**：发送被拒时输入区立即禁用并给结构化原因，而非静默失败 → B1 薄发送端点（§B）。

### 0.3 识别为偏差、按自研设计对待（不能再假设"原产品已打磨好"）

- **合并转发**：CodeBanana 实物只有多选逐条转发（可附说明），"多条讨论合并为一个带上下文的
  Team Agent 任务"是本平台增量设计（字典 `mergedForwardMessage` 存在但页面未见实物）→ D8 按新设计评审。
- **DC 语义**：CodeBanana 的 DC 是"静默协调器（消息**不会**出现在聊天中）"；设计稿是可见协调输出。
  本文预设**可见输出**：内部平台"过程即记录"的审计要求下，静默协调不可取 → D8 设计阶段确认。

### 0.4 明确不吸收（写死排除，防止后续被当遗漏）

- 项目/消息**双入口**（两个导航入口进同一窗口、不同排序）——单入口（项目页）足够，动机已由 0.2-2 吸收。
- 右侧 work-viewer（文件树/最近文件/Diff/端口预览）——本地执行路线下由 daemon + 本机 IDE 承担，平台侧另议。
- 上下文用量指示器 + 清空上下文——依赖 daemon usage 回调聚合，随后续交付。
- 语音输入、消息回复（reply）线程、消息转发（D8 的合并转发除外）——后续。
- v1 排除项继续有效：§8 成员管理增强（邮件邀外部好友/解散群组/头像编辑器）、§6.1 斜杠命令、
  §7 导出 Skill 草稿 / 恢复检查点（三态回滚，独立 CR 量级）/ 点踩反馈。
- **mobile 全程不在 P2 范围**：`packages/views` 只覆盖 web + desktop（Electron 同一套组件）；
  `apps/mobile` 是独立 RN 组件集，三模式窗口的 RN 版另立交付。

```

 ├─ CR-C  D5 Private Ask（含 B2）

 ├─ CR-E  D4 presenter 控制权（含 claim 串行化键改造）
 └─ CR-F  D7 门禁接合（含 B4 迁移）
        CR-G  D8 DC + 讨论转执行（依赖 CR-D；转发目的地依赖 CR-A）
```

| CR | 覆盖 | 性质 | 前置 | 量级（粗估） |
|---|---|---|---|---|
| **CR-A** | D2 + D3 核心：三 tab 骨架 + Team Agent 消息流最小闭环（B1/B3/B5） | 后端 + 前端，**最重** | D1（已交付） | 前端 4–6 人日 + 后端 2–3 人日 |
| **CR-B** | D3 完整形态：队列条展开列表/逐项撤回/停止/过滤开关 | 纯前端 | CR-A | 2–3 人日 |
| **CR-C** | D5 Private Ask（B2） | 小后端 + 前端 | CR-A | 2–3 人日 |
| **CR-D** | D6 Discussion（B3 的 discussion 容器） | 小后端 + 前端 | CR-A | 2–3 人日 |
| **CR-E** | D4 presenter（claim 串行化键 `agent_id`→`project_id`） | 后端重、风险面独立 | CR-A（UI 挂点） | 4–5 人日 |
| **CR-F** | D7 门禁接合（B4 迁移 + 审批卡/blocker/CR 徽标） | 后端 + 前端，跨 P1 链路 | CR-A | 4–5 人日 |

v1 的"D5/D6 可并入主体 CR"**作废**——CR-A 计入 B1 后端后已是 CR-2026-004 的 2–3 倍体量，再并会成为难评审难验收的巨型 CR。

## B. 后端能力缺口清单（按需求补齐，随所属 CR 交付）

### B1 Team Agent 群聊消息持久化（CR-A，本文最重要的决策点）

**现状**：multica 的 `chat_session`/`chat_message` 严格 1:1（仅 `workspace_id`/`agent_id`/`creator_id`，
无项目维度、无多人可见语义）；`agent_task_queue` 是任务队列不是聊天记录。
**"全员可见、刷新可回放的群聊消息历史存在哪里"目前无解**，v1 把 D3 描述成"接既有能力"不准确。

两个候选方案：

- **方案甲（本文预设）：复用 comment + 隐藏容器 Issue**。
  项目 lazily 创建一个系统容器 Issue（B3），Team Agent 面的每条用户消息 = 该 Issue 的 comment，
  Agent 回复与工具执行 = 既有 task transcript / timeline。
  优点：消息历史、分页、@提及、附件、通知、WS 事件**全部白拿**；前端直接套
  `packages/views/issues/hooks/use-issue-timeline.ts` 的既有模式。
  缺点：comment 带 resolved/reaction 等聊天不需要的语义（无害不用即可）；
  评论触发入队现为 fire-and-forget（下面的薄端点解决）。
- **方案乙：新表 `project_chat_message` + 专用消息 API + 新 WS 事件**。
  模型干净、发送端点天然可同步 429；但分页/附件/提及/通知基础设施全部重建，量级约 ×3。**不推荐**。

**甲的补强——薄发送端点**（对齐 CodeBanana 的同步禁用体验）：
`POST /api/projects/{id}/chat/messages`，服务端顺序执行
**容量守卫（复用 D1 的 `guardProjectQueueCapacity`）→ 落 comment → enqueue**；
满队时同步返回 429 `project_queue_full`（含 depth/limit，评论**不**落库）。
既有的评论 @提及 fire-and-forget 路径保持不动（向后兼容，Issue 页照旧）。
最终选型在 CR-A 的 SDD 定案，偏离方案甲需给出理由。

### B2 chat_session 项目维度（CR-C）

`chat_session` 加 nullable `project_id` 列 + 按 `(project_id, creator_id)` 查询会话；
Private Ask 会话按项目上下文隔离、与既有全局 1:1 chat 并存。迁移量小。

### B3 系统容器 Issue（CR-A 建 team-agent-chat；CR-D 建 discussion）

项目首次打开聊天窗口时 lazily 创建，打专用类型/label 标记，Issue 列表与看板过滤隐藏。
Discussion 面挂 discussion 容器 Issue 的 comment 流——v1 说"挂项目根 Issue"，该 Issue 并不存在，需自建。

### B4 `agent_task_queue` 增列迁移（CR-F，沿 v1）

`cr_id`/`pipeline_node_run_id` 两列 P0 设计有、迁移未做，CR-F 自带迁移。

### B5 模型选择器数据源（CR-A 的 SDD 内核实）

§6 要求模型列表 = daemon 上报的本机 Runtime 可用模型（非云端全集）。`runtimes` 页面/API 已存在；
既有 1:1 chat 输入区是否已带模型选择器**待核实**——有则复用，无则 CR-A 内新建下拉（读 runtimes 数据）。
无可用 Runtime 时输入区提示「请先在设置中启动本地 Agent」。

### WS 语义修正（全体 CR 的实现前提，替代设计稿 §9.3 的表述）

设计稿写的"WS 房间分级（`workspace:{id}` / `task:{id}` / `chat:{sessionId}`）"与 multica 实现**不符**：
实际是**单条 workspace 级 socket**（`packages/core/api/ws-client.ts`），服务端按 workspace fanout，
客户端按 payload 内的 `issue_id`/`chat_session_id`/`task_id` 字段过滤；没有 per-channel 订阅。
各 D 所说"频道"一律按此理解。推论：**Private Ask 的隐私（消息永不进全工作区广播）只能靠
服务端 per-user 推送逻辑保证，前端过滤保证不了**——这是 D5 验收 1 的验证对象。
新增聊天事件的接入方式：后端加事件类型 → `packages/core/realtime/use-realtime-sync.ts` 加 handler
（或组件内 `useWSEvent`），无需新连接。

## D2 窗口骨架 + 三 tab 切换（CR-A）

**入口决策（v1 未定，本版定死）**：`project-detail.tsx` 主区加 Tabs——**Issues | Chat**，
`?tab=` 参数保持 URL 可达。这是 multica 现有结构里替换点最清晰的位置：主区目前唯一子组件就是
`IssueSurface`，Chat tab 渲染新组件 `packages/views/projects/components/project-chat-panel.tsx`；
右侧 `AnimatedRightSidebar`（含 D1 的 `ProjectQueueStatus`）原样保留，天然充当 chatHeader 信息位。

**范围**：
- 三模式 tab 条：复用 `packages/ui/components/ui/tabs.tsx`（line variant，现成滑动下划线样式）；
  每 tab 带 tooltip + 空态问候语（`heyTeamAgent`/`heyPrivateAsk`/`heyDiscussion` 三条）+ 首次进入教程气泡。
- 三面独立 query key（沿 multica 约定：session/消息级 key 独立根、靠 WS 保鲜）；
  切 tab 纯前端，不重拉数据（react-query `staleTime: Infinity` + WS 失效的既有模式下天然成立）。
- 输入草稿按 `{projectId}:{mode}` 存 zustand——**新建独立 store**（参照 `useChatStore` 的
  workspace-slug 命名空间持久化写法），**不得复用 `useChatStore`**（其 `activeSessionId` 是
  浮窗与 /chat 页共享的全局单例，挂第三个消费者会互抢会话）。
- 右侧抽屉：成员抽屉复用既有 member 组件；技能/定时任务/Agent 配置/设置只留入口占位。
- 新增 UI 文案全部四语（en/ja/ko/zh-Hans）——`packages/views/locales/` 有 parity 测试强制。

**验收**：
1. 项目页 Chat tab 进入群聊窗口，三 tab 可切换，切换不触发网络请求（缓存命中），`?tab=` 深链可达。
2. 各 tab 输入草稿独立保留（刷新后仍在）；浮窗 FloatingChat 与 /chat 页会话不受影响（单例不冲突回归）。
3. web 与 desktop（Electron 共享 views 包）行为一致。

## D3 Team Agent 消息流（核心=CR-A，完整形态=CR-B）

### CR-A 部分：最小可用闭环

**范围**：
- B1 方案甲落地：team-agent-chat 容器 Issue（B3）+ 薄发送端点（守卫→落 comment→enqueue，满队同步 429）。
- 消息流：套 `use-issue-timeline.ts` 模式；用户消息用 `comment-card.tsx` 渲染，Agent 执行过程用
  `packages/views/common/task-transcript/build-timeline.ts` + `TimelineView` 渲染工具执行卡
  （running/done/error/interrupted 徽标 + 耗时 + 可折叠输入输出）。
  注意：`TimelineView` 目前是 `chat-message-list.tsx` 的内部组件，**需导出**。
- 发送：复用 `chat-input.tsx`（纯 props，附件/@提及/草稿现成），onSend 接薄发送端点。
- 满队反馈：429 时输入区禁用 + 「Agent 忙，请稍后」，`projectQueueStatusOptions`（D1 已有）驱动恢复。
- 历史回放：分页加载（"暂无更早消息"分隔线），刷新后全量可回放。

**验收**：
1. 发消息 → 容量守卫 → 落库 → 入队 → claim → 工具卡逐个实时渲染 → 完成，全链路窗口内可见。
2. 刷新页面，历史消息与工具执行卡完整回放（持久化验证，B1 的核心验收）。
3. 满队时发送同步收到 429（消息不落库），输入区禁用并展示 depth/limit；owner/admin 不受禁用（D1 语义）。

### CR-B 部分：队列条完整形态 + 停止 + 过滤

**范围**（纯前端，后端能力 D1 已全部交付）：
- 队列条常驻：「{count} 条排队」；展开列表逐项显示发起人（`fromUser`）；发起人对自己的排队项有
  「清除对话」撤回按钮（调 D1 cancel 端点，403/409 结构化反馈）。
- 停止：发送者停自己（运行中或排队中）、Owner 停任意（D1 已收紧的服务端权限直接生效）；
  停止后已生成内容保留、下一条自动开始。
- 「只看 Agent 请求」过滤开关（0.2-2）：本地过滤消息流，只影响渲染不动数据。
- 消息悬浮操作本期只做**复制**（回复/转发按 0.4 排除）。

**验收**：
1. 队列条 WS 实时（无手动刷新）；撤回自己的排队项成功、撤他人被拒（403 呈现）。
2. 停止双权限路径真机验证；停止后内容保留、队列前移。
3. 过滤开关开关往返，消息流内容与数量正确。

## D4 presenter 控制权 UI（CR-E）

**范围**（沿 v1）：§3.1 状态机全部 6 个通知文案（申请/批准/转让/撤销/拒绝/释放）、chatControlPanel
权限面板、chatHeader「当前主持人」显示。**含后端改造**：claim SQL 串行化键从 `agent_id` 换
`project_id`（P0 §2.2 论证过），presenter 判定接入入队/claim 路径。
可选吸收：CodeBanana 的系统状态卡（"Presenter preferences loaded"类内联状态条）作为通知的呈现形式。

**验收**（沿 v1）：
1. 单一写者：presenter 非空时其他成员消息不被执行（排队或拒绝，按设计稿口径）；Admin 在 Agent 空闲时可直接接管。
2. 6 个状态转移各自触发对应通知卡片；头部主持人显示实时更新。
3. claim 串行化键改造后，既有单 agent 并发语义回归测试全绿（**风险点，独立 CR 的主因**）。

## D5 Private Ask 面（CR-C）

**范围**：B2（chat_session 加 project 维度）+ 窗口第二 tab。
实现路径：**绕开 `use-chat-controller.ts`**（耦合全局 `useChatStore` 单例），直接组合纯 props 的
`ChatMessageList` + `ChatInput` + `TaskStatusPill`，sessionId 由 project-chat-panel 自管。
语义四差异沿设计稿 §4：个人独立队列、默认 Ask-only 只读（execenv 不给写）、仅本人可见、与 Team Agent 并行。

**验收**：
1. 隐私：两个浏览器会话验证 A 的 Private Ask 消息 B 永远看不到——**验证服务端推送逻辑**
   （单 socket 架构下前端过滤不算数，见 §B WS 语义修正）。
2. Team Agent 跑任务的同时 Private Ask 可正常并行问答。
3. Ask-only：Private Ask 内 Agent 无法写 worktree（execenv 只读约束真机验证）。
4. 回归：既有浮窗/全页 chat 不受 B2 迁移与新入口影响。

## D6 Discussion 面（CR-D）

**范围**：B3 的 discussion 容器 Issue + 纯人类多人聊天。
复用清单：`comment-card.tsx`（ActorAvatar + ReadonlyContent + ReactionBar + 附件）、`reply-input.tsx`、
@提及 + 通知 + 订阅基础设施；成员变更等行内系统条。输入区无模式/模型下拉（0.1 表，CodeBanana 实证）。

**验收**：
1. 多成员实时聊天（workspace 级 WS 广播）；@提及触达通知。
2. Discussion 消息不产生任何 `agent_task_queue` 行（除非 D8 的 DC 被显式激活）。
3. 容器 Issue 不出现在 Issue 列表/看板（隐藏过滤验证）。

## D7 门禁接合（CR-F）

**范围**（沿 v1）：pipeline 节点任务（`pipeline_node_run_id` 非空）在消息流内渲染门禁状态条：
`human_approval` 节点渲染审批卡（走 P1 服务端签名审批，非 TTY），有权限者见批准/驳回，驳回注入
review_feedback；review 节点 `verdict=block` 显示 blocker 列表 + reviewLoop attempt N/3；
头部显示 CR 16 态徽标（吃 P1 的 cr 投影表）。**含 B4 迁移**。
（CodeBanana 有"{count} 个待审批任务"计数与 Approval Workflow 项目，但审批卡实物样式快照未捕获——
卡片视觉自定，语义按 P1 签名审批链路。）

**验收**（沿 v1）：

## D8 DC 协调者 + 讨论转执行（CR-G，自研设计定位）

**范围**：DC 特殊 Agent（默认静默，@提及或回复激活；只协调不执行：execenv 只读 + forbidden 全部写
Skill；可 `EnqueueTaskForMention` 路由到 Team Agent）；合并转发（多选 Discussion 消息 → 合并为带
