# P2 交付切分补遗 — 三模式聊天窗口主体

> 背景：《P2-三模式聊天交互设计》§11 的交付切分表只列了 D1（Team Agent 共享队列容量上限），
> 因为那张表衡量的是「需要新写**后端业务逻辑**的部分」——D1 是唯一一项 Multica 后端没有的能力。
> 但设计稿其余章节所说的"直接复用既有能力"指的是**后端基础设施**现成（表、WS、claim SQL、评论系统都在），
> **前端的三 tab 项目群聊窗口本身并不存在，需要从零实现**——这是平台 PRD 人力表中
> 「前端 2 人 · P2–P3 重」的主体工作量，此前未编入交付切分。本文补齐 D2–D8。
>
> D1 已由 CR-2026-004 交付（容量守卫 + owner/admin 插队 + 撤回权限 + project-detail 队列指示 +
> quick-create 满队反馈）。本文各项均以 D1 的后端能力为既有前提。
> 交互细节、字典锚点、后端映射一律以《P2-三模式聊天交互设计》对应章节为准，本文不重复，只做切分与验收定义。
> 日期：2026-08-01。

## 0. 总览与依赖顺序

```
D2 窗口骨架 + 三 tab 切换          ←—— 一切的容器，先行
 ├─ D3 Team Agent 消息流（含队列条完整形态、toolExecutionCard、停止）
 │   ├─ D4 presenter 控制权 UI
 │   └─ D7 门禁接合（审批卡 / blocker / CR 徽标）
 ├─ D5 Private Ask 面
 └─ D6 Discussion 面
     └─ D8 DC 协调者 + 讨论转执行（合并转发）
```

D2 是唯一的硬前置；D3–D6 之间无相互依赖，可并行；D7 依赖 D3，D8 依赖 D6（合并转发的目的地依赖 D3）。

## D2 窗口骨架 + 三 tab 切换

**范围**：项目群聊窗口容器（chatHeader 头部工具条、模式切换条、消息流区、输入区四段式，§1 骨架图）；
三模式为同一窗口内三个 tab，切换纯前端不重拉数据；三面独立 query key；输入草稿按 `{projectId}:{mode}` 存 Zustand。
成员/技能/定时任务/Agent 配置/设置等右侧抽屉本期只留入口占位（成员抽屉复用既有 member 组件）。

**明确排除**：§8 的成员管理增强（邮件邀请外部好友、解散群组、头像编辑器）、§6.1 斜杠命令、§7 的
导出 Skill 草稿 / 恢复检查点 / 点踩反馈——各自另立交付（恢复检查点依赖三态回滚，工作量独立成 CR 的量级）。

**验收**：
1. 项目页可进入群聊窗口，三 tab 可切换，切换不触发网络请求（缓存命中），各 tab 输入草稿独立保留。
2. 三面消息流各自用独立 query key（切换回来不丢滚动位置为加分项、非门槛）。
3. web 与 desktop（Electron 共享 views 包）行为一致。

## D3 Team Agent 消息流（P2 主体核心）

**范围**：
- 消息流：用户消息 + Agent 回复渲染，接 `agent_task_queue`（issue/task 链路）与 WS `workspace:{id}` + `task:{id}`。
- **toolExecutionCard**（§3.3）：消费 pkg/agent 六类 Message 流（NDJSON→WS→卡片），
  running/done/error/interrupted 状态徽标 + 耗时 + 可折叠输入输出。
- **队列条完整形态**（§3.2，补齐 CR-2026-004 留下的 UI 缺口）：常驻队列条显示「{count} 条排队」；
  展开可见排队项列表，每项显示发起人（`fromUser`）；发起人对自己的排队项有「清除对话」撤回按钮
  （调 D1 已交付的 cancel 端点，403/409 结构化反馈）；满队 & 非 owner/admin 时输入区禁用 +
  「Agent 忙，请稍后」（D1 的 429 与 queue-status 端点均已就绪）。
- **停止**（§3.4）：发送者停自己（运行中或排队中）、Owner 停任意（D1 已收紧的服务端权限直接生效）；
  停止后已生成内容保留、下一条自动开始。

**验收**：
1. 发消息 → 入队 → claim → 工具卡逐个渲染 → 完成，全链路在窗口内可见。
2. 队列条实时（WS 驱动，无手动刷新）；排队项显示发起人；发起人撤回自己的项成功、撤他人项被拒（403 呈现）。
3. 满队禁用态与恢复（复用 D1 验收口径，但发生在聊天输入区而非 quick-create 弹窗）。
4. 停止按钮双权限路径真机验证。

## D4 presenter 控制权 UI

**范围**：§3.1 的控制权状态机全部 6 个通知文案（申请/批准/转让/撤销/拒绝/释放）、chatControlPanel
权限面板、chatHeader「当前主持人」显示。**含后端改造**：claim SQL 串行化键从 `agent_id` 换 `project_id`
（P0 §2.2 论证过的方案，涉及 claim 语义变更，需独立评审），presenter 判定接入入队/claim 路径。

**验收**：
1. 单一写者：presenter 非空时其他成员消息不被执行（排队或拒绝，按设计稿口径）；Admin 在 Agent 空闲时可直接接管。
2. 6 个状态转移各自触发对应通知卡片；头部主持人显示实时更新。
3. claim 串行化键改造后，既有单 agent 并发语义回归测试全绿（风险点，独立 CR 的主因）。

## D5 Private Ask 面

**范围**：§4——与 Team Agent 同构的会话面，四处不同：个人独立队列（互不可见）、默认 Ask-only 只读
（execenv 不给写）、消息仅本人可见（WS `chat:{sessionId}`）、可与 Team Agent 并行。
后端 `chat_session`/`chat_message` 语义现成，主要是把既有 chat 视图（`packages/views/chat/`）
嵌进窗口第二 tab 并对齐项目上下文。

**验收**：
1. 两个浏览器会话验证隐私：A 的 Private Ask 消息 B 永远看不到（含 WS 层面无广播泄漏）。
2. Team Agent 跑任务的同时 Private Ask 可正常并行问答。
3. Ask-only：Private Ask 内 Agent 无法写 worktree（execenv 只读约束真机验证）。

## D6 Discussion 面

**范围**：§5——纯人类多人聊天，无队列无 Agent 驱动，后端映射为挂 CR 壳 Issue（或项目根 Issue）的
`comment` 流，复用评论 + @提及 + reaction + 订阅基础设施；成员变更等行内系统条。

**验收**：
1. 多成员实时聊天（WS `workspace:{id}` 广播）；@提及触达通知。
2. Discussion 消息不产生任何 `agent_task_queue` 行（除非 D8 的 DC 被显式激活）。

## D7 门禁接合（Team Agent × CR 治理）

**范围**：§3.5——pipeline 节点任务（`pipeline_node_run_id` 非空）在消息流内渲染门禁状态条：
`human_approval` 节点渲染审批卡（走 P1 服务端签名审批，非 TTY），有权限者见批准/驳回，驳回注入
review_feedback；review 节点 `verdict=block` 显示 blocker 列表 + reviewLoop attempt N/3；
头部显示 CR 16 态徽标（吃 P1 的 cr 投影表）。
**前置事实**：`agent_task_queue.pipeline_node_run_id` 列尚未落库（P0 设计有、迁移未做），本项含该迁移。

**验收**：
1. 真实跑一条带 human_approval 的 pipeline，审批卡出现 → 网页点批准 → 服务端签名 grant → crctl 验签推进，全链路不落 TTY。
2. 驳回路径：reject_reason 注入修复节点，消息流可见 reviewLoop 轮次。
3. CR 状态徽标与 `cr` 投影表一致（P1 已交付的同步链路直接消费）。

## D8 DC 协调者 + 讨论转执行

**范围**：§5.1–§5.2——DC 特殊 Agent（默认静默，@提及或回复激活；只协调不执行：execenv 只读 +
forbidden 全部写 Skill；可 `EnqueueTaskForMention` 路由到 Team Agent）；合并转发（多选 Discussion
消息 → 合并为带上下文的 Team Agent 任务；无 CR 时可触发 `requirement-register` 升级为 CR）。

**验收**：
1. DC 静默/激活边界：未被 @ 时不响应；激活后只产生协调输出，无任何文件写入（审计验证）。
2. 合并转发：选中 N 条消息生成一个 Team Agent 任务，prompt 含 `triggerMessage` + `chatHistory` 汇总结构。
3. 讨论升级 CR 路径走 P0 的 Issue→CR 升级链路，产生合规的 CR 壳。

## 附：与 CR-2026-004（D1）的边界备忘

- D1 交付的是容量治理**后端全量能力** + 无聊天窗口前提下的最小可见 UI（project-detail 队列指示、
  quick-create 429 反馈）。D3 落地时，队列条完整形态直接消费 D1 的
  `GET /api/projects/{id}/queue-status`、429 `project_queue_full` 结构化响应与已收紧的 cancel 权限，
  **不需要再动后端**。
- D1 实现期已确认并记录的两个事实，D3/D7 实现时需要知道：
  1. 评论触发的入队是 fire-and-forget（评论先落库，enqueue 失败仅日志）——聊天输入区的满队反馈
     必须靠前端禁用态 + queue-status 轮询失效，不能指望评论接口返回 429。
  2. `agent_task_queue` 尚无 `cr_id`/`pipeline_node_run_id` 列（P0 设计有、迁移未做），D7 需自带迁移。
