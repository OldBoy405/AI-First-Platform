# 缺口清单 — 排除与条件触发（防遗漏台账）

> 文档定位：区分“当前明确不做”“完整形态不做但有最小替代”“条件满足后重评”，避免把本期裁剪永久化。
> 实证基线：multica `082a753`（merge CR-2026-031）；tools 已与 `origin/custom/main` 同步至 `462c3e9`（merge CR-2026-044）。
> 方案依据：`docs/analysis/AI-First平台缺口修订与最小落地方案.md`。
> 历史来源：P2 切分 §0.4、CR-F 范围排除项、旧优先级清单。历史“写死排除”保留为来源，不再作为当前永久决策。

---

## 0. 判定规则

| 分类 | 含义 | 后续处理 |
|---|---|---|
| **维持不做** | 动机已被现有能力吸收，或与当前 AI First 研发主线无关 | 不立项；出现新用户事实再改表 |
| **排除完整档** | 大而全形态无必要，但存在低成本最小替代 | 只允许最小档进入相关 CR，不单建完整产品 |
| **条件 backlog** | 有真实价值场景，但当前缺使用量、依赖或失败证据 | 条件满足后重新写 PRD，不自动实施 |
| **移出排除** | 已有基础或价值闭环要求明确，不能继续写成永久不做 | 转入计划清单或相关 CR 的最小范围 |

“代码中没有某组件”只能证明未实现，不能单独证明不值得做。排除必须基于用户价值、替代能力和触发条件。

## 2. 维持不做

### 2.1 项目/消息双入口

现有项目页入口与 Agent 请求过滤足以完成发现和降噪。新增第二入口会引入导航、排序、未读和 deep link 双语义，没有额外闭环价值。

### 2.2 语音输入

当前主要场景是桌面研发协作，OS 语音输入可替代。该能力不影响 CR、Pipeline、审批或价值复盘。

### 2.3 逐条消息转发

核心业务动作是把讨论上下文合并转成执行任务；逐条转发会丢失上下文并增加目标、权限和通知语义。现有合并转发足够。

### 2.4 成员管理增强

邮件邀外部好友、解散群组和头像编辑器不是同一个需求，但都不属于当前单组织研发治理主线。外部协作未来必须先定义身份、权限和审计，不能把它伪装成一个小 UI CR。

---

## 3. 排除完整档，保留最小替代

### 3.1 work-viewer

不建设平台内 IDE：文件树、编辑器、端口预览和 Diff viewer 均继续由本地 IDE/daemon 承担。

允许的最小替代仅包括：

- 审批卡显示 changed files 数量和关键路径。
- 链接到 commit、已有 Diff 页面或本地打开动作。
- 不在平台复制文件读取、Git diff 解析和端口代理。

触发条件：非开发审批人反复反馈无法从证据摘要判断是否批准。

### 3.2 mobile

不追求 Web 三模式窗口的 RN parity。移动端候选只包含：

- pending approval 列表。
- 审批证据只读摘要和批准/驳回。
- CR 当前状态与失败通知。

触发条件：移动审批成为稳定场景，并能复用既有审批 API；否则保持不做。

## 4. 条件 backlog

### 4.1 上下文管理

原“依赖 daemon usage 回调”已经不是完整阻断理由。分档：

1. **P0**：显式“新会话继续”，保留原会话和草稿，不声称清空模型服务端记忆。
2. **P1**：按现有 task usage 估算会话用量并做阈值提示。
3. **不做**：为不同模型构造看似精确但无法验证的统一 context 百分比。

触发条件：context exhausted 或用户手动新建会话达到可观察频率。

### 4.2 回复线程

先复用 Issue comment 的 reply/thread 能力或生成引用回复，不为 Chat 新建独立消息树和 unread 模型。

触发条件：长 Discussion 中出现可复现的上下文错配、重复回答或无法定位被回复对象。

### 4.3 导出 Skill 草稿

最小档只做：选择消息和已有 tool 调用摘要 → 生成私有 Markdown 草稿 → 人工编辑。版本化转换脚本只负责确定性骨架；LLM 负责业务归纳；发布治理仍走未来独立流程。

触发条件：同类成功流程被人工复制至少 3 次，且已有 owner 愿意维护。没有复用证据时，复制消息文本足够。

### 4.4 恢复检查点

完整“文件 + 消息树 + 模型记忆”原地回滚风险高，继续排除。升级顺序：

1. 复用现有 checkpoint 查看和 resume。
2. 必要时恢复到新分支/新 worktree并启动新会话，保留历史。
3. 只有新分支恢复仍无法满足真实事故，才讨论消息截断或 session version。

禁止在 UI 功能中直接实现 `reset --hard`、账本回写或另一套 Git 恢复算法。

---

## 5. 移出永久排除

### 5.1 Pipeline 斜杠命令

入口基础已经存在，永久排除与 P2 交互设计、M2 验收和未来 Wiki/需求工坊冲突。按 Runner 依赖分档：

- Runner 前：不新增命令；现有 `/note` 和 slash Skill 保持。
- Runner 稳定后：`/进度`、`/工作流` 只读查询。
- 写命令：由路由 Agent 选择 Pipeline，调用受控 Start API；slash 只作为薄入口，不承载状态或 Git 算法。

### 5.2 点踩反馈

价值复盘不能只有耗时和 pass/fail。最小档是一位负反馈、可选文本、`task_id/message_id` 和时间；优先复用现有 Reaction 与 activity/event 入口。

只有数据证明需要分类统计时再增加少量 reason taxonomy；不从 11 类弹窗起步。

---

## 6. 防遗漏与防蔓延检查

后续 PRD 遇到本表能力时必须依次确认：

- [ ] 当前分类是维持不做、排除完整档、条件 backlog，还是移出排除。
- [ ] 触发条件已有可验证证据，不是“以后可能需要”。
- [ ] 是否先采用表中的最小替代。
- [ ] 是否复用现有 Issue/Reaction/Skill/checkpoint/approval 能力。
- [ ] 是否把状态、Git、账本和审批继续留在 `crctl`/既有边界。
- [ ] 是否明确写出完整档不做，防止 CR 扩张。

条件未满足时，记录证据缺口即可，不注册 CR。
