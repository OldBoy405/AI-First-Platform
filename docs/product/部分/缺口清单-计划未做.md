## 0. 公共架构约束

| 模块 | 应该拥有 | 不应该拥有 |
|---|---|---|
| **Agent** | 路由、职责判断、选择 Pipeline/Skill | 状态机、Git 算法、受控文件写入 |
| **Pipeline** | 节点顺序、输入传递、reviewLoop、失败中止 | 复制 Skill 完整算法、手写账本操作 |
| **Runner** | 节点调度、任务关联、等待、失败中止、幂等续跑 | 状态机/门禁解释、Git/账本写入、业务判断 |
| **Skill** | 业务判断、编排步骤、输入输出和失败语义 | 手写原子账本逻辑、重复实现 crctl |
| **crctl** | 状态、门禁、CAS、受控账本写入、审计、原子提交 | 业务设计判断、LLM 评审结论 |
| **版本化脚本** | PRD/SDD/TASK/traceability 等确定性转换 | 状态推进、人工审批 |
| **README** | 人读流程总览 | 另一份可执行细节事实源 |

**Ponytail 顺序**：复用现有能力 > 标准库 > 原生 Git/文件 API > 已有依赖 > 一行代码 > 最小新增代码。

## 3. S0-1/S0-2 — Pipeline Runner

### 3.1 业务缺口

当前 Pipeline 由 IDE Agent 与人工逐段驱动；Multica 的运行表、审批卡和投影只能展示部分节点，不能自动按 Pipeline 顺序推进。因此 Agent 驱动的 CR 交付仍未形成平台内闭环。

### 3.2 已解决基础设施

| 已有能力 | 直接复用方式 |
|---|---|
| `pipeline_run` / `pipeline_node_run` | 记录调度与恢复，不新增运行表 |
| `agent_task_queue.cr_id` / `pipeline_node_run_id` | Runner 入队时直接关联 |
| Pipeline JSON + Agent/Skill matrix | 生成只读 Go registry，不建模板服务 |
| TaskService + daemon task lifecycle | 节点执行通道 |
| 签名审批 + grant polling | human approval 等待与恢复 |
| governance projector + CR gate UI | 事件投影和展示，不重做 UI |
| `crctl` 状态/门禁/reviewLoop/checkpoint/writeback | Skill 调用，Runner 不解释或复制 |
| PG 事务/行锁 | 防重复入队，不建新事务框架 |

### 3.3 本次最小改造

#### Runner Core CR

- 扩展现有 generator，生成完整节点、owner、`reviewLoop`、`onFail` 和 source digest。
- 在 server 内增加窄 `StartRun` / `AdvanceRun` / `ResumeRuns`。
- 扩展既有内部入队参数，写 `cr_id`、`pipeline_node_run_id` 和选中 Skill。
- task/review/approval 终态统一唤醒 `AdvanceRun`。
- 仅启用 `architecture-design`，跑通 write → review block/repair → approval → approve → push。

#### Runner Main Track CR

- 在 Core 通过真实验收后启用四条 CR 主 Pipeline。
- requirement-register 产生 CR-ID 后补入现有 run context。
- 复用 code pipeline 的 TASK/test/review 和 feature writeback 深原语。
- 输出单次 run 价值摘要。

### 3.4 明确不做

- DAG、并行分支、8 条 Pipeline 一次全开、多机调度。
- 新 DSL、模板数据库、动态插件、消息总线。
- server 侧 Git/YAML/门禁解释器。
- 新 Runner 控制台；第一版 API + 现有 CR UI 足够。
- 把“选择代码评审 LLM”扩成第五种签名审批；先复用已配置评审模型。

### 3.5 核心验收

- 同一 node/attempt 并发推进只产生一个任务。
- review block 只重放 Pipeline 声明的节点，attempt 与 `review-loop.yml` 一致。
- 人工审批前停止，批准后继续，Runner 不签名、不推进状态。
- 四个故障窗口重启均能续跑且不重复入队。
- 一条真实 CR 走完四主 Pipeline 并归档，手动 Skill + `crctl` 路线仍可用。

旧的“前置全部就位”和“后端 6-8 人日”不再作为事实。量级必须在 Runner Core SDD 核实接口后重估。

## 5. 周边能力重新归位

### 5.1 审批周边

- 当前单项目审批卡、签名和 owner/admin 校验已实现。
- 当前没有“服务端动态角色策略”；`canApprove` 写死 owner/admin，CR owner 到 Multica user 的身份桥也不存在。
- 待审批中心只在出现跨项目并行待办时做只读聚合。
- 角色策略配置必须在身份桥确定后单独立项，不与审批中心或 Skill 选择器合并。

### 5.2 Skill 选择器

通用 Chat、Team Agent 和 Private Ask 已通过 `ChatInputCore` 启用 slash Skill 选择；daemon 也会注入显式选择。该项从“计划未做”移除，降级为验收/技术债：只有真实误用证明必须严格排除其他 Skill 时，才补 `skill_ids` 窄化。

### 5.3 P3 与 Wiki

不再注册“P3 组织智能 + Wiki”大包，按以下顺序拆分：

1. Runner 自带价值复盘 Lite。
2. traceability 只读视图。
3. Wiki maintain/query。
4. 私有 Skill 草稿与后续发布门禁。
5. 成熟度评分。

每项都需独立用户场景和触发证据；withdrawn 的 CR-2026-013~017 不原样恢复。

### 5.4 tools 静态治理

先执行 S0-0。基线对齐后运行现有 checker；只有仍有可复现残余时才登记窄 CR，并与其保护的 Pipeline/Runner 合同同批交付。
