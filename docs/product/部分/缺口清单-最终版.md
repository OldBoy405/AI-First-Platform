## 0. 当前结论

当前只有一个产品候选：**Runner Core 的 `architecture-design` 真实纵切**。

该候选用于验证版本化 Pipeline 自动调度是否值得继续建设，不预设通用 Runner 或四主 Pipeline 一定成立。当前代码事实只能证明完整自动推进能力不存在，不能证明 Runner 已是最大的用户问题。

- **当前候选**：Runner Core，仅覆盖 `architecture-design`。
- **条件候选**：Runner Main Track。只有 Core 的真实运行证明线性调度模型可复用后才重新立项。
- **直接复用**：Pipeline、Skill、`crctl`、任务队列、审批签名链、运行表、投影、UI 和恢复原语。
- **不随 Runner 建设**：新事务框架、模板数据库、消息总线、DAG、专用控制台、价值评分体系。
- **其他未实现项**：只有满足本文准入门槛后，才可能成为当前候选。

本文不禁止安全修复、可复现 bug、必要维护或新用户事实产生的新 CR；它们仍须走正常 CR 流程。

## 2. 判断规则

### 2.1 Ponytail 顺序

所有 PRD、SDD、TASK、实现和评审按以下顺序停止在第一个足够方案：

1. 复用现有能力。
2. 使用标准库。
3. 使用原生 Git/文件 API。
4. 使用已安装依赖。
5. 一行代码能够解决时不扩张。
6. 最小新增代码。

新表、新依赖、新协议、新服务或通用抽象，必须证明前五层不能覆盖已经出现的验收场景。“以后可能需要”不是理由。

### 2.2 实现状态与当前处置

实现事实和产品决定分开记录：

| 维度 | 可选值 | 含义 |
|---|---|---|
| **实现状态** | 已实现 / 部分实现 / 未实现 | 描述当前代码、台账和验证事实 |
| **当前处置** | 直接复用 / 当前候选 / 条件触发 / 明确不做 / 工程维护 / 未验证 | 决定下一步，不由“未实现”自动推导 |

### 2.3 未实现项准入门槛

未实现项必须同时满足以下条件，才可升级为当前候选：

1. 有已出现的用户问题或运行证据。
2. 现有能力不能覆盖该问题。
3. 能描述最小用户结果，而不只是缺少某个组件。
4. 近期依赖已经具备。
5. 有可运行的验收方式。

不满足时只能进入条件候选、明确不做、工程维护或历史来源。

## 3. 逻辑架构与权威边界

| 层 | 应该拥有 | 不应该拥有 |
|---|---|---|
| **Agent** | 路由、职责判断、选择 Pipeline/Skill；无法确定时向人提问 | 状态机、Git 算法、受控文件写入 |
| **Pipeline** | 节点顺序、输入传递、`reviewLoop`、失败中止、人工节点位置 | 复制 Skill 算法、手写账本操作、实现 Git/审批 |
| **Skill** | 业务判断、编排步骤、输入输出和失败语义；调用 `crctl`/版本化脚本 | 手写原子账本逻辑、重复实现 `crctl`、持有全局运行状态 |
| **crctl** | 状态、门禁、CAS、受控账本写入、审计、原子提交、确定性查询 | 业务设计判断、产品路线选择、LLM 评审结论 |
| **版本化脚本** | PRD/SDD/TASK/traceability 等确定性转换和校验 | 状态推进、人工审批、运行调度 |
| **README** | 人读流程总览、入口和故障处理索引 | 另一份可执行细节事实源 |

权威关系：

```text
用户请求
  -> 路由 Agent 选择 Pipeline/Skill
  -> Pipeline JSON 声明节点顺序与 reviewLoop
  -> Skill 执行业务步骤并调用 crctl/版本化脚本
  -> crctl 写入 Git 权威状态与证据
  -> daemon 上报事件
  -> Multica 投影运行状态与 UI
```

- CR 业务状态以 Git 中受控文件为权威，`crctl` 是唯一合法写入器。
- Pipeline 顺序以 `../tools/pipeline-templates/*.pipeline.json` 为权威。
- Skill 责任归属以 `../tools/agent-skill-matrix.yml` 为权威。
- 状态机和门禁以 `../tools/dir-graph.yaml#change-request-track.state_machine` 与 `../tools/skills/shared/crctl/gates.json` 为权威。
- `pipeline_run` / `pipeline_node_run` 是调度状态和读模型，不反向定义 CR 状态。
- README 与本文均不得复制另一份可执行合同。

| 能力 | 实现状态 | Runner Core 使用规则 |

## 5. 当前候选：Runner Core

### 5.1 候选目的

验证一条已通过需求审批的真实 CR，能否按现有 `architecture-design` Pipeline 自动执行技术设计、评审回修、人工审批收口和 checkpoint，而不要求用户逐节点复制命令或判断下一步。

这是战略候选，不是“最大产品缺口”已被证明的结论。Core 验收后仍可能得出“不继续扩为通用 Runner”的结果。

### 5.2 最小支持面

Core 只支持当前 `architecture-design` 的五个节点：

```text
write-tech-design
→ review-tech-design / write-tech-design 回修
→ human_approval
→ approve-tech-design
→ push-progress
```

Core 只拥有运行生命周期、节点调度、任务关联、等待审批、失败中止和幂等续跑。它不拥有业务判断、状态机、门禁、Git、账本、审批签名、评审结论或 review attempt 计数。

前置治理修复：

1. 从当前 tools 重新生成 Multica gate/review 节点，消除旧 UUID 漂移。
2. 在 tools 的 requirement/architecture Pipeline 中补齐显式 `replayNodes`，让回放顺序归 Pipeline 权威；Runner 不根据 `repairNodeId` 猜测后续节点。
3. Core 的执行 registry 只包含 `architecture-design`；不提前生成其他三条主 Pipeline 的执行合同。

### 5.3 最小运行语义

- 路由 Agent 选择 `architecture-design`，Runner 只接受受支持的固定 registry 条目。
- Runner 复用 projector 已创建或可创建的同一非终态 `pipeline_run`，不得创建平行 run。
- Skill 节点通过现有 TaskService 执行，并关联 CR、run、node 和 attempt 投影。
- review block 只按 Pipeline 的显式 `replayNodes` 回修；attempt 及耗尽结论来自 `crctl` 权威结果。
- `human_approval` 不创建 Agent task。
- 人类在网页批准后，server 生成签名 grant；daemon 投递并 ACK；Runner 再调度现有 `approve-tech-design` Skill；该 Skill 调用 `crctl approve --grant` 推进状态。
- Runner 观察 task/CR/review/approval 的结构化结果继续或中止，不解析自然语言，不补造证据。
- run 保存启动模板 digest；恢复时若当前 registry digest 不一致，明确阻断并转人工处理，不加载或猜测旧模板。
- 重复 task、review、approval 或恢复唤醒不得产生重复执行。

具体 API、函数名、锁、upsert、扫描频率、事件接线和数据库语句由注册后的 SDD 基于真实代码决定，本文不预设。

### 5.4 结果级验收

1. 从真实 `requirement-approved` CR 启动后，完成完整 architecture 流程并形成现有权威证据。
2. review block 后只执行 Pipeline 声明的回修链，最终 pass 或以权威耗尽结果停止。
3. 人工审批前不执行后继 Skill；网页审批后仍由签名 grant、Skill 和 `crctl` 完成状态推进。
4. task 终态重复通知或服务重启不会重复入队或重复推进。
5. 模板 digest 漂移时明确阻断，不用当前模板静默续跑旧 run。
6. Runner 不直接写受控账本、不执行 Git、不实现通用 passCondition 解释器。
7. 关闭 Runner 后，手动 Skill + `crctl next` 路线回归通过。

### 5.5 明确不做

Core 不实现：

- `onFail=skip`、`code_generation` 或 architecture 未使用的节点语义；
- requirement 注册后补 CR-ID、code、test、writeback 或四主 Pipeline 串联；
- 通用工作流引擎、DAG、并行分支、插件或表达式解释器；
- 新运行表、幂等表、模板数据库、消息总线或第二事务框架；
- 多版本模板恢复；
- Runner 专用前端控制台；
- 价值复盘 API、统计表、组织排名或成熟度评分。

## 6. 条件候选

| 候选 | 当前实现状态 | 触发证据 | 最小档 |
|---|---|---|---|
| Runner Main Track | 未实现 | Core 真实运行证明相同线性调度语义可复用于其他 Pipeline | 逐条评估 requirement、code、writeback，不预设一次全开 |
| 单次运行价值摘要 | 部分实现 | 至少 3 条真实 run 后，现有数据仍不足以回答耗时、失败点和审批等待 | 先做确定性查询或临时报告，不建统计表 |
| 待审批聚合 | 未实现 | 至少 2 个跨项目 pending，或审批人出现可复现漏办 | 只读列表/计数并跳回现有审批卡 |
| CR owner 审批角色策略 | 未实现 | 当前 owner/admin 策略出现真实授权不足 | 先定义稳定身份映射，再收紧 `canApprove`；身份桥不独立立项 |
| Wiki maintain/query | 未实现 | 有明确 owner、维护频率和稳定检索需求 | `docs/product/Wiki子系统设计.md` 仅作候选设计输入，不是实施授权 |
| tools 包批量安装体验 | 部分实现 | 全新 workspace 使用现有 Agent/Skill 导入能力无法完成受支持安装 | 先补版本化批处理脚本，复用现有导入 API/CLI |
| 跨 CR traceability 只读查询 | 部分实现 | 真实运行形成稳定的跨 CR 查询需求 | 只读查询，不做评分或新权威域 |
| timeline 分页 | 未实现 | 消息量逼近现有硬帽并出现加载问题 | 增加游标/分页，不重写消息模型 |
| 多 worktree 并行 | 未实现 | per-project 串行形成可测瓶颈 | 独立 DevOps 议题，不进入 Runner Core |

未列入本表的远期微功能不具备当前决策资格；需要时从历史来源重新核实，而不是默认恢复旧范围。

## 7. 明确不做

在没有新用户事实前，不建设以下完整形态：

- 新 Pipeline DSL、模板数据库、动态插件、消息总线、DAG 和多机调度池；
- Runner 专用控制台、完整 work-viewer 或平台内 IDE；
- 文件、消息树和模型记忆的原地三态回滚；
- 跨模型统一精确 context 百分比；
- Web 产品的 mobile 全量 parity；
- 项目/消息双入口和逐条讨论消息转发；
- 组织成熟度排名、预测和无数据基础的大分类反馈体系；
- 私有 Skill Market、独立图数据库或 Wiki 与组织智能的一体化大包。

出现新事实时，先修订本决策入口，再注册 CR。
