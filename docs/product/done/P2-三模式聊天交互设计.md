## 0. 一句话结论

三模式（Team Agent / Private Ask / Discussion）不是三个页面，是**同一个项目群聊窗口内的三个 tab**，共享成员/文件/上下文，但**队列模型、写权限、可见性、实时通道各不相同**。CodeBanana 已经把交互打磨好了，字典是现成的功能清单；我们的增量是把它接到 Multica 的 issue/task/WS 基础设施 + tools 的 CR 门禁上，并把原产品「云端执行」的隐含前提改成「daemon 本地执行」。

## 1. 窗口骨架（三模式共用）

```
┌ chatHeader ─────────────────────────────────────────────────┐
│ 项目头像/名  · {count}位成员 · 当前主持人 · [成员][技能][定时任务][Agent配置][设置] │
├ 模式切换条 ─────────────────────────────────────────────────┤
│ ● Team Agent   ○ Private Ask   ○ Discussion   (chatControlPanel 教程气泡) │
├ 消息流区（随模式切换内容与语义）────────────────────────────┤
│  … 消息气泡 / 工具执行卡 / 系统通知条 / 队列指示 …            │
├ 输入区（随模式切换能力）────────────────────────────────────┤
│ [附件][@提及][技能][模型选择器][Ask▾/Coding▾]  ⌨ 输入框   [发送/停止] │
└─────────────────────────────────────────────────────────────┘
右侧可开抽屉：成员列表 / Agent配置(基本信息·IM设置·技能·定时任务) / 权限申请 / 搜索
```

字典锚点：`shadowchat.chatHeader`（头部 8 个工具按钮 + 搜索 + 会话记录 + 项目设置）、`shadowchat.chatControlPanel.tutorialMultiModeDescription`=「点击在协作 Agent、私有 Agent 和团队讨论之间切换」。

**模式切换是纯前端 tab 切换**，不重新拉数据（三模式的消息流各自用独立 query key 缓存）。切换时保留各自的输入框草稿（Zustand，按 `{projectId}:{mode}` 命名空间）。

## 2. 三模式对照（交互契约核心表）

| 维度 | Team Agent | Private Ask | Discussion |
|---|---|---|---|
| 定位 | 共享 AI 执行层，改项目 | 个人只读探索，不改项目 | 人类沟通层，不执行 |
| 谁能驱动 Agent | **单一写者**：Owner+Admin 默认，其余申请 presenter | 人人可用（各自独立） | 无 Agent 驱动（DC 除外） |
| 队列 | 项目级共享 FIFO，默认 50 槽（可配置，owner/admin 可插队不受限），全员可见 | 用户级独立队列，互不可见 | 无队列 |
| 消息可见性 | 全项目成员 | 仅本人 | 全项目成员 |
| 后端映射(P0) | `agent_task_queue`(cr_id/issue_id) | `chat_session`+`chat_message`(沙箱) | `comment`(挂 Issue) |
| 实时通道 | WS `workspace:{id}`+`task:{id}` | WS `chat:{sessionId}`(仅本人) | WS `workspace:{id}` |
| 写权限(execenv) | Coding 可写 worktree | Ask-only 只读 | 不进 execenv |
| 停止权限 | 发送者停自己 + Owner 停全部 | 仅停自己 | — |
| 计费归属 | 项目 Owner / Presenter(可配) | 按项目上下文 | — |

字典锚点：`shadowchat.forward` 里三模式并列（`teamAgent`/`myAgent`=Private Ask/`discussion`）；`chat.heyTeamAgent`/`heyPrivateAsk`/`heyDiscussion` 三条空状态问候语确认这是三个独立会话面。

## 3. Team Agent —— 单一写者 + 共享队列（最复杂）

### 3.1 控制权状态机（presenter）

字典 `shadowchat` 顶层已给出全部 6 个通知文案，直接定义了状态机的事件：

| 事件文案(键) | 触发 | 后端动作 |
|---|---|---|
| `permissionRequestSentToOwner` | 成员点「请求 Agent 访问权限」 | 建 presenter 申请 → Owner 收件箱 |
| `youGotPermissionToControlAgent` | Owner 批准 | 当前 presenter = 该成员 |
| `youReceivedPermissionFromAnotherMember` / `youTransferredPermissionToAnotherMember` | 转让 | presenter 易主 |
| `permissionHasBeenRevoked` / `yourPresenterRequestHasBeenRejected` | 撤销/拒绝 | presenter 释放/维持 |
| `permissionHasBeenReleased` | 主动释放 | presenter = null，回到 Owner+Admin 默认 |

**关键复用（P0 已论证）**：presenter 的"同一时刻仅一人驱动"直接落在 Multica 的 claim SQL 上——把串行化键从 `agent_id` 换成 **`project_id`**，`NOT EXISTS(active task on same project)` 天然保证单写者，无需额外锁。Admin 在 Agent 空闲时可直接接管（不必逐次审批），映射为"claim 前检查 presenter==null || caller∈{owner,admin}"。

字典锚点：`shadowchat.chatControlPanel`（Agent 访问权限面板：Owner 标记、成员列表、请求按钮）、`shadowchat.presenterRequestNotification`（申请/批准/拒绝卡片）、`chatHeader.currentPresenter`=「当前主持人」显示在头部。

### 3.2 共享队列指示

字典 `chat.taskQueue`：`queuingTip`=「请求排队中」、`queueCount`=「{count} 条排队」、`removeTask`=「清除对话」、`taskFallback`=「任务 #{id}」、`fromUser`=「（来自 {name}）」。

交互：队列条常驻消息流顶部或输入区上方，显示 `{count} 条排队`；每条排队项显示发起人（`fromUser`），发起人可「清除对话」撤回自己的排队项（释放槽位、后续前移）。满默认 50 槽（可按 project/org 配置）时，非 owner/admin 的输入区禁用并提示「Agent 忙，请稍后」；owner/admin 不受此限制，可正常插队优先执行（详见 §11 D1）。全员可见排队数——这是 Team Agent 与 Private Ask 的关键区别。

后端：`agent_task_queue` 的既有 claim/queue 语义（P0 §2.2 已加 `cr_id`+`pipeline_node_run_id`）。队列可见性经 WS `task:{id}` 广播到 `workspace:{id}` 房间。

### 3.3 Agent 执行过程呈现：toolExecutionCard

字典 `shadowchat.toolExecutionCard` 给了完整状态机：

- **status**：`running`（运行中）/ `done`（已完成）/ `error`（错误）/ `interrupted`（已中断）/ `unknown`
- **messages**：`toolIsStillRunning`、`failedWithNoOutput`、`toolExecutionInterrupted`、`completedWithNoOutput`、`resultUnavailable`=「结果不可用（可能被中断或超时）」、`clickToOpen`、`unknownTool`
- **time**：毫秒/秒计时 + 状态标签
- **counts**：域数 / 条数 / 结果数（多结果折叠计数）

交互：Agent 每调一个工具渲染一张可折叠卡片，头部 = 工具名 + 状态徽标 + 耗时，展开看输入/输出。**这正好接 Multica `pkg/agent` 的统一 Message 流**（text/thinking/tool-use/tool-result/status/error 六类），子进程 NDJSON → WS → 卡片，一一对应。`interrupted` 状态对接停止操作与 P1 的任务中断。

### 3.4 停止

字典 `chat.agentGenerating`=「Agent 回复中」+ 输入区「发送」变「停止」。权限：发送者停自己（运行中或排队中）、Owner 停任意。停止后已生成内容保留、槽位立即释放、下一条自动开始——与 Multica 的 stop 语义完全一致（P0 已确认），直接复用。

### 3.5 与 CR 门禁的接合（本平台独有增量）

当 Team Agent 的任务属于某条 pipeline 节点（`agent_task_queue.pipeline_node_run_id` 非空），消息流额外插入**门禁状态条**：
- 到达 `human_approval` 节点 → 渲染审批卡片（不是 TTY，走 P1 §B 的服务端签名审批），有权限者见「批准/驳回」，驳回填 `reject_reason` → 注入 review_feedback 回修复节点。
- review 节点出 `verdict=block` → 消息流显示 blocker 列表 + 自动进入 reviewLoop（attempt N/3）。
- 状态推进（`[cr] status X→Y`）经 P1 §A 同步 worker 投影后，头部显示 CR 当前 16 态徽标。

## 4. Private Ask —— 个人沙箱

字典 `chat.heyPrivateAsk`=「嘿，我是私有问答 Agent！」。`shadowchat.forward.myAgent`=「Private Ask」（内部键仍叫 myAgent，是旧名 My Agent 的遗留，UI 展示统一用 Private Ask）。

交互与 Team Agent 同构，但四处不同：① 队列是**个人独立**的（`queueCount` 只算自己的消息，其他人不可见）；② 默认 Ask-only 只读，execenv 不给写权限；③ 消息仅本人可见（WS `chat:{sessionId}` 只推本人）；④ 可与 Team Agent 会话**并行**——用户可以一边等 Team Agent 跑，一边在 Private Ask 里问问题。

后端：Multica `chat_session` + `chat_message`，本来就是"完全沙箱化（Agent 看不到 Issue）+ provider 会话恢复保持多轮上下文"，语义现成。

## 5. Discussion —— 人类沟通 + DC 协调者

字典 `chat.heyDiscussion`=「嘿，欢迎来讨论！」、`subDiscussion`=「发送消息开始讨论。」

交互：纯人类多人聊天，无队列、无 Agent 驱动。全员自由发言，消息进项目上下文。后端映射为挂在 CR 壳 Issue（或项目根 Issue）上的 `comment` 流——直接复用 Multica 的评论 + @提及 + reaction + 订阅基础设施。

### 5.1 DC（Discussion Coordinator）激活

字典 `shadowchat` 有 `discussion` 键 + `assignAgentTooltip`。DC 默认静默，两种激活：@提及 DC，或回复 DC 的 Discussion 消息。DC **只协调不执行**（总结/追踪/路由到执行 Agent），映射为一个特殊 Agent：它可以 `EnqueueTaskForMention` 到 Team Agent（经 A2A），但自身 execenv 权限为只读、且 forbidden 一切写 Skill。

### 5.2 讨论转执行

字典 `shadowchat.mergedForwardMessage`：`triggerMessage`=「触发讨论的消息」、`chatHistory`=「聊天记录汇总」、`messagesInConversation`=「对话中的 {count} 条消息」。

交互：选中若干 Discussion 消息 → 合并转发到 Team Agent，作为一个带上下文的任务。这实现了 CodeBanana 的核心理念「沟通发生在执行发生的地方」——讨论可被直接转化为执行。后端：合并消息 → 生成 Team Agent 任务的 prompt 上下文；若尚无 CR，可触发 `requirement-register` 把讨论升级为 CR（对接 P0 的 Issue→CR 升级路径）。

## 6. 输入区（三模式差异化能力）

| 控件 | Team Agent | Private Ask | Discussion | 字典锚点 |
|---|---|---|---|---|
| 附件（文件/图片/截图） | ✓ | ✓ | ✓ | `chat.folder/image/video/audio/file` |
| @提及（成员/Agent/文件树） | ✓ | ✓成员 | ✓成员 | changelog 提到 @提及支持文件树 |
| 技能选择器 | ✓ | ✓ | ✗ | `chatHeader.tooltipSkills` |
| 模型选择器 | ✓ | ✓ | ✗ | `models`（Auto+多供应商，本地执行时=本机 CLI 可用模型） |
| Ask/Coding 切换 | ✓ | 固定 Ask | ✗ | `codingAgent`（Coding=写 worktree） |
| 斜杠命令（Pipeline 入口） | ✓ | ✓（只读类） | ✗ | —（本平台增量，见 §6.1） |
| 发送/停止 | ✓ | ✓ | 仅发送 | `chat.agentGenerating` |

### 6.1 斜杠命令：高频动作的全员入口（2026-07-29 增补，S4）

对齐资源四分类（Skill=稳定做法、Agent=角色任务、MCP=外部连接、**Command=高频入口**）中此前缺位的 Command 层：输入框键入 `/` 唤起命令面板，命令映射到既有 Pipeline 触发 API 与查询端点，**不新增执行通路**：

| 命令 | 映射 | 可用模式 |
|---|---|---|
| `/需求 <一句话>` | 触发 `requirement-authoring` pipeline（收集目标→建 CR） | Team Agent |
| `/评审摘要 <CR-ID>` | quality-reviewer 只读生成风险摘要 | Team Agent / Private Ask |
| `/进度 [spec\|CR]` | spec-query 查询（P2.5 轻量档承载） | Team Agent / Private Ask |
| `/工作流` | 列出当前项目可触发的 8 条 pipeline | Team Agent |

命令注册走"托管元数据 + 文件物化"同一双层模型（命令定义文件随 tools 包分发，服务端存元数据与权限）；权限沿用各模式既有约束（如 `/需求` 在 Team Agent 内受 presenter 控制）。价值：非技术角色不必学会"跟 Agent 怎么说"，高频动作一键可达——AI 内嵌在工作场景里，而不是工作之外再挂一个聊天入口。

**本地执行路线的差异**：模型选择器列出的是**该用户 daemon 上已注册 Runtime 的模型**（daemon 检测本机 Claude Code/Codex/... 的可用模型上报），不是云端 30 模型全集。Auto 模式在本地可用集内选。无可用 Runtime 时输入区提示「请先在设置中启动本地 Agent」并给 `multica setup` 引导——这是本地路线对非技术角色的主要摩擦点（P0 已列为代价，缓解方案是共享 runner 池）。

## 7. 通用消息能力（三模式共享）

- **消息操作**（`shadowchat.messageActions`）：回复 / 复制 / 转发 / 恢复检查点。Agent 生成中时恢复禁用（`restoreDisabled`=「Agent 生成中，无法恢复」）。
- **导出为 Skill 草稿**（2026-07-29 增补，S2，仅 Team Agent）：多选一段"打得漂亮"的会话（含 toolExecutionCard 工具调用序列）→ 「导出为 Skill 草稿」→ 生成 SKILL.md 草稿（对话意图 → 指令、工具序列 → 步骤、涉及文件 → 依赖上下文）落入发起人**私有技能库**，人工修订后走 P3 §3 的正常发布流程。这是"经验传递最小单位从一段话变成可执行资产"的落地入口——过程记录（消息流本来就有）到资产沉淀（Skill Market）之间此前缺的那一跳。导出动作即视为本人对该段工作过程的资产化授权；草稿默认私有，发布到组织另经 P3 发布门禁（含敏感扫描）。
- **恢复检查点**（`shadowchat.restoreCheckpoint`）：「恢复到此检查点？将丢弃此后所有内容：Agent 做出的所有文件更改 + 此节点之后的所有对话消息。⚠️ 此操作无法撤销。」——**这是三态回滚，对接上一轮讨论的 Restore**：文件（worktree git 快照）+ 会话（消息树截断）+ 模型记忆（session 版本）。P1 的 crctl CAS + merge 补偿事务语义为其提供骨架；本地执行下文件回滚 = daemon 对 worktree 做 `git` 快照恢复（经 controlled-shell 白名单，`revert`/`checkout` 已在白名单内）。
- **清空上下文**（`shadowchat.contextUsageModal`）：显示当前上下文用量 + 模型，清空后后续消息在全新会话继续；需要 Agent 使用权限（`noPermissionToClear`）——对接 presenter 权限。
- **转发**（`shadowchat.forward`）：转发目标区分组织成员/跨组织好友/虚拟成员/群聊；Team Agent 消息只能转发给有 Agent 访问权的目的地（`forwardMessageTo` 有限制），Private Ask/Discussion 无限制。
- **点赞/点踩 + 反馈**（`DislikeReason`）：11 类点踩原因（不应使用记忆/不喜欢风格/事实不正确/没遵循指示/不该拒绝/懒惰/不安全/有偏见/其他…）+ 可选详情。反馈可对接 Agent 质量度量。
- **重新生成**（`messages.regenerationFailed` 等）：失败重试。
- **敏感内容拦截**（`messages.sensitiveContentBlocked`）：内容安全护栏文案。
- **系统消息**（`chat.memberInvited/memberLeft/memberRemoved/groupAvatarChanged/forwardedMessages`）：成员变更/转发的行内系统条。

## 8. 成员与项目管理（chatHeader 抽屉）

字典 `groupChat.*` + `shadowchat.addMemberModal/inviteGroupModal/memberListSidebar/friendInvite`：
- 加成员：组织成员直接加（无通知） / 邮件邀请外部好友（不入组织，仅访问该项目）。
- 成员管理（Owner）：移除成员、解散群组（不可逆，且「不能解散最后一个含 AI 助手的群聊」）。
- Admin：最多 5 名，Owner 从成员面板任命。
- 项目设置：头像（自定义文字/上传图片/缩放旋转）、项目名、置顶、免打扰（Team Agent / Discussion 分别可静音）。

后端全部落在 Multica 的 `member`/`issue_subscriber`/`project`——单组织下逻辑比 CodeBanana 的跨组织可见性简单得多（P0 已定单组织）。

## 9. 前后端契约要点（给实现的清单）

1. **一个项目 = 一个 Multica project + 一个专属 agent + 三个消息面**（Team Agent→task_queue、Private Ask→chat_session、Discussion→comment）。三面共享 project 成员与 project_resource（worktree/repo）。
2. **模式切换纯前端**，三面独立 query key，输入草稿按 `{projectId}:{mode}` 存 Zustand。
3. **WS 房间分级**（复用 Multica 作用域房间）：Team Agent/Discussion 走 `workspace:{id}`（全员）+ `task:{id}`（订阅）；Private Ask 走 `chat:{sessionId}`（SendToUser，永不进工作区广播）。
4. **presenter 控制权 = claim SQL 串行化键换 project_id**，6 个通知文案已定义全部状态转移。
5. **toolExecutionCard 直接消费 pkg/agent 的六类 Message 流**，NDJSON→WS→卡片。
6. **门禁接合**：pipeline 任务在消息流内渲染审批卡（服务端签名审批，非 TTY）+ blocker 列表 + reviewLoop attempt + CR 16 态徽标。
7. **模型列表来自 daemon 上报的本机 Runtime**，非云端全集；无 Runtime 时引导 `multica setup`。
8. **恢复检查点 = 文件(worktree git 快照)+会话(消息树截断)+记忆(session 版本)三态**，走 controlled-shell 白名单内的 git 操作。

## 10. 与原产品的取舍（本地执行路线导致的四处偏离）

| CodeBanana 原样 | 本平台(本地执行) | 原因 |
|---|---|---|
| 云端沙箱即时预览，任何角色可跑 Agent | 需本机 daemon + CLI；非技术角色靠共享 runner 池缓解 | 本地执行路线（P0 已论证的主要代价） |
| 模型选择器 = 平台托管 30 模型 | = 用户本机 CLI 可用模型 | 平台不碰模型 API Key |
| 计费模式（Owner/Presenter 计 Token） | 保留 UI 但 Token 统计来自 daemon usage 回调，不涉及付费 | 内部工具无计费 |
| 审批在云端 UI 点一下即推进 | 服务端签名 grant → daemon → crctl 验签 | P1 的门禁强度要求（防模型伪造审批） |

字典里 `billingModeModal`/`teamSeats`/`credits`/`usage` 等计费命名空间在内部版**降级为用量展示**，不接支付。

## 11. 交付切分与验收
