# 独立评审与人工审批命令闭环设计

> 状态：设计草案  
> 版本：v0.4  
> 更新日期：2026-08-27  
> 触发事件：CR-2026-052 在 PRD 完成后发生作者自评逃逸；CR-2026-051/052 因 `cr.shell_issue_id=NULL` 无法在 Multica 项目会话中显示审批卡  
> 文档性质：平台级最小改造设计，不是实施授权；本轮只收敛设计，后续实现仍须通过同一个 CR 完成 PRD、SDD、TASK、开发、评审与人工审批

## 1. 结论与范围

本设计只修复两个已经确认的缺口：

1. **独立评审路由缺口**：四个 CR 评审 Skill 的 owner 与实际路由不一致，作者 Agent 可以在同一运行中完成“写 + 评”。
2. **审批卡可见性缺口**：Multica 已有完整人工审批协议，但真实 CR 没有稳定写入既有 `cr.shell_issue_id`，且前端错误地把 `gate_nodes` 当成当前审批卡的存在前提。

采用一个 CR、两条独立工作轨：

```text
Track A：调整 tools 的 owner、Agent 路由、Pipeline 委派合同和 review Skill 前置步骤
Track B：复用 Multica task token 与 task→Issue 上下文绑定 CR，并按 pending_stage 显示唯一审批卡
```

两条工作轨共享的只有 CR-ID 和现有执行环境，不建设共同的新框架。目标闭环为：

```text
作者 Agent 产出阶段内容
→ Pipeline 到达 review-* 节点
→ 新建 quality-reviewer-agent 独立任务
→ review Skill 先将当前 Multica task 绑定到 CR/Issue
→ review Skill 作业务判断
→ crctl review-record 原子记录评审证据
→ Pipeline 按现有 reviewLoop 回修或进入 human_approval
→ crctl/Multica 状态投影得到 pending_stage
→ 项目会话显示唯一 ApprovalCard
→ 人类批准或驳回
→ 现有 Ed25519 grant 经 daemon 投递
→ crctl approve 复核门禁并推进状态
```

本设计不创建第二套评审凭证、来源证明、审批主体、状态机或事务框架。

## 2. 已有能力：直接复用，不重复建设

### 2.1 tools 已有能力

#### `crctl review-record`

现有 `crctl review-record` 已负责：

- 校验评审 payload schema；
- 计算并校验 subject digest；
- 管理 review attempt 与 review loop；
- 写 canonical annotation；
- 投影 traceability；
- 写审计/outbox；
- 通过 CAS 和 durable transaction 保证多文件一致性。

因此 review Skill 继续只负责业务判断和调用 `review-record`。本设计不新增 `crctl review`、`artifact-record`、provenance 账本或另一套评审落盘命令。

#### `crctl approve`

现有 `crctl approve` 已统一支持：

- 人类交互式终端审批；
- Multica Web/Desktop 签发的 Ed25519 grant；
- 审批前门禁重验；
- evidence freshness；
- CAS；
- 审批账本和状态原子推进；
- 审计与 outbox。

因此人工审批协议保持不变。Agent 只能说明当前等待审批，不能代替人类批准，也不能把 shell 命令包装成新的产品审批入口。

#### Pipeline

现有 CR Pipeline 已拥有：

- 节点顺序；
- 输入传递；
- `reviewLoop`；
- blocker 回修；
- 技术失败中止；
- `human_approval → approve-*` 顺序。

本设计不修改 Pipeline schema、不引入新 Runner，也不把 review loop 搬到独立评审入口或 Agent prompt。

### 2.2 Multica 已有能力

Multica 已有：

- `agent_task_queue.issue_id`、`project_id`、`cr_id`；
- task 对应 Agent、workspace、Issue 和 Project 的持久化上下文；
- task claim 时签发的 `mat_` task-scoped token；
- 认证中间件从 token 权威恢复并覆盖请求头中的 `user_id`、`agent_id`、`task_id`、`workspace_id`；
- `TaskService.AttributeTaskToCR` 与 `SetTaskCRAttributionIfValid`；
- `cr.shell_issue_id` 既有列；
- `/api/projects/{id}/gates`；
- `pending_stage`、`can_approve`、evidence、`pending_advance` 和 `gate_nodes`；
- Web/Desktop `ApprovalCard`；
- 现有批准/驳回 API、grant 签发、daemon 投递与 ACK；
- `activity_log` 和 `cr:updated`/项目刷新事件。

本设计只补齐这些既有能力之间的两个断点，不新建 Approval Read Model、Registration Origin Adapter 或 reconcile 子系统。

## 3. 已确认的两个缺口

### 3.1 缺口 A：作者可以直接执行评审

当前事实为：

- `quality-reviewer-agent.md` 已路由需求、技术设计、开发计划和代码评审；
- `agent-skill-matrix.yml` 仍把相关 review Skill 的 `owns` 放在作者型 Agent；
- `requirement-writer.md` 和 `dev-agent.md` 仍把评审写成当前 Agent 可直接执行的意图；
- Pipeline 节点只写“调用 review-*”，没有明确要求创建新的 quality reviewer 任务；
- matrix 是声明性治理，不是调用级运行时拦截器。

因此，annotation 存在、`verdict=pass` 和 `blockers=[]` 只能证明评审证据形状满足门禁，不能证明作者与 reviewer 是两个独立运行。CR-2026-052 的直接根因是 owner 和路由合同错误，不是 `review-record` 缺少另一套事务或签名协议。

### 3.2 缺口 B：CR 没有进入项目审批读路径

当前项目 gates 查询通过以下关系限定项目 CR：

```text
cr.shell_issue_id → issue.project_id
```

真实注册流程没有稳定填充 `cr.shell_issue_id`。CR-2026-051/052 的该字段为 `NULL`，所以即使 CR 已进入审批状态，也会在 gates 查询阶段被过滤。

当前已有的 `StartTask → AttributeTaskToCR` 只更新 `agent_task_queue.cr_id`，且 `cr_id` 来自 daemon 根据任务起始分支名的 best-effort 自报。首次 requirement task 可能早于 CR 注册，不能依靠该时点完成 CR→Issue 绑定。

前端还有第二个断点：`ProjectTeamAgentChat` 只遍历 `cr.gate_nodes` 创建 `CrGateCard`。即使服务端已经根据 `cr.status` 返回非空 `pending_stage`，只要没有当前 `human_approval/running` node，审批卡仍不会显示。这违反“当前状态足以决定当前审批卡，节点只提供历史和 blocker 增强”的既有设计原则。

## 4. 责任边界

|---|---|---|
| Agent | 意图路由、职责判断、选择 Pipeline/Skill、把评审委派给唯一 review owner | 状态算法、账本写入、绑定 SQL、人工审批 |
| Pipeline | 节点顺序、输入流、`reviewLoop`、失败中止、要求独立 reviewer 运行 | 身份签名、API 细节、评审业务判断、绑定事务 |
| Skill | 评审业务判断、调用 task binding、准备临时 payload、调用 `review-record`、传播失败 | 直接写 canonical 账本、复制 `crctl`、修改 Multica 数据库 |
| `crctl` | 状态、门禁、CAS、受控账本、digest、attempt、审计、原子提交 | Agent 调度、LLM 评审判断、Multica API/数据库 |
| 版本化脚本 | PRD/SDD/TASK/traceability 的确定性转换 | 状态推进、审批、Agent 调度 |
| README | 人读入口、流程概览和兼容边界 | 第二份状态机、协议或实现细节事实源 |
| Multica Task Service | 校验 task token 上下文，原子绑定 task→CR→Issue，记录平台审计 | CR 状态推进、评审判断、模糊猜测关联 |
| Multica gates/UI | 根据既有 `pending_stage` 展示唯一当前卡片，保留节点历史 | 新审批协议、直接修改 CR 状态 |

## 5. Track A：独立评审最小改造

### 5.1 适用范围

只覆盖与 CR 审批门禁直接相关的四个 Skill：

- `review-requirement`
- `review-tech-design`
- `review-dev-plan`
- `review-code`

`review-planning-report` 与 `review-alignment` 保持现状，不在本 CR 顺带调整。

### 5.2 owner 与兼容关系

`agent-skill-matrix.yml` 调整为：

- 四个 review Skill 的唯一 `owns` 为 `quality-reviewer-agent`；
- `requirement-writer` 和 `dev-agent` 不再 `owns` 这些 review Skill；
- Pipeline owner 保留对相应 review Skill 的 `can-call`。

保留 `can-call` 是兼容要求，不代表允许作者在当前运行中自评：

1. `emit-registry.mjs` 当前要求 Pipeline owner 对每个节点具有 `owns|can-call`；
2. `check-agents-contract.mjs` 当前要求 Agent 正文引用的 active Skill 出现在 `owns|can-call|external`；
3. pi、Claude 等运行时仍需要加载并执行现有 Pipeline；
4. matrix 当前没有调用级运行时拦截能力。

本设计不新增 `can-delegate` 关系，也不修改 matrix parser。实际独立性由“唯一 owner + Agent 路由 + Pipeline 委派合同 + 结构测试”共同约束。

### 5.3 Agent 路由合同

`requirement-writer` 和 `dev-agent` 的评审意图改为：

```text
读取 crctl next / 当前 Pipeline review 节点
→ 创建新的 quality-reviewer-agent 任务
→ 只传 CR-ID、权威 workspace 和该 review Skill 已声明的输入
→ 等待结构化评审结果
→ 作者 Agent 只消费 blocker 并执行回修，不代替 reviewer 判断
```

独立入口“独立评审 `<CR-ID>`”也遵守相同合同：路由 Agent 先调用 `crctl next` 确认当前合法 review Skill，再委派给 `quality-reviewer-agent`。不新增 `crctl review` 包装命令。

一次独立调用只完成一次评审。重复回修和重评仍归 Pipeline `reviewLoop`。

### 5.4 Pipeline 合同

三条 CR Pipeline 保持 schema、节点顺序和 `reviewLoop` 不变，只修改四个 review 节点的 prompt：

- reviewer 必须是新建的 `quality-reviewer-agent` task/run；
- 不得恢复作者会话执行评审；
- 每轮 review loop 都是一次新的 reviewer 执行；
- 技术失败按现有 `onFail=abort` 中止；
- 业务 `verdict=block` 继续按既有 `reviewLoop` 返回 writer/implementation 节点；
- Pipeline 不内嵌 task binding API、SQL、评审维度或 `crctl` 落盘算法。

### 5.5 不支持子 Agent 的运行时

如果目标 IDE/runtime 不能从作者会话创建独立 subagent：

1. Pipeline 停在当前 review 节点；
2. 不得退化为作者直接评审；
3. 提示用户另开独立会话，以 `quality-reviewer-agent` 身份运行同一个 review Skill；
4. canonical review 结果完成后，原 Pipeline 再继续。

这会多一次人工启动，但不会改变状态机或破坏 CR 数据。pi、Claude 等支持独立任务的运行时可直接完成委派。

### 5.6 诚实边界

本工作轨提供组织性强制，不提供密码学运行身份证明：

- `crctl` 不新增 run attestation 校验；
- 旧 PASS 不自动作废；
- 不伪造或回填历史 reviewer 身份；
- tools 仍无法在调用级机械阻止一个故意绕过 prompt 的模型直接执行 review Skill；
- 若未来出现结构约束仍无法控制的真实逃逸，再独立设计运行身份和调用拦截层。

## 6. Track B：CR→Issue 绑定与审批卡可见性

### 6.1 绑定时机

四个 review Skill 在写临时评审 payload、调用 `crctl review-record` 之前增加同一个平台前置步骤：

```text
若当前运行具有 Multica task-scoped context：
  调用 bind-current-task-to-cr(CR-ID)
  成功后继续 review-record
  失败则按技术失败中止，不写 canonical review
否则：
  视为普通本地/非 Multica 执行，保持现有 review-record 行为
```

绑定放在 review Skill，而不是 Agent 或 Pipeline：Skill 拥有业务编排步骤和 I/O；Agent 只负责路由，Pipeline 只负责节点与循环。

选择评审时点是因为它满足两个条件：

- CR 已完成注册，CR-ID 和 `cr` 投影已经存在；
- 审批卡只需在评审通过、进入人工审批前可见。

即使本轮评审为 block，提前建立正确关联也不会显示错误审批卡，因为 `pending_stage` 在非审批状态为空。

### 6.2 窄接口

新增一个 task-scoped Multica 接口及其薄 CLI 包装。建议合同为：

```http
POST /api/crs/{cr_id}/bind-current-task
Authorization: Bearer mat_...
```

请求不接受 `task_id`、`agent_id`、`workspace_id`、`issue_id` 或 `project_id`。这些值全部由服务端获取：

- `task_id`、`agent_id`、`workspace_id`：来自 task token 认证中间件写入的权威 actor context；
- `issue_id`、`project_id`：来自 `agent_task_queue` 和对应 Issue/Project；
- 调用方只提供需要绑定的 CR-ID。

建议成功响应：

```json
{
  "cr_id": "CR-2026-052",
  "task_id": "task-uuid",
  "issue_id": "issue-uuid",
  "project_id": "project-uuid",
  "changed": true
}
```

同值重放返回 `changed=false`。

### 6.3 校验与事务

服务端在一个事务中锁定并校验 task、Issue、Project 和 CR：

1. 请求必须由有效、未撤销的 task token 发起；
2. token 中的 task 必须存在且属于 token workspace/agent；
3. task 必须有 `issue_id`；
4. Issue 必须属于同一 workspace 且属于一个有效 Project；
5. task 已有 `project_id` 时，必须与 `issue.project_id` 相同；
6. CR 必须存在于同一 workspace；
7. `agent_task_queue.cr_id` 只允许 `NULL → cr_id` 或同值；
8. `cr.shell_issue_id` 只允许 `NULL → issue_id` 或同值；
9. 非空异值一律拒绝，不覆盖、不猜测。

成功路径在同一数据库事务中完成：

```text
更新 task.cr_id
+ 更新 cr.shell_issue_id
+ 写 activity_log(action=cr_issue_bound)
```

任一写入或审计失败，整个成功事务回滚。事务提交后再发布现有 `cr:updated`/项目刷新事件；事件发布失败不回滚已提交事务，但必须记录错误并依赖现有重新查询机制恢复 UI。

冲突属于前置条件拒绝，不执行绑定写入。平台使用现有 `activity_log` 记录 `cr_issue_bind_rejected`，包含 workspace、Issue、Project、task、Agent、CR、当前值和拒绝原因；不为此新建审计表。

### 6.4 建议错误语义

| 错误 | 含义 | 结果 |
|---|---|---|
| `TASK_CONTEXT_REQUIRED` | 不是 task token 调用 | 零绑定写入 |
| `TASK_ISSUE_REQUIRED` | 当前 task 没有 Issue | 零绑定写入，review Skill 中止 |
| `CR_NOT_FOUND` | 同 workspace 中不存在该 CR | 零绑定写入 |
| `TASK_PROJECT_MISMATCH` | task/Issue/Project 关系不闭合 | 零绑定写入 |
| `TASK_CR_CONFLICT` | task 已绑定另一 CR | 零覆盖 |
| `CR_ISSUE_CONFLICT` | CR 已绑定另一 Issue | 零覆盖 |
| `CR_BIND_FAILED` | 事务或审计失败 | 全部回滚 |

这些错误是技术失败，不得转换成业务 blocker，也不得递增一次成功评审的 attempt。

### 6.5 现有 `StartTask` 归因的处置

现有 daemon `StartTask` 自报分支 CR-ID 的 best-effort 归因可以保留，用于兼容和辅助可见性；它不是本设计中审批卡绑定的充分条件。

新的 task-scoped 接口复用其已有 workspace 校验思想，但补齐：

- task token 的权威 task 身份；
- Issue/Project 闭合校验；
- `cr.shell_issue_id` CAS；
- 事务审计；
- 成功后的项目刷新。

不要求重写全部任务 enqueue 路径。

### 6.6 审批卡渲染

`GET /api/projects/{id}/gates` 保持现有响应模型，不新增 `pending_approval`、`gate_history` 或另一套 status→stage 映射。

前端改为：

```text
对每个 CR：
  pending_stage 非空
    → 直接渲染一个 ApprovalCard
  遍历 gate_nodes
    → 跳过当前 human_approval/running 节点
    → 保留 blocked card 与已完成/失败历史
```

`ApprovalCard` 从 `CrGateCard` 内部实现中提取为可直接调用的组件，但继续消费相同的：

- `cr.cr_id`
- `cr.pending_stage`
- `cr.can_approve`
- `cr.evidence`
- `cr.evidence_digest`
- `cr.pending_advance`

批准/驳回仍调用现有 API。前端不构造伪 `GateNode`，不直接改状态，也不签发新类型 grant。

该规则保证：

- 有审批状态、无 gate node 时，显示一张当前审批卡；
- 同时有 `human_approval/running` node 时，仍只显示一张当前审批卡；
- blocker 和历史节点继续显示；
- `pending_stage` 为空时不显示当前审批卡；
- CR 离开审批状态后当前卡片自然消失。

### 6.7 存量 CR

不新增 `reconcile-cr-origin` 或通用 reconcile 子系统。

CR-2026-051/052 的修复方式为：

1. 人类确认各自来源 Issue；
2. 从该 Issue 启动一次受控 Multica task；
3. task 调用同一个 `bind-current-task-to-cr(CR-ID)`；
4. 服务端执行相同校验、CAS 和审计；
5. 项目 gates 重新查询后验证卡片可见。

这不是本轮设计文档编辑时立即执行的操作，而是后续实现 CR 的验收步骤。禁止用会话内直接 SQL 代替该路径。

### 6.8 信任上限与残余风险

本最小方案明确接受以下上限：

- task token 可以权威证明 task、Agent 和 workspace；
- Issue/Project 由 task 行和数据库关系派生，不能由调用方伪造；
- CR-ID 仍由 review Skill 提交，服务端只能校验该 CR 属于同一 workspace；
- 因此，同 workspace 内恶意或错误的 task 理论上可能抢先把尚未绑定的 CR 绑定到错误 Issue；
- CAS、独立 reviewer 路由、结构测试和 `activity_log` 降低概率并提供追责，但不构成 CR→Issue 的密码学来源证明。

本 CR 不为该风险改造 enqueue 协议或引入签名来源。只有在实际发生错绑或风险评估升级时，才把合同升级为“调度层创建 reviewer task 时权威写入 `cr_id`”，并让绑定接口不再接受调用方 CR-ID。

## 7. 人工审批保持原样

人工审批继续使用现有闭环：

```text
ApprovalCard 批准/驳回
→ Multica 服务端重新计算 evidence digest 并校验人类权限
→ 签发既有 Ed25519 grant
→ daemon 投递 grant 到 Operational Workspace
→ crctl approve --grant 重验签名、状态和证据
→ 原子写 approval.yml、推进 cr.md 状态、产生 outbox
→ Multica 投影新状态并刷新项目会话
```

保持以下不变量：

- Agent 不得代表人点击或批准；
- Web grant 与 TTY 审批都是现有 `crctl approve` 的入口，不新增第三套协议；
- review PASS 与人工批准仍是两个不同节点；
- `pending_advance=true` 时继续使用现有等待语义；
- 证据漂移继续由现有 API/`crctl` 拒绝；
- 本设计不改变审批人权限、grant schema、daemon ACK 或自动续跑机制。

## 8. 兼容策略

### 8.1 pi、Claude 与其他 IDE/runtime

- `crctl` 状态机、gate、`advance`、`approve` 均不读取 matrix owner 作为状态转换条件，因此 owner 调整不改变状态推进语义。
- Pipeline owner 保留 `can-call`，现有 registry 和 Agent contract 校验继续通过。
- 支持 subagent/task 的运行时直接委派 `quality-reviewer-agent`。
- 不支持独立任务的运行时改为第二独立会话，不允许作者自评降级。
- 普通本地运行没有 Multica task token 时，review Skill 跳过平台绑定步骤，继续使用现有 `crctl review-record`。
- Multica task context 存在但绑定失败时，review Skill 必须硬失败。

### 8.2 旧评审证据

- 旧 annotation 保持可读；
- 旧 PASS 不自动作废；
- 不回填或伪造独立运行身份；
- `crctl` 不宣称能够从旧 reviewer 字符串证明独立运行；
- 对已知发生作者自评的在途 CR，应人工触发一次新的独立评审，而不是修改旧 annotation。

## 12. 已知风险与升级条件

| 风险 | 当前控制 | 升级条件 |
|---|---|---|
| 作者 Agent 技术上仍可直接调用 review Skill | 唯一 owner、Agent 路由、Pipeline prompt、结构测试 | 再次发生真实自评逃逸时，引入调用级执行身份拦截 |
| CR-ID 由 Skill 提交，可能在同 workspace 内错绑 | task token、数据库派生 Issue/Project、CAS、审计 | 出现错绑或安全等级提升时，由 enqueue/调度层权威写 task.cr_id |
| 不支持 subagent 的运行时不能单会话跑完 | 停在 review 节点，第二独立会话完成评审 | 多运行时频繁受阻时，再设计统一调度 Adapter |
| 成功事务后刷新事件发送失败 | 记录错误，依赖现有重新查询恢复 | 发生持续不可见时，复用现有事件重试能力，不新建审批队列 |
| 旧 PASS 无独立运行证明 | 保留历史、对已知事故 CR 手工重评 | 不在本 CR 批量废止或伪造历史身份 |
