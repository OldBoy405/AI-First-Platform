## Why

现有流程仍围绕阶段审批、各 loop/cycle 的评审次数及固定文件套餐组织执行， 尚不能保证充分授权后无需机械续杯、跨阶段累计修复受限及连续无进展停止。 单改提示词不能改变门禁与运行时行为。此前四阶段 registry 和去 Agent 接力成果应复用而非重做。

## What Changes

- 扩展既有审批与 CR 权威记录，绑定有版本的可信目标、范围、交付位置、验收、禁止项及执行上限；未授权敏感动作与扩围拒绝。
- 建立 CR 累计逻辑修复消费合同，默认 6 次，跨阶段和 cycle 保留，失败也计次，重放幂等，追加授权保留历史。
- 连续两次同根因且无可验证进展停止；由独立评审核验证据并给出明确升级原因。
- 配套调整 gates、状态声明、模板和权限合同，使授权内普通执行无需重复阶段人工确认，交付前独立验证不可省略。
- 按长期有效信息和最小变更验证记录组织文档，机械例外须独立证明无语义变化，长期规则更新现有权威源。
- 与 multica 的唯一 Runner 派发、异常分流及版本合同协同切换，新 CR 显式试点，旧 CR 保持原合同，发布重试不得再次消费授权。

### New Capabilities

- **execution-authorization**：可信授权包、敏感动作约束、适用版本与 scope 校验及授权消费。
- **repair-governance**：跨阶段累计修复额度、逻辑修复幂等、显式追加和连续无进展停止。

### Modified Capabilities

- **evidence-delivery-contract**：授权驱动门禁、内容型产物合同、独立验证及版本化新旧流程共存。

## Success Criteria

- [ ] AC-1：充分授权的普通变更无需重复阶段确认或人工搬运，仍必须通过适用门禁。
- [ ] AC-2：授权不足或扩围只补问必要取舍，未授权部分不先执行。
- [ ] AC-3：额度内且有可核验证据进展的修复自动继续。
- [ ] AC-4：默认累计第 6 次已消费后拒绝第 7 次，跨阶段/cycle 不重置。
- [ ] AC-5：连续两次同根因无进展停止，升级附证据、尝试路径及所需动作。
- [ ] AC-6：同一逻辑修复的重投、恢复和发布重试不重复扣额、不产生第二次逻辑派发。
- [ ] AC-7：旧版本、旧 cycle 或不适用 subject 的证据不能推进当前执行，历史可追溯。
- [ ] AC-8：未授权敏感动作无法通过作者自报、模糊实施授权或转述放行。
- [ ] AC-9：交付前独立核验实际差异和可运行证据；机械例外不能掩盖规则变化。
- [ ] AC-10：维护故障先有界恢复，再找维护责任人，业务方不承担技术搬运。
- [ ] AC-11：主动通知仅授权、需处置阻断、交付；文档与长期规则归属正确，无全文复制。
- [ ] AC-12：旧 CR 不静默迁移、新旧派发不双写、配套恢复未就绪不提前删除旧路径。
- [ ] 三条代表路径及失效用例通过隔离接口测试与独立评审；真实部署或试点未执行必须明确未验证。
