# AIFI-45 跨仓切片计划

## Dependency Graph Summary

```text
S1公开CLI信任边界 → S2完整授权与消费 → S3修复准入/独立进展
                      ├→ S4敏感动作与内容门禁 ─┐
                      └→ M-S1可信入口/传输 ───┼→ M-S2真实队列/四阶段恢复
S3/S4与M调度配套 → S5新旧合同/registry ────────┘
M-S2 → M-S3最小通知/消费者幂等 → S6跨仓三路径/全量/独立审查
```

**并行化**：只读环境核查可与S1并行。M签名/入口在共享payload字节合同稳定后可独立；同一仓共享入口文件单writer。T额度与M任务记录不各写一套预算。普通模式遇重大设计偏离、技术阻断、迭代上限暂停。

## 五步分析与Rationale

1. 依赖：授权字节与可信scope是任何业务准入前置；额度裁决在T先完成，M只能引用receipt入队。
2. 风险：信任、锁/提交、跨run身份、数据库唯一键和旧合同均高风险，负例先于放行正例。
3. 工作量：S1为M（已有CLI/crypto可复用），其余跨事务/运行时合同为L；S/M/L是相对复杂度，不承诺固定工时。
4. 分组：按公开可验证行为纵切，不按“先全写schema再全写实现”横切；每次一条失败测试→最小GREEN→相关回归。
5. 并行：环境调查不写代码；合同确定前不让两个writer同时改crctl/approval/Runner；隔离DB只可新建本change实例。

每片必须满足原生BUILD B3.4：TC完整、产物存在、选中测试非零且通过、相关全量回归、证据即时登记。部分TC通过只能标部分任务，不能登记整片完成。所有新命令仅在隔离fixture测试，业务功能与新policy默认不启用。
