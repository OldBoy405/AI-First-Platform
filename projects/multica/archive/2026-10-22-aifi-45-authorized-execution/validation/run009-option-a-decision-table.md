## 1. 现状：新状态必须同时接到自动判断与恢复

- 当前 Runner 的证据读取使用精确 `(run,node,attempt)`；调用顺序还受任务状态及部分 verdict 分支影响。`conclusiveReviewEvidence` 核 attempt、subject、时间、裁决与 blockers 形状（`multica/server/internal/governance/runner.go:1482-1506`）。这是本地形状校验，不证明身份和来源已可信。
- `reviewRoundUndelivered` 在没有决定性证据时读取 `needs_reconcile`，投影被认为已追平便可能走 `reviewDeliveryGap` → `failRun`（`runner.go:1560-1612,1629-1638`）。设计要求读取/解码错误不能当成缺交付；不据有限审查宣称现有所有辅助读路径均已满足。当前读路径不查询 A 的 pending。
- requirement 的恢复路径对迟到且已形成决定性 verdict 的情形先尝试继续原 run；确认为未交付的路径可能重派，已开始的普通失败/取消有拒绝条件。`ev.Verdict != ""` 且非决定性时不会简单按无记录重派；verdict 为空但其他字段非空不能概括为同一分支，解码错误也另处理（`runner_requirement_resume.go:190-264,670-705`）。这些是 requirement 所见，其他 pipeline 的恢复语义仍须分别核对。**独立复核指出**：该路径与“迟到评审一律不自动作用”的笼统说法直接矛盾，必须拆成两层：派发记录只定**轮次身份**，迟到证据**是否可应用**另按合同和当前状态决定；对仍在途且派发有效的轮次说“重验后应用”，不说“复活”。
- `WakeGrant` 的已提交 ACK 只触发重读和唤醒，不是新授权；已见 CR、任务、grant 和启动/周期 wake，未证明存在 pending 补齐专用 wake 或全部入口覆盖（`runner.go:1673-1730,1784-1810`）。失败 run 的扫描/恢复规则不能未经核实推广到所有 pipeline。

**候选接口要求**：自动 walk、缺交付判定及对应 pipeline 的人工恢复读取同一套有版本的事实分类及作用域；不能只增加一张 pending 记录，也不能把 `needs_reconcile=false` 当作 pending 不存在的证明。分类依据的 run/cycle、pending、closure、证据和处置须有一致性读取与版本；fail/恢复提交时必须确认结论仍有效，竞争失败须重判。公共事实分类不等于入口恢复资格相同：需逐 pipeline 评审任务 completed/failed/cancelled/in-flight × 迟到 PASS/BLOCK × 原失败原因，特别是已开始后失败的任务和迟到 verdict；保留何种差异或改变须批准。接口、物理状态和具体错误码均未定。

## 2. 逻辑分类（不是新 schema）

| 分类 | 必须具备／需保留 | 允许的处置 | 不得推断 |
|---|---|---|---|
| 接收待核 | 有界的原始输入、实际来源及可靠摄入责任；事件和子事实身份尚待定义 | 验证或按已批准容量规则隔离；未能持久承担责任时不能 ACK 为已可靠接收 | 字段自报、owner 兜底、hash 非空或 ACK 等于可信绑定 |
| 绑定未决 | 有合法恢复路径但缺待核事实；保存可追溯材料和重判责任 | 不推进；绑定/补充到达、启动及周期重判；达到策略阈值升级 | 无 run 等于旧轮；超时等于不适用或可以销毁 |
| 已验证有关联、等待补齐 | 权威证据足以关联到受控作用域和相关执行，但尚不足以决定是否可应用 | 针对关联范围等待；保留重判触发、可观察原因与恢复责任 | 未验证的声称可无限阻塞其他 run；把待决当已交付 |
| 已证历史／不适用 | 有可信、冻结的绑定和规则证明此子事实不适用于当前节点或只属于已终态旧轮 | 仅保留历史与处置，幂等重放，不创建新 run、不污染节点、不派发 | 未验证的旧轮声称即历史；历史保留即完成当前交付 |
| 适用且证据充分 | 原始 scope、run/node/attempt/cycle、实际 reviewer/任务 generation、subject、冻结的 template/policy、receipt 等按该轮可信冻结合同核验；适用评审须核作者/reviewer 真实独立性，交付须有匹配实际差异和测试的证据 | 针对具体阶段与动作，在受审查的事务及同步域内重验状态及适用准入，原子记录数据库 effect 和处置 | 单靠 reviewer 字符串、已签载荷或上次准入就足以授权当前 effect；把交付门槛无条件扩展到所有节点 |
| 已关联但证据无效 | 有可信关联，规则已证明格式非法或内容无效；与缺项未决、读取错误、已核验事实冲突区分 | 按合同保留可审计原因并拒绝推进；何种可可信补齐、何种可人工恢复/重派需批准 | 把无效、缺项和已证不适用混同；已可信证明绑定不适用时应按历史分支处置 |
| 已核验事实冲突 | 同一经认定的事实身份存在实质不一致，证据与来源可审计 | 相关事实不推进，隔离并交授权流程裁定；一致缺项可按规则补齐 | 未认证的恶意副本自动成为可信冲突并永久阻断无关 run；按先到/后到覆盖 |
| 不可判／已升级 | 权威链或策略无法给出结论；记录原因、责任与可恢复材料 | 按已批准的审计、复核、人工作业和恢复规则处理，不产生未授权 effect | 容量或时间到期本身证明无效；人工操作自动等于授权或永久丢弃 |
| 确认无交付 | 按适用合同校验任务结束清单，证明涉及该轮的任务/代次及事件范围已闭合，且没有可影响该轮的可信待决；清单真实性、完整性、关联方式和多任务处理待定 | 对该合同走已批准的失败/恢复策略 | 未发现记录、投影追平或未认证事件都足以单独证明闭合 |
| 读取或校验系统错误 | 错误可辨别并保留恢复责任，不把错误吞成空集合 | 失败封闭、重试或升级，依合同决定 | 错误等于历史、未交付或有效无阻碍 |

这些分类是推理词汇，不预设枚举名或存储实现。严格/可信 pin 的 legacy 如何分别解释“确认无交付”、invalid 和人工恢复，需兼容性决策与测试，不能凭缺字段静默降级。当前 legacy 行为不能未经批准整体替换。

### 关键未决：怎样既不误失败，又不让伪造事件无限阻塞？

新轮评审在权威开轮信息到达前可能只能归入“绑定未决”；此时既不能把它猜成当前 run，也不能让任何人仅凭伪造 `(CR,run,node,attempt)` 无限阻止 Runner。用户已确认采用平台派发记录与任务结束清单的方向；仍须由权威生产者/可信作用域、可验证的关联证据以及可信清单的完整性和交付闭合条件共同定义：**何时该 pending 足以阻止特定轮次判缺交付；何时可安全判定真正缺交付**。需要确定精确轮次或可信预开轮关联键、授权生产者集合及其代次和交付保证；尚未完成最终 run 绑定的可信早到项也必须纳入闭合判断。未认证声称不能自行取得阻塞资格或推进 closure；时间、投影追平或本地空集合不能单独证明 closure。这些条件尚无批准答案。分类器未具备可信输入时只保留审计和待裁责任，不可宣称自动分流正确。

## 3. ACK、补齐与恢复

0. **四类身份不能混用。** 待定合同须区分投递/副本身份、经权威认定的子事实身份、补齐或授权更正版本、业务 effect 的稳定幂等身份；未认证首包不能抢占权威事实身份，verdict 等内容也不能靠改身份逃避冲突检测；父事件已 processed 或 ACK 不得跳过新子事实及可信补充的分类。缺失、显式空与已验证值须区分；旧重判工作者提交前验证分类/处置版本，避免覆盖较新冲突或裁定。具体键和更正权限均待批准。**已证的现实反例**：服务端幂等键无 stage 维度而 `event_kind` 统一为 `'review'`，同 commit 的 code/test 评审在 DB 层只能存一行（`crsync.go:277-320`；`migrations/433...up.sql`、`610...up.sql`、`613...up.sql`；`crevents.go:1160-1207,1239-1247,1410-1416,1540`），说明“子事实身份”目前并不存在，不能把它当作已有能力设计。
1. **接收与业务处置分离。** 确认收到之前须耐久保存实际接收输入、来源、可重放材料及责任；未能持久接收时按协议明确失败或背压，不能发送会让上游删除唯一副本的成功 ACK。若材料已安全摄入，ACK 不等于已绑定或已应用；上游 ACK 丢失须能幂等重投。当前 ledger 的首包、后到输入与实际投影可能不同，不能只保存“首包=应用输入”的假设。
   - 静态事实（`multica/server/internal/daemon/crevents.go`）：批量 ACK 的 `Accepted` 是 **事件 id 列表**，rejected 也是按 id（`:75-81,1005-1028`）；**并非所有事件 id 都是文件名**——commit-scan 用合成 id `commit:<sha>`、reconcile 用 `snapshot:<trunkSHA>`（`:837,1204,1220`），`applyAck` 会跳过这些合成 id（`:1019-1021`）；outbox 通道的 id 才是目录内文件名（`:1089`），命名空间按 root 而非全局。报告本身带 `WorkspaceRootHash`（`:71-73`），因此精确表述是：**ACK 可按 root 汇总，但不能按任务汇总**。事件结构无 task/run/attempt/cycle 字段（`:55-68`），但 `Payload`（RawMessage）与 `Evidence`（map）是透传自由字段，**不是无处可放**，只是无类型化、无校验、服务端不保证保存；daemon 侧合并去重键 CR+commitSHA+eventKind（review 再加 stage）本身即丢弃任务区分（`:1403-1431`）。
   - 因此“任务结束清单”无法从现有链路直接得出：事件没有任务归属，ACK 无法按任务汇总。CUSTOM #284 **修复前**的零证据成功路径比先前描述更宽：`settleRoot` 对未纳入投影的 root 返回 `(false, nil)`（`:435-440`）；`settleCREventsForTask` 在 `collector==nil`、`PipelineCrID==""` 或 `root==""` 时**完全静默** `return nil`（`daemon.go:6372-6374`），未纳入监控时也只告警后返回 nil（`:6383-6387`）。修复后的 CR 绑定失败分支见 §5；即使组件级 settle 成功，也不能证明本任务的事件完整上送。采集入口是 task 级（`task.PipelineWorkspace`），粒度是**整 root**（含其他 CR）。
   - 变更面已可判定（本轮新增静态核实，仍未经独立复核）：服务端 `cr_sync_event` 表列为 `workspace_id, cr_id, commit_sha, event_kind, payload, evidence, actor, occurred_at, received_at, processed_at`，幂等键是 `UNIQUE (workspace_id, cr_id, commit_sha, event_kind)`（`migrations/433_aifirst_cr_projection.up.sql`、`610_cr_sync_event_workspace_uniq.up.sql`、`613_drop_cr_sync_event_old_uniq.up.sql`）。入库为 `ON CONFLICT ... DO NOTHING`，且冲突时**只**在既有 `evidence` 为空对象时补写 evidence，**payload 永不更新**（`crsync.go:277-311`）。
   - 由此推得的两个硬限制：①**payload 路线不足以承载任务归属**——冲突时 payload 没有任何更新语句，后到事件的归属信息不会进库，而该事件仍会被 ACK（随后 daemon 删除 outbox 文件）。限定：payload 丢失仅当首条已 `processed`；若首条未 processed，`ingest` 会用当前 wire 事件执行 `apply`，后到 payload 仍可能生效（`crsync.go:315-320`）。②crctl 的评审事件 `event_kind` 统一为 `'review'`、stage 放在 payload（`crctl.mjs:3379-3390`），而**服务端幂等键没有 stage 维度**，同一 `(workspace, cr, commit_sha, 'review')` 的不同 stage 事件在 DB 层只能存一行。这同时把 `run009-option-a-review.md` 第 2 条“去重键无独立 stage 维度、event_kind 是否区分 stage 未证”**升级为已证**：`event_kind` 不区分 stage，塌缩发生在唯一索引层。
   - 可达性（独立验证结论：**条件性可达**，非仅理论可能）：commit-scan 对同一 commit 可从 subject 解析出 `stage=code`（`crevents.go:1239-1247`），并在该 sha 下同时存在 `test-report.md` 与 `trace.tests` 时再生成 `stage=test`（`:1160-1167,1175-1207,1540`）；daemon 合并键含 stage（`:1410-1416`），两条都会上送，服务端第二条 `DO NOTHING`。crctl 正常路径较难触发（review-record 每 stage 单独提交，`:3771`）；`dev-plan` 不被 subject 正则匹配（`:363`）；amend/rebase 不会让既有 outbox sha 相同。
   - 若要求**逐事件清单**，则要么改变事件身份键（schema/wire 变更），要么另建独立的逐任务投递记录，不能从 `cr_sync_event` 推导。后续用户采纳的最小实现不再要求逐事件清单：以“终态前严格 settle 成功”作为无交付判定前提，不新增表或改幂等键；实现与边界见 `cr-settle-fail-closed-20261030/REVIEW.md`。另需注意 outbox 侧去重比较面**包含 payload**（`tools/skills/shared/crctl/scripts/lib/outbox-contract.mjs` 的 `OUTBOX_COMPARED_FIELDS`，易变键白名单仅 `detected_at`），所以在 payload 里加任务键会同时改变客户端去重语义：同逻辑事件因 payload 不同而变成 `OUTBOX_DEDUP_CONFLICT`。客户端“认 payload”与服务端“不看 payload”的错位本身是需一并评审的语义矛盾。
   - 未验证（不得当作已知）：新增 `workspace_id` 列的迁移不在本轮读取范围内；`applyReview` 主体、写 `trace.tests` 的代码、`cr_sync_event` 既有数据分布、迁移实际执行顺序均未核（`610` 注释称旧键在 `394` 删除，而 `613` 才删除，二者不符）；未跑 DB、测试或任何命令。
   - 载体可行性（当前工作树静态复核，更正此前结论）：`terminalTaskReport` 有 `taskID/runtimeID/dispatchedAt/claimRequired` 字段；`handleTask` 的 daemon-token 路径把有效任务元组放入 context，`reportTerminalTask` 在发送前经 `withContextClaim` 填充该元组（`daemon.go`、`execution_terminal_claim.go`）。所以不能仅凭完成/失败调用处的 report 字面构造断言生产路径从未填充。该链有条件：PAT 或缺字段等路径不因此自动获得严格元组，实际到达、鉴权及持久回放仍须验证；元组也只表示对应任务代次，**不能表达“本任务发出过哪些事件”或证明 RUN-009 轮次闭合**。另外 outbox 目录由 `deriveInstallRoot` 解析到 git common dir 的父目录（非 git 仓回退 opWs，`workspace-transactions.mjs:59-66`），同仓所有任务共用；文件名通常为 `{ts}-{cr_id}-{kind}-{sha8}.json`，但 `ev.dedup_name` 可整体覆盖（`crctl.mjs:503`）且 `emitOutboxEventOnce` 会复用既有名（`:527-538`），且平铺写入（无 task 子目录，`scanOutboxDir` 跳过目录 `:1073-1076`）。故“每任务清单”不能靠现有路径推断。
2. **可信补齐不等于覆盖。** 为同一经核验事实补缺项须保存所有来源与验证结果，不改变已验证的 run/cycle/subject/verdict 等事实；已核验矛盾保持冲突。最终子事实身份、可信来源优先级、撤回/更正语义、同 commit 不同 stage 的真实来源形状均待定。
3. **恢复责任不依赖唯一 outbox 文件或 Git blob。** 可持久列出待判项、版本、原因、下一责任及变更；绑定到达触发重判，启动/周期补扫兜底。用持久可重放状态或等价机制覆盖“提交后唤醒丢失”；禁止依赖内存队列。限额满时不抛弃已 ACK 的责任；对未接收数据实施已批准的背压。额度分配、输入大小与解析成本、来源/租户限额和可信流量保障、重复副本成本、升级/终结时限、审计与保留策略待定。接收成功、永久拒绝、可重试背压须定义协议语义；批量响应逐项对应，不能只凭父批次成功认定每条责任。
4. **人工恢复不可制造授权。** 按合同区分已知缺交付、有效迟到、未决、恶意/无效及已取消；重派、恢复原 run 或只保留历史需各自的资格和审计。恢复后仍须重读撤销、STOP_NEW、readiness 和适用 resume 事实。重判完成须为受影响 pipeline/run 定向唤醒并设计丢失补偿；已失败 run 是仅落证据并通知人工，还是允许受控恢复，须按 pipeline 另定，不能假设普通 Reconcile 等于显式恢复。

## 4. 事务与锁：约束而非既定锁序

- 在实际生产者和可信存储确定后，提出并独立评审跨进程协调域；终态、受控开轮、无标记 run 收编、显式恢复、事实绑定及节点写须逐入口覆盖或给出可证明的等价 CAS。`run009-terminal-writer-inventory-20261029.md` 只是有限起点，不是完整清单。
- 数据库 effect 与对应处置应在同一可证明的事务边界内一致；重读原始绑定、终态、准入版本和事实时须防撤销/变更竞争。对**不存在**的绑定/撤销记录也须说明如何防 phantom 或并发创建，不能只锁已有行。持业务锁事务内不等待外部业务网络调用或 effect；数据库访问本身可能经网络。
- 外部 effect、队列或跨连接写入不可凭单个 DB 事务宣称 exactly-once。若涉及它们，须设计与操作绑定的稳定 identity、持久意图、执行方实际校验的栅栏、授权/撤销线性化规则、接收方幂等及结果查询。lost-ACK 时先恢复原操作结果，不能换 ID 盲目重发；接收方无所需能力时结果保持不确定并交授权流程裁定。敏感 action/target/environment 仍须专项授权；当前均未定。
- 已见投影取消 node→run、Runner fail run→node；SyncService 实例内 mutex、按 run 的 session advisory lock 和持该锁后经 pool 执行的事务未证明属于同一域。writeback 可从不同路径进入。**观察到相反语句顺序不等于已证明死锁**；引入共同域前须核连接、锁键/模式、取得与释放时点、调用嵌套及触发器/外部写者。不能把候选 `workspace+CR → head → run → node` 当成已证全局锁序。具体证明须覆盖锁后重新选择的 run ID、CAS 谓词和影响行数、缺行的创建/撤销/更正与删除重建；失败须重判。需单列内部嵌套重复取锁、writeback、回调重入，以及恢复提交后排队前崩溃或并发重试，避免条件性自等待与重复派发。
