# 远端发布未知结果：合同修订方案草案

> **DRAFT / 非批准。** 用户同意按“目标已达成但本次尝试未证实 → 显示目标状态与待核状态，不重推，不自动继续下一受保护动作”方向准备修订方案；未批准本草案、归档合同修订、Gate1/Gate2 或实现。用户对“已用于真实业务或可能已有旧数据”回答“是”：不拆推两项各自为真，按可能有存量和在途工作设计。用户原文及确认边界见 `verdict-authority-acceptance-20261030.md`。

## 1. 范围与目标

**目标：** 远端 push/finalize 的结果与同一尝试的权威结算可区分。外部调用可能成功、延迟、失败或回执丢失；不把当前远端状态、普通日志、未经认证的调用方报告、ACK 或人工点击直接升级为“本次 effect/no_effect 已证明”。未知时保留真实账目，禁止重复可能已发生的动作及自动发出下一受保护动作。

**不在本草案实施：** 不创建或修改 STDD change、归档及已确认 proposal，不执行真实 push/CR，不查询或变更部署与数据库，不改旧 runner，不签发生产裁决、不选定 key/信任根/远端供应商、不默认必须升级签名协议或修改数据库 schema。

**边界：** 本方案是对原合同**拟议修订**。归档 `projects/tools/archive/2026-10-27-trusted-verdict-channel/canonical/specs/code/trusted-merge-gate.yaml` 的 SC-MG-015/016/017/018/019/020 及 M 归档 SC-VC-019–022/034/035/036 现仍有效；新 proposal 和 Gate 未获批准前不得替换或冒称新的规则已经生效。当前两侧可信 verdict proposal 分别排除改变生产入口与签名代码，原 AIFI-45 的入口/代次/锁/验收也不得被本草案替代。

## 2. 事实模型与证明边界

| 事实 | 说明及候选证明要求 | 不能推断 |
|---|---|---|
| 目标状态 | 经认证的观察绑定目标仓库、远端、ref、目标提交、祖先关系和观察时点；显示当前是否包含目标 | 哪个尝试造成状态，或过去没有发生过 push；历史可能被改写 |
| 本次 effect | 被授权且能关联准确尝试的可信回执或等价权威证据；定义完整性、重放、时效、撤销/代次及来源后由服务端独立验证 | 签名 permit、ACK、目标达成、caller 的 `effect`、单纯客户端成功日志 |
| 本次 no_effect | 可信证明针对该尝试的动作确未发生，涵盖谁可签、旧执行者/迟到请求已被有效约束、竞态与代次；如何证明应按具体远端能力审查 | 当前远端在 prev、超时无回执、仅有 caller 或未经认证的 `settled_no_effect`、人工单击确认。固定等待时间不能单独排除迟到 |
| 未知 | 上述证据不足或不能验证；显示可核实的目标观察和“尝试待核”，保留未决记录及槽位 | 未发生、已经完成、失败或可重发；不能推断未消费，也不得无独立授权重复扣除或发放额度 |

“本次未发生”不是“这个目标历史上从未发生”；“当前达成”也不一定是本次 push 所致。远端观察必须防止不同仓库/ref、过期观察、历史回退和 `prev → expected → prev` 等误判。

**候选证据来源与当前 BLOCK：** 当前源码中所查 merge report 只接收调用方的 kind，尚未证明存在生产远端观察者、回执签发者或独立验证入口；部署是否有其他来源仍未知，不能宣称绝对不存在。候选采用隔离控制环境中的受保护观察者，从经认证远端读取并签署**目标观察**，由独立消费方验证其身份、对象和时点；它只证明观察到的状态，不凭此证明本次 attempt 或 no_effect。对于 `intent` + prev，可研究受保护的“发出前持久记录 + 执行权唯一性 + 旧执行者已被有效 fence + 无可迟到请求”等联合证据；其中任一事实不能认证就不能断言未发出。对已 issued 的请求，即使远端当前在 prev，也需可验证的远端/执行者终结与迟到排除证据。证据生产、跨仓验证、保护及各远端供应商能力尚未确定：**在这些能力设计、独立验证并获准前，依赖它们的结算/重试分支均为 BLOCK，不存在已证实的自动恢复路径。**

**两个 no_effect 不能混淆：** 归档 SC-VC-022 的已认证 pending/deny/stopped 或失效授权，可按原合同对**尚未发生的本地/授权层效果**结算 no_effect；SC-VC-020 要求撤销先于结算时记 no_effect，且外部动作不执行，后者是必须兑现的义务。本草案不一概冻结或改变这些场景。若不能证明该义务已兑现、远端动作已发出或可能发出，不能仅凭授权被拒、撤销或局部 no_effect 证明远端效果未发生；merge 的撤销线性化还须遵守 SC-MG-014。授权层 no_effect 后若出现与之矛盾的远端事实，追加矛盾证据并冻结远端范围，不能回写历史。归档 SC-VC-021/022 的已消费不退款、未知不得推断未消费和未知不释放 slot 均须保留。

## 4. 候选身份、状态与恢复规则

**设计前置的身份模型：** 候选区分三个不同维度：① **防绕过的冻结范围**绑定经认证的远端仓库身份及 ref、稳定业务来源与关联 CR/lineage；② 每个 effect 再绑定操作种类（含 merge 或 finalize）、目标及冻结输入摘要、当前授权代次；③ 一次 attempt 以 effect 身份和不可复用的 attempt 身份关联 reservation、command/mapping、发出状态和结算证据。授权代次、目标及摘要属于 effect 的绑定，**不能**构成绕开已有冻结的条件。相同标识的原字节重放须返回原结果，不同内容须明确冲突；不同 attempt 或不同 effect 不能被无意合并。具体主键、身份权威来源、attempt 与原 mapping 的关系及 schema 尚未选定，是正式方案的阻断项，不声称现有实现已具备这些约束。

**跨代次与跨 CR 防绕过：** 候选对认证的远端仓库/ref 在 reserve/issue 时、任何外部发送之前，原子建立持久占用，并持续至经批准的可信结算或解除；不能等到事后发现“待核”才占用。占用持续覆盖在途、待核、重新授权或变更代次、resume/epoch、换输入摘要、换目标/rebuild、base 漂移和同业务来源重建 lineage/CR。其他 CR 指向同一认证远端/ref 时，默认阻断任何受保护写入；若要例外，须先证明能从远端有效隔离仍可能迟到的旧请求。仓库别名、ref 或业务 origin 真实性不能只用 caller 自报；无法判定映射则按相关目标冻结。这可能影响多个流程，是待审的可用性取舍，并非现已部署的全局锁。

**冻结持有者与传播：** 推荐由 M 平台受保护的持久化事务状态保存并强制核对占用/冻结事实，候选受保护执行者在每次真正发出前使用同一权威事实和已批准的锁/代次；该执行者实际存在和隔离尚未证明。任何 T verdict 或 permit 都不能越过 M 的冻结；M 向执行者提供权威状态的认证、绑定及故障处理通道尚未定义，具体数据结构与负责 change 待正式设计。此候选**不能单靠 M 数据库检查证明无绕过**：必须另由受保护执行身份/远端的可信限制 fence 所有可直接 push 的旧或并发执行者，覆盖检查到实际外部动作的间隙；做不到即不可启用。归档 command open slot 属 command 状态，当前 merge reserve 可见的是 reservation/settlement，不能假定二者共用 slot。SC-VC-022 的已 issued 未知 command 不释放 slot；要改变须另审。上述权威持有者、原 mapping 与 attempt 如何协调 SC-VC-035/SC-MG-016，必须在 Gate 前选定并验证，现为 BLOCK；不得声称生产已冻结。

以下是行为草案，不预定状态名、数据库列、新协议版本或具体回执格式。`已确认方向` 只指用户同意准备“目标达成/本次待核”的方案，不表示已批准合同；其他行是**工程候选**，可能需进一步业务决策。

| 场景 | 候选动作 | 后续授权 / 备注 |
|---|---|---|
| 【工程候选】原始 intent + 远端 prev，可信证据证明尚未发出且无旧执行者可迟到 | 先按批准合同完成旧尝试的确定处理；如授权仍有效，再按批准的唯一 attempt 规则请求新尝试 | 必须原子核对当前 head/代次、绑定和旧尝试；证据不够视为未知。新 attempt 与 command/mapping 的关系尚待设计 |
| 【工程候选】intent + prev，但记录、持久性或旧执行者不可信 | 保留未知，停止新 publish | 不能只因 journal 叫 intent 或当前仍为 prev 就判断 no_effect |
| 【用户同意准备方案的方向】unknown + 可信观察已含目标，但本次归属未知 | 显示“目标当前已达成，本次尝试待核”，不重推，不以此结算该次 effect | 未知 command 不释放 slot；与 SC-MG-015 冲突的成功结算须正式修订审批 |
| 【工程候选】intent + 可信观察已含目标，但本次归属未知 | 显示目标当前已达成，核查是否真的从未发出，不直接依据目标状态结算该次 effect | 归档 SC-MG-015 的 given 未覆盖 intent；意图记录的可靠性和旧执行者状态、槽位处理须正式评审 |
| 【工程候选】unknown + 远端 prev 或不可读，含未经认证的服务端 no_effect | 保留未知，不重推、不结算 no_effect | 即使用户可见远端当前旧位置，也不能排除迟到、并发及历史回退 |
| 【工程候选】获得可信本次 effect / no_effect 证明 | 对照授权、身份、命令与尝试、原始证据及幂等规则，经批准后按相应合同结算 | 证据不足或矛盾则冻结；前次 effect 的确认不自动授权下一次 effect |
| 【原合同待协调】confirmed 且可信终态与远端正常前进一致 | 不重复动作 | 后续独立 effect 仍需当前授权与自己的证明 |
| 【原合同待协调】已确认目标退回 prev、历史分叉或事实冲突 | 冻结并保留矛盾证据 | 不改写旧已提交结算，不猜 no_effect |
| 【工程候选】已有 reservation 重放、重复/冲突 report、无匹配 reservation | 返回原始映射或明确冲突，不把 replay 解释成新可执行许可；核对 report 实际提交/命中行及相同事实 | attempt 与映射如何对应以及错误码待设计；不同内容不能静默写成同一成功 |

**人工核查不是万能解：** 可由有权人员调查并提交供独立验证的证据；人类 resume 证明授权意图，不自动证明远端效果发生或未发生、旧推送已停止，也不自行释放 slot 或终结 attempt，不能仅凭点击把未知改成 no_effect 或打开新 attempt。归档 SC-VC-019 的 human-purpose resume、epoch 单次消费等约束可作为设计输入，但其与当前 DB grant 路径、slot 和远端事实尚未完整接通；不能声称已有可直接复用的可信生产恢复入口。

**候选人工业务收口，待单独评审：** 对已认证“目标当前达成”但归属仍未知，可允许有权人员把展示/工单状态标为“目标已达成、归属未证并完成核查”，保留原 attempt 的未知、审计、可能已消费额度与动作冻结；这不把账本结成 effect/no_effect，也不批准重推。若业务要求解除冻结或开展另一个远端动作，除重新获得独立授权外，仍须先证明旧动作不能迟到且所有旧执行路径已被有效 fence，并经新合同及部署门禁批准；审批按钮本身不是此证明。证据仍不足时可能长期冻结，导致已达目标的流程无法自动完成；该可用性后果及能否接受须在正式审议时明确，不由当前方向确认代签。

### 4.1 待核时必须约束的后续动作

在正式实现和部署条件获得批准后，候选按上述受保护业务来源及远端仓库/ref 冻结范围拦截：同一 attempt 的重复 publish、新 attempt，同一 CR 事务内其他仓库的所有后续 publish，以及 finalize push；例外须经可信证据与批准合同证明。指向同一目标 ref 的其他 CR 也按 §4 防绕过要求处理。不能把目标观察直接当可信 settlement 或额外额度消费/释放；不能依据该未决结果自动推进依赖其完成的 CR 状态、归档或发出声称成功并触发后续受保护 effect 的 outbox。纯读取、审计、故障告警及人工核查材料投递应仍可用，避免冻结把人工处置通知也堵住。对经可信证据证明独立于该冻结范围的动作不应无依据扩大全局冻结。具体依赖及范围需要对真实入口逐项审查；**不是当前已实施的阻断。**

## 5. 存量、并发与部署安全前置

1. **保留事实：** 旧结算、签名原字节、旧 journal 和审计不得静默重写或删除；旧 `effect/no_effect` 是否可作为新授权证据，取决于可信来源与历史覆盖，不因字段存在即认定可信。已生效事项不自动回撤，未证实身份/历史/在途的情况不得当作全新请求。
2. **先控制旧路径，再激活新判断：** 新合同不会自动改变既有部署。启用前由被批准的部署/远端管理职责持有者提供证据：所有可发起或结算该类 effect 的副本、执行者和旧入口已纳入清单并受到不可绕过的统一限制；不兼容、无法观测或未隔离的旧 writer/副本不放行。不能只靠旧客户端自报版本或新客户端自觉遵守：如果某执行者可绕过控制面直接访问远端并 push，须在远端/身份或等效可信隔离处有效 fence；无法证明则不能启用。是否存在此类凭据或可用 fence 当前未知。需要覆盖真实 `mergeCr`、finalize、resume 及其他写入路径，而不是只验证一个 helper。
3. **避免检查后切换：** 将获批部署代次/策略、权威清单和可变更的 writer 与 effect 授权关联；部署或策略变化时，先前静态检查不能独自作为当前放行依据。具体锁、隔离、fencing 机制与部署事实未知，需设计和独立验证，不预设特定 DB trigger、版本或外部服务。
4. **在途与回滚：** 已发出但结果未知的旧 attempt 不能因升级、重启、切换 epoch、搬迁或回滚变成未发生或新额度。旧 settlement 是否含可验证证明未知；新策略可能使部分在途工作或 finalize 暂停，影响范围尚无权威数据，不能断言全部或没有受影响。回滚至旧代码可能把新待核状态误当成功或直接 push，须由不受旧代码控制、经批准的部署/远端 fence 确保待核时旧路径不可发起 effect，并验证所有副本；不能证明等效限制则禁止回滚并保持冻结，故障时只研究经审批的前向修复或冻结远端写入，不保证两者一定可行。待核状态具体编码及旧 reader 的失败关闭性尚未选定、须测试；schema 回退或数据迁移也不得删除、丢失或绕开仍需生效的占用/待核记录。禁止在不明存量时做无条件回滚或复制/改写历史。
5. **权限/环境：** 实际受保护执行者、信任根与目标环境隔离必须按真实部署另行出证；已归档的 `channel-component` 不能替代 strict-production，历史本机隔离失败的资料不能外推当前环境。部署检查、裁决认证和业务准入是不同门禁。

## 6. 方案归属与审批路径（建议，待确认）
