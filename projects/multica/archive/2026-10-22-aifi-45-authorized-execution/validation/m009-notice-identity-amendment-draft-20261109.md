# M009 通知身份设计修订草案（2026-11-09）

> **DRAFT／未批准／未闭合。** 本文供评审 `design.md §5` 第 79–82 行的替换方向，不修改已批准设计、canonical 场景或 Gate 状态。用户已选择复用现有 notice 唯一键的实施方向；该选择不等于批准合同修订或降低现有验收要求。

## 拟替换文本

以下四项拟替换原第 79–82 行；第 76–78、83–84 行及现行 SC-NTF-001～007 保持不变：

1. 复用现有 `cr_execution_notice` 作为通知持久身份，`(workspace_id, dedupe_key)` 的既有唯一约束承担并发去重。规范事件身份应满足原设计第 78 行和 SC-NTF-005/006：覆盖可信 workspace、project、CR、稳定原因/事件、重要证据摘要、非空受众及规范化接收者；未变化的事实跨 run/commit 重放仍复用身份，不同 CR、新失败、重要证据或接收者变化、以及交付完成不得互吞。
2. 不新增 `inbox_item.details.execution_notification_key`、partial UNIQUE 索引或相关迁移。notice 与其 Inbox 记录在同一事务内持久化；唯一键冲突时返回原 notice 及原 Inbox ID，不产生第二条内部通知。
3. `pending`／`delivered` 状态及 Inbox ID 保存在既有 notice 记录。提交后广播；已提交的 pending 在既有恢复路径中以原 Inbox ID 重投，广播后标记前的中断允许同 ID 再投，消费者须按该身份幂等展示。不得宣称第三方物理 exactly-once，已 delivered 的相同事件不作为新通知重播。
4. 通知失败不回滚已提交的业务事实，不重签授权、不重复扣额或派发 writer；同时保留 SC-NTF-007 对 Inbox 持久化失败后沿原身份恢复、不丢提交后提醒的要求。不能以“尚无 pending 行”或一条风险记录替代该保证。

## 评审前未决事实与实施缺口

用户后续采纳以下方向：若确无既有权威责任来源，由真实业务生产者在既有业务记录中明确保存责任及证据快照；授权决策者、维护责任人和交付接收者可以是同一人，但须有各自的可信依据，不从 starter 或 owner 猜测。不新增数据库结构、不回填历史；具体生产者、资格依据、持久化字段及恢复能力仍须核实。方向确认不等于批准本合同草案或赋予任何人权限。

- **项目及事件身份**：当前 `NoticeDedupeKey` 包含 CR、cause、evidence digest、audience 和接收者，数据库唯一约束另含 workspace；尚未证明其覆盖可信 project。生产失败接线当前对错误码而非重要证据求摘要，同码的新失败或证据变化可能被吞。须明确已有可信 project/事件/证据的来源与稳定规范化规则，不得以 run ID 或错误码替代尚未证明的业务身份。
- **写前故障**：当前业务状态先提交、notice 独立提交；notice 写入前失败时没有 pending 行，现有恢复不能补造提醒。需证明可从既有持久业务事实安全、幂等重建待通知意图，或经合法流程提出其他兼容方案；未经修订批准不得削弱 SC-NTF-007。
- **真实生产路径和接收者**：授权投影可能先于 runner 更新导致漏通知；交付路径、实际技术故障根因和已试路径尚未完整接入；`started_by` 的成员身份不证明其为有权授权者。须在已批准范围内核实事实、权力来源与实际动作，不能由状态或角色猜测。
- **消费者恢复**：须用真实服务器载荷验证同一 Inbox ID 重投不会新增用户可见提醒；广播成功并不等于客户端已展示或第三方已送达。
- **旧键**：接线前无已知生产调用方不等于数据库无旧行。若发现旧键行，保留数据并单独裁定重放、兼容及验证，不预设回填或双写。
