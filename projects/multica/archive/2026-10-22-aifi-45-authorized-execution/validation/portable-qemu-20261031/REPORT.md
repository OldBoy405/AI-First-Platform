## 结论

- 选定来源为 MSYS2 官方仓库 `repo.msys2.org`（仅 https、固定主机名、无重定向、不读取本机认证文件）。这是可获得“免安装”QEMU 的现实途径：`qemu.weilnetz.de` 只发布 NSIS 安装包（发布 SHA-512），本机没有 7-Zip 之类工具可离线解包，故未选用。
- **依赖闭包过大，获取未完成。** 以 `mingw-w64-ucrt-x86_64-qemu-11.1.3-1` 为根做完整依赖解析，最后一次运行在 **109 个包、203,273,174 网络字节**处失败于 `mingw-w64-ucrt-x86_64-giflib` 不在两个仓库索引中。失败原因是 MSYS2 的 `qemu` 包连带 GTK3/SDL2/音频/SPICE 等图形与媒体栈，而不是运行无头虚拟机所必需。
- **单个包即超出本机 Node 可缓冲上限。** qemu 包解压后为 **1,084,108,800 bytes**，超过本 Node 构建的单 Buffer 上限（512 MiB）。因此“读入整个 tar 再解析”不可行，`portable-qemu-extract.cjs` 目前**无法**抽取该包，需要改为流式解压与流式写盘。
- 抽取到磁盘的体积将达数 GB；本机剩余空间约 9.4 GB（获取前观测）。

## 关键限制（不得当作隔离或验收）

1. QEMU 官方不发布 Windows 二进制；MSYS2/第三方构建存在供应链风险，且本轮未做签名校验。
2. 即便取得二进制，仍缺 guest 内核与 initramfs/rootfs；已下载的 `pgvector/pgvector:pg17` OCI 镜像是容器镜像，不能直接启动，需要层转换、whiteout 处理与串口/块设备进出机制。
3. TCG（无虚拟化）不在 QEMU 安全支持范围内；WHPX 可用性未验证（`systeminfo` 只显示“已检测到虚拟机监控程序”，未显示 Hyper-V 功能项）。
4. QEMU 进程与调用者同一 Windows 用户；无共享目录/网卡时可缩小攻击面，但不是安全边界。
5. 上述任何一项都不构成 AIFI-45 的隔离证据、TC 通过或 Gate3 放行。

## 与自建 WSL 发行版的对比（供决策）

| 维度 | QEMU（无共享、无网卡） | 自建 WSL distro（`wsl --import`，rootfs 自带 `/etc/wsl.conf` 关闭 automount/interop） |
|---|---|---|
| 内核 | 独立 guest 内核 | 与其它发行版共用 WSL2 VM 与内核 |
| 宿主文件可见性 | 不配置共享即不可见 | 需在首次启动前于 rootfs 内写好配置；guest root 能否手动挂载 drvfs 未验证 |
| 网络/端口 | 可完全无网卡 | 与 HOLD 环境共享 localhost/NAT，端口需自选且不得连接 HOLD |
| 审计 | 命令行即设备清单 | 依赖 WSL 内部行为，可见性差 |
| 成本 | 高（110+ 包、数 GB、仍需内核与启动管线） | 低（可复用已校验的 OCI 层） |
