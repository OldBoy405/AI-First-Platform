## 0. 为什么要重跑

第 6 轮 strong 档复核对第一次运行判 BLOCKING（针对"能否运行真实目标"），并指出证据里有三处**启动器自报值被当成测量结果**：

| 复核 | 问题 | 本轮处置 |
|---|---|---|
| e | 顶层 `capabilityCount: 0` 是 `runner.go` 写死的常量，不是测出来的 | **删除**该顶层字段；目标 token 的能力数仍在 `targetToken.capabilityCount`（从目标进程挂起时读取） |
| b/c | `targetToken.handleListApplied` / `inheritedHandleCount` 由启动器按 `len(inheritedHandles)` 自填，却放在 `targetToken` 下像实测值 | **移出** `targetToken`，集中到新的 `launcherAsserted`，并带 `note: "launcher self-report; not a measurement of the target"` |
| c | `final.environmentKeys` 由启动器用占位路径 `C:\placeholder` 算出；而**探针自己看到的** `environmentKeys` / `loopbackError` 因 `probeEvidence` 结构缺字段被反序列化丢弃 | `probeEvidence` 补 `environmentKeys` / `loopbackError` 两个字段，探针视角完整读回；`launcherAsserted.environmentBlockKeys` 优先取探针那份 |
| g | `runner.go` 文件头注释仍写"清理探针后再执行测试二进制"，与代码相反 | 已改为明确声明本修订版是 synthetic-probe only、拒绝 `--target-binary`/`--target-sha256`、**没有**执行真实目标的代码路径 |
| f | `whoami` 记成 `GOBAO`（像 `%USERNAME%`） | 第二轮记录的是环境变量拼接 `%USERDOMAIN%\%USERNAME%`，不是执行 `whoami` 的回执；runner 写入父目录身份，但缺运行前独立记录 |
| h | 第一次归档的 `probe-evidence.jsonl` 未记录复制时哈希 | 第二次构建记录登记原件哈希；随后核对归档文件与记录哈希一致。该比较不能单独证明原件在复制期间未变化 |

此次修改意图是区分启动器自报与目标数据；未经独立复核不能据此宣称修改没有影响隔离机制，也不能宣布机制安全。

## 2. 证据归属（本轮重点）

`phase-complete` 现在明确分三块，互不冒充：

**`targetToken` — 从目标进程挂起时的 token 读取**
```json
{"verified":true,"isAppContainer":true,
 "expectedSid":"S-1-15-2-348881166-…-2015684767","actualSid":"S-1-15-2-348881166-…-2015684767",
 "capabilityCount":0,"integritySid":"S-1-16-4096"}
```

**`launcherAsserted` — 启动器对自身行为的自报**
```json
{"handleListApplied":true,"inheritedHandleCount":3,"environmentBlockKeys":21,
 "note":"launcher self-report; not a measurement of the target"}
```

**`probe` — 目标进程内部产生（写到 `work/probe-report.json` 后读回）**
```json
{"appContainerSidMatched":true,"networkCapabilitySids":[],
 "environmentKeys":[…21 个键…],"environmentExact":true,
 "ownFileRoundTrip":true,"sentinelReadDenied":true,"sentinelWriteDenied":true,
 "loopbackRefused":true,
 "loopbackError":"dial tcp 127.0.0.1:64049: connectex: …"}
```

**字段值核对**：解析后的 `probe.environmentKeys`、`probe.loopbackError`、`probe.loopbackRefused` 与 `work/probe-report.json` 中相应值一致；这不是两个文件字节级一致性证明。顶层已无 `capabilityCount`。注意 `launcherAsserted.environmentBlockKeys` 在探针返回键时取的是目标报告数量，命名和自报注释不准确。

归档 JSONL 记录：`processExitCode=0`、`jobActiveAfterExit=0`、`jobEmptyConfirmed=true`、镜像 SHA 与钉值相同。`phase-complete.runtimePreserved=false` 与 `final` 中的 `true` 不一致：源码在 `phase-complete` 写出后才执行 defer；不能用前者推断最终资源状态。`final.environmentKeys` 仍是启动器生成的占位环境键，不是目标实测。
