## N1（P0：NTF-005 / NTF-007 / NTF-006 / NTF-001）

**migration `646_cr_execution_notice.{up,down}.sql`**（**不新增 FK/级联**，遵守仓库硬规则）：

```sql
CREATE TABLE cr_execution_notice (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id   UUID NOT NULL,
    cr_id          TEXT NOT NULL,
    cause_code     TEXT NOT NULL,
    audience       TEXT NOT NULL,          -- authorizer | maintainer
    dedupe_key     TEXT NOT NULL,          -- sha256(cr_id, cause_code, evidence_digest, audience)
    inbox_item_id  UUID NOT NULL,          -- 1:1 扩展，刻意不加 FK（同名表行由同一事务写入）
    state          TEXT NOT NULL DEFAULT 'pending'
                     CHECK (state IN ('pending', 'delivered')),
    delivered_at   TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX cr_execution_notice_dedupe ON cr_execution_notice (workspace_id, dedupe_key);
CREATE INDEX cr_execution_notice_pending ON cr_execution_notice (workspace_id, state) WHERE state = 'pending';
```

**为什么是 1:1 附表而不是给 `inbox_item` 加列**：fork 双周 rebase 时改上游表的冲突成本高；
附表和 Inbox 记录一一对应，是那条记录的扩展，**不是新增全局账本**（SC-NTF-005 的约束）。

**`internal/governance/execution_notice.go`**：

1. `noticeDedupeKey(crID, causeCode, evidenceDigest, audience) string` —— sha256，区分四种受众/原因组合；
   不同 CR 同根因**不互吞**（key 内含 `cr_id`）。
2. `buildNotice(event) (*notice, error)` —— 纯函数：结论 + 错误码 + canonical 证据链接 + 所需动作；
   **禁止贴整份 JSON**（含 `{`/`}` 连续块或超长即拒绝，返回 `NOTICE_BODY_VERBATIM_PAYLOAD`）。
3. `routeNotice(cause) audience` —— 额度/无进展 → `authorizer`；环境/凭据/部署/绑定 → `maintainer`；
   维护角色**不自动获得**业务授权（NTF-004 的反例断言就靠这条）。
4. `isSilentEvent(kind) bool` —— 正常节点 / ACK / 有进展的修复 → true，**不写 Inbox**，只留运行记录（NTF-001）。
5. `deliverNotice(ctx, tx, notice)` —— 同一事务内：`INSERT … ON CONFLICT (workspace_id, dedupe_key) DO NOTHING`
   拿插入结果；只有真正插入了才 `CreateInboxItem`，两者写同一 receipt；提交后发 `EventInboxNew`，再置 `delivered`。
6. `recoverPendingNotices(ctx)` —— 扫 `state='pending'`，按**同一 `inbox_item_id`** 重投（消费端幂等），
   不新建 Inbox 记录（NTF-007 的"可能重广播但不重复提醒"）。
7. 故障钩子（沿用既有 `…TestHook` 写法）：`notice-before-inbox` / `notice-after-commit` / `notice-before-mark`。

**测试**（`execution_notice_test.go`，`TestTC_NTF_001/005/006/007`）：
- 005：同原因+证据+受众跨提交重放并发 → 只有 1 条 Inbox；不同 CR 同根因 → 2 条；
  证据变化或受众变化 → 新 key，新通知。
- 007：三个边界各注入一次故障 → 不丢通知、不重复提醒、不重签授权、不重复计费、不回滚业务事实。
- 001：正常节点/ACK/有进展事件 → 无 Inbox 行，运行记录仍在。
- 006：`delivered` 之后再发生"新失败/证据变化/受众变化/交付" → 各生成新通知，不被旧 root 吞掉。

## N2（P1：NTF-002 / NTF-003 / NTF-004）

依赖 N1 的 `buildNotice` + `routeNotice`：三类事件（授权请求 / 需处置阻断 / 已交付）的文案与受众；
维护者通知必须带**已试路径**，且文案里不出现"请执行某命令"这类搬运（NTF-003）；
授权决定只发给有权者，剩余阻断与所需判断要写清（NTF-004）。
