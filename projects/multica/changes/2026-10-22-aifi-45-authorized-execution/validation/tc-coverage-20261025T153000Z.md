## 增量 7（同日 · RPR-007，D4 按建议实现）

**D4 采用“不新增 purpose”的路线**（我上一版计划里的 `purpose:'repair-extension'` 被自己否掉）：追加 = 同一 lineage 内一张
新的已签名 grant，`repair_limit` 写**新总额**，`supersedes_grant` 指向当前 tip；账本记 `applied_grants` 链。

| 情形 | 结果 |
|---|---|
| 新 grant 正确 supersede tip 且总额变大 | 应用：`limit` 6→8、`consumed` 不变、链加一条 |
| 同一追加 grant 重放 | `replayed:true`，链**不再加**、总额不变（追加只生效一次） |
| 用被取代的旧 grant 再准入 | `REPAIR_GRANT_SUPERSEDED`（不能把总额降回去） |
| 新 grant 但 `supersedes_grant` 不是当前 tip | `REPAIR_GRANT_CHAIN_INVALID`（链不连续不认） |
| 追加总额未变大 | `REPAIR_LIMIT_NOT_INCREASED` |
| 历史保留 | `applied_grants.limits = [2,4]`、`consumed` 三条 receipt 原文不动、`tip_grant_id` 指向新 grant |

## 增量 34（祖先目录逃逸：补接线正反例时发现的真实绕过）

### 缺陷

git 会**穿过**目录符号链接去枚举其内部文件：把授权前缀下的某个目录换成指向仓外的链接后，`git ls-files --others` 报的是 `src/leak/secret.txt`（链接内部的文件），链接本身**不会作为变更路径出现**。于是：

- 该路径字面上带授权前缀 `src/`，lexical 判定通过；
- 叶子 `src/leak/secret.txt` 经链接看是一个普通文件，`lstat` 判非符号链接；
- 结论是 `allowed: true`——**可以经链接把授权范围外的内容纳入核对并通过**。

## 增量 57（TC-RUN-010 前置阻塞核实：真实授权无法被敏感动作裁决消费）

### 核实到的事实（都给了证据行）

1. **`grant_json` 形状不一致**：真实签发端点 `execution_authorization_http.go:226-232` 写入的是 `recordJSON`，即 `ExecutionAuthorizationRecord` = `{schema, envelope:{key_id,payload_b64,signature}, source}`（`execution_authorization.go:195-200, 165-169`）。而 M003 的 `ResolveVerifiedGrantTx`（`execution_control_policy.go:52-90`）从 `grant_json` 顶层读 `limit/target/environment/repos/...`——真实记录里**没有这些顶层字段**，因此 `parsed.Limit < 1` → 返回 `ErrPolicyUnverified`。
2. **M003 的 policy 测试用的是扁平 `grant_json`**（`execution_control_policy_test.go:14-31` 直接 INSERT 一个 `{limit,target,environment,...}` 的 JSON），所以那些 leaf 全绿**不代表**真实签发的授权能进入该裁决。
3. **"缺专项无动作"未实现**：`ApplySensitiveActionTx`（`:122-131`）只校验 `req.Target/req.Environment` 与 grant 一致，**完全不看 `req.Kind` 是否在 `sensitive_actions[]` 清单里**。只要 target/environment 匹配，任何 kind 都能消耗额度。
4. **没有生产端点**：`grep -rn "sensitive" internal/governance/execution_authorization_routes.go cmd/server/router.go` 零命中；`ApplySensitiveActionTx` 只有测试调用，与 EVD-007 接线前同一形态。
5. tools 侧 `lib/execution-sensitive-action.mjs` 是**本地文件账本**（`ledgerDir(grant)/actions/<key>.json`），与服务端裁决不共用，`crctl sensitive-action` 不走 HTTP。

### 结论

- `TC-RUN-010` 的正向路径（精确专项授权正例只一次消费）当前**不可达**：不是"用例还没写"，而是"真实签发的 grant 进不了裁决器"。
- 只写拒绝侧用例（缺专项/对象变化被拒）在本期是 **vacuous**：因为正例根本不存在，拒绝侧全绿不能证明任何东西。按纪律不得据此计 PRESENT。
- 台账仍 **43/49**；`TC-RUN-010` 仍 MISSING。

## 增量 69（RUN-003 第三/四步：撤销竞态探针 + 入队门控用例与门控前移）

### 1. 撤销竞态探针（"持锁可线性化"的动态证据）

按 `postgres-row-lock-probes` 纪律做：只接受 `SQLSTATE 55P03`；`lock_timeout=300ms`，**不使用 statement_timeout**（否则 57014 会把"没锁住"伪装成"被拒绝"）；UPDATE 与 DELETE 各自独立夹具（无锁的探针会污染下一个：一个挪指针、一个删记录）。
- 钩子 `ExecutionAdmissionTestHook` 与既有 `ExecutionActivationValidationTestHook` 同形，在**持锁且已判定之后、effect 之前**调用。
- 两个叶子：`pointer update waits`（撤销的语句）、`referenced record delete waits`（head 记录删除）。均拿到真 55P03，耗时 0.35s/0.33s（与 300ms 锁超时吻合）。

- 负向断言：`tx == nil` 直接判失败（没持锁的探针什么都证明不了）；钩子未执行也判失败。
