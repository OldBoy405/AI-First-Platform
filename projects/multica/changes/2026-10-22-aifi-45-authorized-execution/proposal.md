## Why

现有 Runner、可信阶段审批、任务幂等与独立 reviewer 可复用， 但完整授权包、跨阶段累计修复、无进展停止、全阶段恢复派发和最小通知尚需配套合同。 已有代码 walker 或本地 registry 不等于部署运行时已接通，不能只改 prompt 宣称减负完成。

## What Changes

- 复用平台认证、审批记录与 Ed25519 传输，记录并绑定执行授权包，维护送达、crctl消费和实际执行的不同事实。
- Runner 唯一自动派发；以既有 run/node/task lineage 关联 tools 裁决的逻辑修复，恢复、并发与发布失败不双派或重复消费。
- 完成目标阶段的实际启动、wake、发现和恢复接线，联合校验 run/node/attempt/cycle/subject/模板版本及独立 reviewer。
- 按业务授权者或维护责任人分流异常，仅主动通知授权、需处置阻断及交付，未变化阻断重放不重复提醒。
- 与 tools 配套版本启用，新 CR 显式试点；旧 CR 保持 pin 与证据，显式迁移保留授权及历史消耗。

### Modified Capabilities

- **authorized-runner**：可信授权绑定、crctl裁决消费、唯一全阶段派发与恢复、证据身份和版本隔离。
- **attention-routing**：最小主动通知、阻断重放抑制、业务/维护分流及可查询运行记录。

## Success Criteria

- [ ] AC-1/2/8：充分授权普通请求自动推进；缺失、扩围或敏感动作缺专项授权时停止，作者和task-token不能自授权。
- [ ] AC-3/4/5：Runner遵守crctl额度与进展裁决，默认第7次不派发，连续两次无进展升级。
- [ ] AC-6：重复事件、恢复、崩溃、并发wake和发布重试不产生第二次逻辑修复或重复消费。
- [ ] AC-7：旧cycle/run/subject/模板证据只留历史，不推进当前执行。
- [ ] AC-9：交付必须有独立差异与可运行证据；真实UUID隔离及机械例外合同受验证。
- [ ] AC-10：维护异常有界恢复后通知维护者；授权变化通知有权者，不让业务方搬命令。
- [ ] AC-11：只主动通知授权、需处置阻断、交付；未变化阻断重放不重复提醒，新失败与重要变化不被吞。

- [ ] 普通授权、高风险、失败恢复三条路径通过真实认证入口和实际wake链的隔离集成测试；不以直接调用walker或假队列代证。
