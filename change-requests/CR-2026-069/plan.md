### 2.1 TASK-10 的完成边界（`FR-10` 约束下的显式口径，防 `deliveryIndexComplete` 永久不可达）

`dep-1` FR-8 第 1/5 项把 FR-8 的执行次数钉为「改造前一次 + **部署后**（14 天窗口）一次」，AC-17① 同样写作「合并前与部署后各恰好执行一次」。若把 TASK-10 的完成标志写成「部署后的 `after` 真实执行完成」，则该 TASK 只能在 merge 与部署之后才可能 `done`，而 `crctl task done` 仅允许 `status=developing` ⇒ `deliveryIndexComplete` 归档门禁永久不可达（正是 CR-2026-057 FR-10 要阻断的形态）。因此本计划把 TASK-10 的**完成边界**限定在 deployment 前可登记的事件：

1. `cr-cost.mjs after --window 14d` 子命令落地，且「14 天窗口」「`insufficient-sample` 终态」「目标桶 ≥20% ∧ 三项护栏不恶化」三项判定为**纯函数**并由 `test/cr-cost.test.mjs` 覆盖（含样本不足路径）；
2. AC-14 的真实冒烟记录（逐 Runtime 四类行为 + 每个 Runtime 一行 `check-install` 读数）落 `evidence/ac14-smoke.md`；
3. AC-20 的启用顺序记录（每个 Runtime 的「conformance 通过 + 真实冒烟通过 + 降级验证通过」前置证据链）落同一证据文件；
