# PRD — P2 三模式聊天 CR-B：D3 完整形态（队列条 + 撤回 + 停止 + 过滤开关）

> 依据：`docs/product/P2-三模式聊天窗口主体-交付切分.md` v2（d7e4ece）的 CR-B 节；
> 交互契约与字典锚点以《P2-三模式聊天交互设计》§3.2（共享队列指示）/§3.4（停止）/§2（三 tab 布局）为准。
> 前置 CR-A（CR-2026-006，v0.13）已交付：三 tab 骨架、Team Agent 消息流闭环（容器 Issue +
> 薄发送端点 + 满队 429 禁用态）；D1（CR-2026-004，v0.12）已交付队列治理后端全量能力。

## 1. 概述

**背景**：CR-A 交付后，Team Agent 面能发消息、看执行、满队被禁——但队列对用户仍是"黑盒"：
只有右侧 sidebar 的深度数字（D1 最小 UI），看不到**谁**在排队、排到哪了；排错了撤不回
（D1 撤回能力只有 API，无聊天入口）；跑歪了停不下（停止无 UI）；长流程刷屏时人看不清自己
关心的请求。本 CR 把 D3 补到交互稿定义的完整形态。

**本 CR 交付**（交付切分 v2 的 CR-B）：
1. **队列条常驻 + 展开列表**：Team Agent 面内「{count} 条排队」常驻指示，展开逐项显示发起人，WS 实时。
2. **逐项撤回**：发起人对自己的排队项「清除对话」，消费 D1 已收紧权限的 cancel 端点。
3. **停止**：发送者停自己（运行中或排队中）、Owner 停任意；停止后已生成内容保留、下一条自动开始。
4. **「只看 Agent 请求」过滤开关**：本地渲染过滤，防 Agent 过程消息淹没请求脉络（吸收 CodeBanana 双入口动机）。
5. **消息悬浮操作：复制**（回复/转发按切分文档 §0.4 排除）。

**修正切分文档的一处不准**：切分文档称 CR-B"纯前端，后端能力 D1 已全部交付"。实查 D1 交付的
`GET /api/projects/{id}/queue-status` 只返回 `{queue_depth, queue_limit}`，且任务响应体
`AgentTaskResponse` 不含 originator 字段、平台无项目级排队明细列表端点——**"展开列表逐项显示
发起人"缺数据源**。本 CR 含一处小后端读侧扩展（FR-6），只加读、不动 D1 写侧与治理语义。

**技术前提**：
- 撤回/停止全部消费既有 `POST /api/tasks/{taskId}/cancel`（CancelTaskByUser，originator-or-owner/admin
  对全部可取消状态一律适用）；服务端仅做 SDD DD-2 的一处权限调序（originator 先行放行），其余零改动。
- 队列实时性沿 D1 既有 WS 事件驱动（task:queued/cancelled/running/completed/failed 失效重取），不加新连接、不加新事件类型。

## 2. 用户故事

- **US-1** 作为**项目成员**，我希望在群聊里直接看到当前排队有几条、都是谁发起的，
  以便判断"现在发合适吗、前面还有谁"。
- **US-2** 作为**发消息排队的成员**，我希望能撤回自己还没开跑的请求（改主意/发错了），
  槽位立即让给后面的人，而不用去求 owner 或等它白跑一趟。
- **US-3** 作为**发起人**，我希望 Agent 跑歪时立即停止，已产出内容保留供参考；
  作为 **Owner**，我希望能停掉任何成员的任务以止损（误触发/死循环/占坑）。
- **US-4** 作为**看历史的成员**，我希望一键过滤掉工具执行过程噪音，只看"谁请求了什么、
  Agent 最终答了什么"，以便快速回顾群聊脉络；需要细节时一键还原。

## 3. 功能需求

| ID | 需求 | 优先级 |
|---|---|---|
| FR-1 | **队列条常驻**：Team Agent 面消息流与输入区之间固定位置常驻队列条，显示「{count} 条排队」（口径=D1 queue-status 的 queue_depth，即 queued+dispatched）；count=0 时收起为不占注意力的形态；随 WS 事件实时更新，无手动刷新 | P0 |
| FR-2 | **展开列表**：点击队列条展开排队项列表，逐项显示：发起人（头像+显示名，交互稿 `fromUser` 锚点）、请求摘要（触发消息截断）、状态（排队中/已派发）、入队时间；顺序与 claim 顺序一致（priority DESC, created_at ASC，owner/admin 插队项排前） | P0 |
| FR-3 | **逐项撤回**：列表中**自己发起且为 queued/dispatched** 的项显示「清除对话」按钮 → 调 `POST /api/tasks/{taskId}/cancel`；成功后该项移出列表、计数减一（WS 驱动）、其对应的群聊请求消息标注已撤回；他人项无按钮；竞态兜底：任务恰已完成时服务端幂等返回 200+原状态，前端据返回状态提示「任务已结束，无法撤回」（不静默）；非发起人直接调 API 被 403 | P0 |
| FR-4 | **停止**：① 自己的请求运行中时，输入区「发送」变「停止」（字典 `chat.agentGenerating`「Agent 回复中」）；② Owner 对任意运行中/排队中任务有停止入口（展开列表项 + 运行中工具卡区域）；③ 停止后已生成内容保留（interrupted 徽标，CR-A 已有渲染），槽位立即释放、下一条排队项自动开始；④ 普通成员停他人 → 服务端拒绝原样呈现 | P0 |
| FR-5 | **「只看 Agent 请求」过滤开关**：Team Agent tab 旁迷你开关；开启后消息流只保留用户请求消息与 Agent 最终结果，隐藏中间工具执行卡与过程性条目；纯本地渲染过滤——不触发网络请求、不动缓存数据、关闭即全量还原；开关状态按项目本地持久化 | P1 |
| FR-6 | **队列明细数据源（后端读侧小扩展）**：为 FR-2 提供项目级排队明细——预设方案：扩展 `GET /api/projects/{id}/queue-status` 增加 `items[]`（task_id、originator 显示信息、status、priority、created_at、请求摘要），既有 `queue_depth`/`queue_limit` 字段与语义不变（向后兼容，D1 的 ProjectQueueStatus 组件零改动）；权限=工作区成员可读（与现端点一致，交互稿"全员可见"）；明细含**全部占用项目队列的任务**（群聊发起 + Issue 页 @提及/quick-create 发起），不限容器 Issue；等价替代方案（独立明细端点）SDD 定案 | P0 |
| FR-7 | **消息复制**：消息气泡悬浮操作提供「复制」，取该条消息完整文本；本期唯一悬浮操作 | P2 |

## 4. 非功能需求

- **NFR-1 D1 治理语义零改动**：不修改容量守卫、插队、撤回的服务端语义；cancel 权限仅允许
  SDD DD-2 所述的一处调序（originator 先行放行，修复私有 agent 下"发得进撤不回"的不对称），
  其余 cancel 权限路径零改动；FR-6 仅新增读侧数据，queue-status 既有消费方行为不变。
- **NFR-2 四语文案**：全部新增 UI 文案 en/ja/ko/zh-Hans 四语，locale parity 测试全绿；
  沿用交互稿字典锚点（`fromUser`、`chat.agentGenerating` 等）。
- **NFR-3 零回归**：CR-A 已交付行为（发送/429 禁用/恢复、消息流渲染、草稿、模型选择器）不变；
  既有浮窗/全页 chat、Issue 页、任务详情页停止入口不受影响；不触碰 `useChatStore`。
- **NFR-4 实时性不加基建**：队列条/列表/停止态全部由既有 WS 事件驱动失效重取；不新建 WS 连接、
  不新增事件类型；断线重连后自动对账（沿 react-query refetch 既有行为）。
- **NFR-5 双端一致**：web 与 desktop（Electron 共享 `packages/views`）行为一致；mobile 不在范围。

## 5. 验收标准

- **AC-1**（FR-1/2，实时可见）双浏览器会话：A 发两条消息入队，B **无手动刷新**看到队列条计数变化与展开列表两项（发起人=A）；第一条开跑后计数减一、列表首项移出；顺序与 owner 插队语义一致（owner 项排前，真机验证）。
- **AC-2**（FR-3，撤回）发起人撤回自己的 queued 项：列表移出、计数减一、DB `status='cancelled'` 行保留（SELECT 审计核对）；撤他人项无入口且直接调 API 被 403；竞态兜底：撤回已完成项服务端幂等返回 200+原状态，前端据返回状态提示「任务已结束，无法撤回」（非静默）；Team Agent 为 private/受限可见 agent 时发起人仍可撤回自己的项（权限对称）。
- **AC-3**（FR-4，停止双权限）发送者停自己运行中任务 → 工具卡 interrupted 徽标、已生成内容保留、下一条排队项自动开始执行；Owner 停任意成员任务同样生效；普通成员经 API 停他人被拒。停止后无幽灵状态（队列计数、agent 状态、输入区状态三者一致）。
- **AC-4**（FR-5，过滤开关）构造含 ≥2 轮请求与多张工具卡的消息流：开启开关后仅请求与最终结果可见、无网络请求发出（DevTools 验证）；关闭后全量还原；开关往返多次内容与数量正确；刷新后开关状态保留。
- **AC-5**（FR-6，兼容）queue-status 扩展后：旧字段值与扩展前一致（同场景对拍）；D1 右侧 sidebar 指示与 CR-A 满队恢复行为回归通过；成员与 owner 读明细均 200，明细含 Issue 页 @提及发起的排队任务（非群聊来源覆盖验证）。
- **AC-6**（FR-7 + NFR-2/3）复制取回消息全文；locale parity 测试全绿；views/core 既有测试全绿。

## 6. 成功指标

- Team Agent 队列从"黑盒数字"变为"可见、可撤、可停"：排队/执行全程无需离开聊天窗口、
  无需求助 owner 或等待白跑，D1 交付的治理后端能力 100% 有了用户入口。
- 长流程群聊可通过过滤开关一屏回顾请求脉络，Team Agent 面具备日常高频使用的可读性。

## 7. 范围排除

- 消息回复（reply 线程）、逐条/合并转发、reaction → 分别按切分文档 §0.4 排除或归 **CR-G**。
- Private Ask / Discussion 内容面 → **CR-C / CR-D**；presenter 控制权（含"presenter 在时其他人排队/拒绝"语义变化）→ **CR-E**；门禁状态条/审批卡 → **CR-F**。
- 队列上限配置 UI（D1 已交付 settings 写入口，本 CR 不做管理界面）。
- 切分文档 §0.4 全部写死排除项（双入口、work-viewer、上下文用量、语音、mobile 等）继续有效。
