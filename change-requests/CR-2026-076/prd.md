# CR 执行闭环与门禁减负修订

## 1. 概述

### 1.1 问题与目标

当前需求来自 AIFI-54 的附件《Tools 统一优化实施方案 v3》（`tools-unified-cr-optimization-plan-v3.md`，attachment id：`01a111e4-4512-73ce-a553-51fe38b85d3e`）。附件中的历史复核指出：运行绑定依赖手工声明、任务 Git trust 遮蔽身份、评审落盘未包含实际提交、普通 BLOCK 回修收尾与线上合同不一致，造成跨节点反复中止；重复人工启动确认、全文／集合漂移冻结和无条件实现重放则增加形式性成本。

本 CR 在保留真实失败、授权、签名、并发和发布安全边界的前提下，以一个批准范围完成四个工作包：

1. 运行绑定、Git 身份、评审提交及普通 BLOCK 复评闭环。
2. G01～G04：合法本地信任贯通、默认开发启动减负、合法人类继续一次一 cycle。
3. G05/G06：同一工作项复用整个 Git tree 内容比较，决定继续或最小重验。
4. G07、既有红例、Windows 文档链扫描及真实安装生效收敛。

注册摘要按权威 `cr.md` 保留：

> 依据 AIFI-54 附件 tools-unified-cr-optimization-plan-v3.md，单个 CR 完成机器启动绑定、Git 身份保留、评审落盘与隔离提交恢复闭环；贯通合法本地信任、取消默认重复开发启动确认、合法人类继续一次一 cycle；G05/G06 同一工作项复用 Git tree 比较决定继续或最小重验，并收敛 CI 数量告警、既有红例、Windows chainCheck 与实际安装生效验证。复用现有状态、权限、事务、审计和发布流程，不新增执行器或影子账本；不关联其他 CR

## 3. 功能需求

### FR-01：机器保证启动前可信绑定

平台必须先消费 task 的可信正式 CR 关联；无直接关联时可消费当前来源 Issue 的唯一正式 CR 关联。唯一目标可继续预检；多个关联不得猜测，明确 CR 信号但缺少可确认目标时请求既有合法输入；普通无 CR 信号任务保持原行为。

明确目标后，复用当前 task 的可信项目资源和 workspace inspect，核验 authority、真实根、资源健康及阶段事实。显式声明与正式关联、可信资源或预检事实冲突，必须在进程启动及任何业务写入前拒绝，不静默覆盖。归档后的新任务重新取当前 authority，不沿用已删除 worktree。

保留显式 execution_context 兼容，补齐最薄的领取／Task 字段接线，在启动前生成、注入完整上下文；不扫描历史评论、按自由文本猜 CR、回退主机根列表或允许运行中任意 rebind。采用既有校验顺序，目标解析先于资源预检、冲突拒绝先于业务动作；同一失败只输出对应既有合同的确定结果。

### FR-02：任务 Git trust 保留用户身份

任务 trust 使用 Git 原生叠加方式，保留原配置与身份加载链，不为 safe.directory 替换用户全局姓名／邮箱，不修改用户全局身份，不设机器人身份兜底。提交所需身份不可用时，正常新操作须在账本写入前报告环境问题；已有未完成事务依原恢复合同处理，不把环境错误记成业务 BLOCK。

### FR-03：review-record 写入与隔离提交原子闭环

正常 PASS／BLOCK 均须经过前置核验、payload／对象校验、实际 write-set 构造、既有 durable transaction + CAS、仅本次实际 `files[]` 的隔离提交、事务完成，再发包含真实提交 SHA 的 outbox 后返回成功。

无 bump 分支提交实际 annotation 与 traceability；有 bump 分支将 review-loop 一同纳入实际 write-set。须检查整个 index 的隔离条件，不以“只 add 指定文件”证明隔离；不得夹带、丢弃作者或其他任务变更。

提交失败：非零返回，回滚本次账本写入与本次暂存影响，保留原评审 payload 及操作恢复依据；不发成功事件，不推进下一节点。commit 后崩溃：按已提交事实恢复，不重新评审或再次 bump，事件引用真正包含评审账本的 SHA。恢复固定原 CR、loop／cycle／attempt、被评审对象、verdict／blockers、payload、bump 意图及本次 write-set；同一次操作重投先识别原意图和完成事实，再决定恢复或幂等返回，输入或对象被替换不得当作同一次操作的新执行。幂等识别和指纹参与事实集合沿既有 review transaction／intent 契约落实于 SDD，不引入第二幂等账本。

恢复期间对象变化不得以新摘要重标旧 verdict；无法安全恢复则技术中止、报告，不伪造业务结论。上线前已有未提交评审须承接原结果受控完成，不重跑 `--bump-attempt`。本地提交不等于远端发布，远端仍由 checkpoint／push-progress 完成；advance 保持状态职责，不自动 add 整个 CR 或代提交作者代码。

### FR-04：普通 BLOCK 回修与 next 收尾一致

作者按现有 write-dev-plan → write-dev-tasks 增量同步／合法状态收尾 → 实际提交与 status／next 核验 → reviewer 链路完成回修。不要求全量重拆，不固定每轮提交次数，不让 write-dev-plan 冒用 write-dev-tasks 尚未完成的职责。

next 复用现有 subject／composite digest，判定优先级为：upstream 路线 → 耗尽等待合法人类继续 → 普通 BLOCK。普通 BLOCK 对象已变且作者已收尾时建议独立复评，不自动 PASS；对象未变继续回修。必需产物缺失／摘要不可计算走原修复或技术失败；无旧摘要不推断已修好。

工具、Skill、矩阵、模板及实际导入 instructions 必须同步，正式合同覆盖后关闭按 CR-ID／cycle 写死的临时例外。

### FR-05：G01/G02 合法本地信任贯通

仅对来源、stage 和归属合法的本地批准应用本地信任；来源缺失、未知或非法不得默认为本地。服务端签名批准维持原严格校验。

合法本地路径下，PRD／SDD／PLAN／TASK 正文漂移、TASK 集合增删、工具升级带来的证据定义变化，在当前必需产物齐全且结构合法时仅 warning，不自动撤销批准、重签或强制重审。合法存量文档 PASS 缺 `subject-sha256` 可提示继续，不补造摘要、新 PASS 或新签名。

必需文件缺失、索引／依赖／记录结构非法、最新真实 BLOCK、blockers 非空及真实测试失败继续硬阻断；历史 PASS 与 warning 不得覆盖它们。明确撤销批准或要求重审则走既有合法路线。保留原批准、subject 和 verdict 作追溯，不篡改历史证明等价。

gate、validate、next、批准和合入对同一事实必须一致。单独 warning 不触发 onFail、失败退出或后续同一漂移阻断；有真实错误时仍失败。保持既有返回字段类型，warning 使用现有可扩展形式，不新增专用提示次数／提交账本。工具不凭文档哈希替人推断业务范围扩展；操作者负责必要重审判断。

### FR-06：G03 默认 coding 取消重复开发启动确认

默认 coding 路径不再把独立 development-start human_approval／approve-dev-start 作为必经节点。首次 implement-code 前仍要求合法设计批准、PLAN／TASK 完整性、最新计划评审 PASS 且 blockers 为空、资源与实际 readiness，经现有 advance 合法进入 developing，不伪造 development-start 批准。

保留旧审批调用及历史记录兼容；同步 developing gate、next、合法转换、Skill、模板／索引、实际 comment 路径及 gate 投影消费者。不要求实现完整 coding Runner，不对运行中的旧图强行热换合同。本 CR 自身遵循当时合法有效的旧／新合同，不能自授减负。

### FR-07：G04 人类继续一次一 cycle

同一 cycle 的自动回修上限与历史 attempts 保留。耗尽后的继续依赖平台已认证人类触发事实及既有权限，不承认 Agent 自报人类或仅加 `--confirm`。

固定判定顺序：认证来源及权限 → 当前 CR／loop／耗尽事实 → 目标唯一性 → 原指令的重放／恢复事实 → 明确 cycle 转换。目标唯一时普通“继续”即可表达恢复意图；不唯一才询问，不要求固定措辞。

原操作在既有审计／恢复依据中固定认证来源指令、CR、loop、from-cycle、目标转换和原因；同一来源指令在同一明确目标操作范围只授权一次转换。失败可恢复同一操作，成功重投不得再增 cycle；下一次耗尽必须有新的人类指令，旧评论不能重解释为无限授权。新 cycle 不清真实 blockers，不代表业务批准。复用既有 reset、事务和审计，不另建票据服务、权限数据库或常驻调度器。

### FR-08：G05/G06 共用整个 Git tree 内容比较

两个消费目的共用一个内容比较缝：被评审／批准代码源与当前已提交源用于 G05；测试报告记录的源与同步后源用于 G06。代码资源来自既有仓库声明，独立代码仓比较整个 Git tree，包括代码、测试、README、配置，不设扩展名白名单或 codeRoot。

SHA 继续承担历史追溯与发布事务身份，不因内容等价抹掉版本信息。知识仓其他 CR 的已提交账本变化不算当前代码资源变化；当前 CR artifact 分别按合法本地和 server-approve 规则核验。多代码仓须对每个参与资源确定结论，任一不可判不得宣称全仓等价。

### FR-09：G05 合入对象与发布意图核验

合法本地路径代码 tree 相同时，可继续额外空提交等内容等价源推进，不仅因 HEAD 不同要求回实现。tree 不同须先更新测试／代码评审证据并执行必要的原代码确认，不能直接合入。当前本地 CR artifact 漂移按 FR-05 提示，必需产物、结构和真实失败仍检查。

server-approve 的签名、摘要／源绑定和归属维持严格合同，不转换为本地批准。workspace 健康、路径、仓集合、真实远端源同步、lease 和发布检查均不放宽。

新发布事务固定本次实际发布 source；已有产生副作用的 journal 按原意图及 source 恢复，后来的等价 HEAD 或文档变化不得改变进行中的发布对象。批准入口、verifyReleaseSubjects、mergeCr 远端源预检和后续 publish 相关消费者须一致，不仅放宽单个 helper。

### FR-10：G06 同步后的最小重验

保留 freshness 探测。实施前合法同步完成则继续尚未开始的实施；评审前同步后 tree 与有效测试源相同则继续现有评审接续，不因同步重复实现／测试；tree 改变则先走已有测试报告与代码复评节点，仅真实测试／评审失败才回 implement-code。

等价比较不替代有效报告、日志、真实退出码和 verdict，不把未执行验证宣称已测。dirty、分叉、冲突、同步失败或环境不匹配走已有失败合同，不猜测成功，不把技术中止计为业务失败。复用现有节点、freshness 输出和必要消费者，不加 CR 状态、完整执行器或后台重试。

### FR-11：代码源不可判时恢复或建立新证据

文档 PASS 缺摘要兼容不能类推为代码源缺失可直接等价放行。先沿已有读取／同步路径恢复原 Git 对象；仍不可判则建立新测试、代码评审及必要代码确认事实，不以当前 HEAD 补造历史 source，不伪造原代码批准，不无理由重做实现。

### FR-12：G07 数量下降告警与既有红例收敛

合法逐文件用例数低于登记基线改为 warning；必需文件零有效执行、少跑／未登记文件、文件集合不一致、加载失败、TAP 不可判／未收敛、真实未豁免失败，以及登记 schema、基线字段或既有例外结构／期限非法继续失败。例外只按当前有效既有合同消费，摘要不能将有效例外中的实际失败说成“所有测试通过”。

沿用 manifest、suite report、exceptions，显式维护登记，不自动改基线，不建数量审批流程。定点复现附件所述四个 summary 宿主环境例外，复用 baseEnv 隔离测试子进程，根因转绿后撤销对应例外；若现有登记已变化，报告当前事实与对应覆盖，不造新豁免。不在生产任务全局清可信绑定变量，不靠数量 warning 隐藏红例。保留已完成 D 两处 fixture 修复回归，不重复实施。

### FR-13：Windows chainCheck 真实扫描

本机路径文件名提取使用 `node:path.basename` 代替 `split("/")`，通过 docCount 和 Windows 原生嵌套路径断言证明真实扫描，避免空扫描假通过。使用现有测试入口，不加依赖或路径助手，不改 gate 表达式，不扩建文档链类型／规则体系。

### FR-14：实际发布生效与合法执行边界

复用维护来源的导入／发布流程，核对 CLI、daemon、Skill／instructions 及必要平台消费者实际取用版本；生产者先兼容新合同，再切消费者，核验桌面监督恢复后的版本事实。源码合入、构建成功或仓库镜像更新不单独算实际交付完成。

plan 须提前列明所需人类动作、责任方、窗口和可达入口；接受一次明确合法且有边界的人工启动前置，不接受逐节点人肉代跑。正式治理使用已发布、已验证入口，候选 CLI 仅用于隔离 fixture 或明确受控测试。稳定入口不可用则技术中止，不盲目重投。

工作包按运行／提交闭环 → 本地信任／流程减负 → G05/G06 共用比较／重验 → CI／小缺陷／实际生效推进，夹具和测试随对应行为同步。复用现有计划评审核对命令、模式、执行者、资源、人工前置及验收可达性，不另加预评审。技术中止修同一环境／事务且不重复 bump；真实 BLOCK 按正常回修。证据 ID 稳定，不机械重编号，交接依据实际产物、必要账本、状态、提交及规定发布事实，不只看 exit=0。

## 4. 非功能需求

### NFR-01：安全与权限

不放宽路径 containment、可信根、所有权、签名、CAS、lease、远端源、真实测试失败或人工审批身份边界。权限判断先于业务写入；错误输出遵循现有 CLI／平台合同的唯一状态／code，不以“任意 403 或 404”或不确定重试替代判定。本 CR 仅定点改变行为，不定义新 HTTP API、通用授权框架或第二执行入口。

### NFR-02：错误闭包与恢复

所有新增消费点须继承原错误体（现有 code、原因与可用的结构化 recovery），不新增同义错误码体系；SDD 必须给出到现有唯一错误出口的映射，并可通过当前原生入口验收：

| 错误类 | 结果及写入范围 | 调用方动作 |
|---|---|---|
| 输入／payload 解析或对象校验失败 | 非成功；零该次业务写入，不产生 PASS 或批准事实 | 修合法输入，不能原样盲重投 |
| 来源、权限、绑定、路径冲突 | 原既有拒绝 code；零业务写入，绑定冲突在启动前失败关闭 | 由合法来源／平台纠正，不清绑定或切执行器 |
| 操作重放输入冲突 | 不覆盖原意图、对象或历史结果；零新业务副作用 | 核验原操作，走既有报告／恢复入口 |
| 锁／CAS／事务失败 | 未完成部分回滚或按既有 durable recovery 固定恢复；不宣称业务成功 | 只按结构化恢复指令恢复同一操作 |
| review 提交失败 | 非零；回滚本次账本与暂存影响，保留原 payload／恢复依据；无成功事件 | 恢复同一次操作，不重评、不再 bump |
| commit 后完成／事件阶段中断 | 保留真实已提交事实，不将已成功提交当作零写入；重放不重复 commit／attempt | 按原事务恢复事件与完成事实 |
| dirty／分叉／冲突／环境或同步故障 | 原技术错误，不写业务 BLOCK，不绕过失败继续 | 原合法环境修复／同步／报告路线 |

### NFR-03：性能与最小实现

复用原生 Git tree 对象比较，等价场景不新增实现／测试轮次；不引入语义扫描、扩展名影响分析、常驻进程或额外依赖。性能验收以行为成本为准：相同 tree 的同步不会触发无理由重测／重实现，同一操作重投不会增加 cycle／attempt／提交。内部算法与字段编码归 SDD，不在 PRD 冻结实现细节。

### NFR-04：兼容性与审计

本地信任与 server-approve 路径严格分离；保留历史批准、SHA、subject、verdict、attempts、旧审批调用及进行中发布 journal 的原意图。保持既有接口字段类型、状态模型与 warning 扩展形式；生产者先兼容、再切消费者，旧运行图不强制热换。CR 状态及账本仍只由 crctl／对应 Skill 写入，不手工篡改。

### NFR-05：证据可信与跨平台

使用现有测试文件、fixture 和原生入口，先固化错误场景再最小修改；不冻结无关措辞、不建设额外测试平台。文本哈希／跨行解析先规范化 CRLF 为 LF，跨行解析失败硬报错，不能返回空集合假通过。Windows basename 验证必须包含非零 docCount 与原生嵌套路径。测试报告如实列出未测、例外及环境技术中止；不拿模型自报、源码存在或构建结果代替真实生效证据。

| AC-02 | FR-01 | 仅当前来源 Issue 有唯一正式 CR 关联时可复用；多个目标不猜测；普通无 CR 信号任务不退化。 |

验收执行要求：使用现有原生 CLI、评论路径、gate 投影与测试入口；候选逻辑仅在隔离 fixture／明确受控测试验证，不要求尚不存在的完整 coding Runner 回放。同一合同域本轮可查问题尽量列全，技术中止与真实业务 BLOCK 分开；不规定必须一轮 PASS、不增评审计数层。各 AC 的实际命令、模式、资源、责任与人工前置由计划评审确认可达，测试与线上证据如实区分。

## 6. 成功指标

1. 功能覆盖：AC-01～AC-24 均有可归因的回归或真实生效证据；未测、技术中止和有效例外逐项明示，不能填为 PASS。
2. 安全不回退：非法绑定／来源／签名、缺件／结构非法、最新真实 BLOCK、真实失败、发布对象漂移的负向案例均继续拒绝或沿原技术失败路线中止。
3. 幂等成本：同一已完成 review 操作重投新增 attempt／提交为 0；同一成功人类继续指令重投新增 cycle 为 0。
4. 减负一致：合法本地文档漂移不产生自动重审／重签或 warning-only 失败；默认合法首次实施无重复 dev-start 确认；相同 tree 同步不产生无理由实现／测试重放。
5. 实际交付：整体评审、代码确认与规定发布完成，CLI／daemon／线上合同实际版本可核验，并有安装后新 run 的目标行为证据；仅源码、镜像或构建不能使该项达成。

## 7. 范围排除

- 不拆分 G05/G06 或小缺陷为新 CR，不重新注册四个工作包，不关联其他 CR，不复用历史审批作为本 CR 授权。
- 不新增数据库、影子账本、权限框架、授权票据服务、通用提交服务、万能恢复器、新 CR 状态、多 Pipeline／完整 coding Runner、常驻调度器或后台重试服务。
- 不采用 v2 本地正文冻结；不把本地信任扩展为未知／非法来源放宽、server-approve 放宽、自动 PASS、隐藏最新 BLOCK／测试失败、缺件放行或代码源缺失等价放行。
- 不新增 codeRoot、文档扩展名白名单、语义哈希、智能测试影响分析、额外测试平台或数量变化审批流程。
- 不修改用户全局 Git 身份，不增加机器人兜底，不在生产任务清／覆盖可信绑定，不靠运行中 rebind 或第二执行器绕过 authority。
- 不把 advance 扩为作者／全目录自动提交；不把本地评审提交当成远端发布，不改写进行中发布 journal 的原意图和 source。
- 不重复实施已完成 D 两处 fixture 修复，不固化旧测试总数、评论数或逐字提示，不全局顺移既有证据编号。
- 不额外增加预评审，不对运行中旧 coding 图热换合同，不用本 CR 未批准／未发布的新门禁自我授权，不以逐节点人肉代跑代替正式闭环。
- PRD 不展开内部指纹编码、字段键序、全量错误码枚举、事务实现算法；由 SDD 对照既有能力定点设计。本轮需求编写不写 specs／delivery，不修改注册输入、受控审批或状态账本。
