AI-FIRST 研发协同平台 · 产品介绍

把"超级个体"的能力，稳定转化成"超级团队"的能力

AI-First 平台不是又一个更好看的 AI 工作台，而是企业把个人 AI 效率转化为组织级、可信、可复用交付能力所需要的新基础设施——不做锦上添花的效率工具，而是 AI 进入正式研发交付后，团队必须补上的新基础设施—— 知识有主事实源，流程有状态机，Agent 有职责和权限，质量有门禁和证据，度量看结果不看热闹。

01为什么是现在：AI 放大的是系统，不是个人

很多团队现在真正的问题，不是没有会用 AI 的人，而是团队里已经有人被 AI 放大了，但组织系统没有跟上。 AI 进来以后，代码、需求、原型、测试都变快了太多——但如果知识、流程、质量仍然靠人肉传递， 个人效率提升得越快，团队级损耗就越明显。这不是自然升级，而是把旧研发系统的短板放大了。

02两条路径的交汇点：超级个体自下而上，超级团队自上而下

超级个体不是全栈岗位，而是完整交付能力——能力边界不再由岗位定义，而是由目标、上下文和工具链定义。 一个后端工程师借助 Agent 可以完成从需求理解、影响面分析、方案设计、代码实现到测试补全、发布检查的完整闭环。 但超级个体只是起点：如果他的 Prompt、检查清单、失败经验只留在自己电脑里，团队不会真正进化。

管理者在这个过程中真正要做的四件事——定清边界（哪些事 Agent 做、哪些事人判断）、管好事实（可追溯）、 卡住质量和安全（门禁前移）、推动平台化——正好对应平台的四组能力：Agent 执行模式（Ask-only/Coding）、事实底座、质量门、组织智能看板。

03六大核心能力：平台如何逐一兑现

一个 AI-First 研发协同平台至少要具备六类核心能力——本平台按此框架逐项对照实现，无一空缺。

核心能力要解决的问题本平台的实现
① 事实源能力PRD 在飞书、设计在 Word、接口约定在群聊——Agent 再强也只能靠猜 Git 权威事实源：specs/(PRD/SDD/traceability)、delivery/(任务/发布)、change-requests/(在途变更)、docs/(探索型知识)四目录契约
② 超级个体协同层高手的工作过程只留在自己电脑里，团队不会真正进化 Skill Market（私有→组织→公共三级发布）+ 资产元数据卡（适用场景/依赖/权限/失败处理）+ 会话一键导出 Skill 草稿 + 资产复用率进成熟度看板
③ 流程编排能力看板只有"待办/进行中/已完成"，AI 不知道什么时候能做什么 CR 16 态门禁状态机，每步有 trigger / gate / 产物 / 回写规则；8 条 Pipeline 承载常用流程
④ Agent 工作单元能力Prompt 只是话术，容易失效；Agent 需要明确职责与工具权限 9 个角色化 Agent（规划/需求/开发/评审/交付/竞品/知识/客服 + 系统编排器）+ 每项目专属 Agent + A2A 跨项目协作
⑤ 质量与安全护栏能力AI 写得更快，但没有证据链就没法进入企业级研发主链路 5 道质量门（文档/设计/测试证据/代码/规划）+ 签名审批（Ed25519，批后改证据即失效）+ 受控 git 白名单 + AI 行为审计
⑥ 场景视图与度量能力不同角色看到的不该是同一组信息；不能只统计调用次数 场景工坊（需求工坊/质量中心/效能驾驶舱）+ AI 成熟度看板五维十指标 + 治理板块 + 交付效能板块
一句话立场：这类平台的核心，不是"AI 能不能干活"，而是"AI 干活能不能被团队信任、复用、追溯和持续改进"。 常规 AI 工具看单次产出好不好，研发协同平台要看整条交付链有没有变好。

04五层技术架构：桌面优先 · 事实源留在本地 · 薄服务

面向企业研发、私有代码、数据安全要求较高的场景，本平台采用"本地执行、隐私优先"路线—— Agent 跑在用户自己机器的 daemon 上，平台只做编排、协作与治理，服务器永远看不到用户的模型凭据与源代码。

图 4-1　AI-First 平台五层架构：本地事实源 + 薄服务治理 + Agent 执行平面（SVG）

业务事实尽量留在客户自己的 workspace，平台做工作台、编排、治理、Wiki 消费层和度量；AI 执行尽量靠近代码和文档现场， 而不是把所有上下文复制到一个远端黑盒里。这是本平台架构选择背后唯一的原则。

05核心设计理念

AI-First 平台最容易被误解成"更聪明的工具集合"。但真正难的是把研发系统中那些过去靠人默契维持的东西， 变成 AI 能运行的工程结构——知识要有主事实源，流程要有状态机，Agent 要有职责和权限，质量要有门禁和证据，度量要看结果不看热闹。

核心设计思想与理念

🤖

AI 是队友，不是工具

每个项目自带一个与项目同名的专属 Agent，作为团队的一等成员参与代码生成、评审、执行与协作，而不是一个被动等待指令的问答框。 Agent 有自己的身份配置（Basic Info 七维：Agent/Soul/Identity/User/Memory/Teams/Tools）、有跨会话记忆、有明确的职责边界—— 你不是"打开一个工具"，而是"叫醒一个团队成员"。

💬

沟通发生在执行发生的地方

核心设计原则——讨论、AI 执行、代码环境必须共享同一个"项目容器"， 而不是分散在群聊、邮件、Jira 与 IDE 之间。三模式聊天（Team Agent 共享执行 / Private Ask 个人探索 / Discussion 人类讨论）物理分离又共享同一上下文； Discussion 里的一段讨论可以被直接合并转发给 Team Agent 作为执行任务的上下文——沟通不需要先"翻译"成工单再排队，讨论本身就是任务的起点。

🔒

本地执行、隐私优先

Agent 运行在用户自己机器的 daemon 上，模型凭据、源代码、执行痕迹都不出内网；服务器只做编排、协作与治理，永远看不到用户的实际工作内容。 这不是性能优化，而是安全边界的第一性选择——用 AI 强控人、压缩个人隐私空间的路线，是本平台明确不走的路。

🧬

多 Agent 智能编排

Agent 智能编排提供的不只是"跑代码的 daemon"，而是一整套多 Agent 编排底座—— pkg/agent 后端抽象统一了 14 种 CLI 子进程包装（Claude Code/Codex 等）；claim SQL 的原子语义让同一 Agent 天然串行、 不同 Agent 天然并行，无需分布式锁；A2A 协议让一个项目的 Agent 可以被"借"到另一个项目执行任务，50 槽 FIFO 队列保证任务不丢不乱序； Discussion Coordinator 只协调不执行，负责把人类讨论路由给合适的执行 Agent。这套编排能力是"Agent 作为自主队友"得以规模化的工程基础。

📊

度量而非监控

AI 成熟度看板用来量化组织转型，但设计上刻意反 Goodhart—— 数量指标（Token 强度、AI 渗透率）与质量护栏（门禁通过率、EVIDENCE_DRIFT）强制同屏呈现，个人排名默认关闭，只有部门聚合默认可见。 这不是一个盯着每个人敲了多少字的监控系统，而是一面镜子：告诉组织"AI 原生转型走到哪了"、"交付有没有真的变好"， 而不是把 Token 消耗这种行为数据异化为绩效竞赛的弹药。

结构化设计：把默契变成工程结构的六个设计

📚

可信知识底座

三类知识分级——交付关键知识进 Git 强治理基线，过程态知识留在 CR 目录待稳定回写， 探索型知识（竞品/访谈/纪要）可被 Wiki 消费但不强制入基线。"Git 负责让事实可信，Wiki 负责让知识好用"。高频问答经知识晋升巡检回写事实源。

🌱

超级个体协同层-能力资产化

过程记录（会话/执行记录可见）+ 资产沉淀（Skill Market）+ 复用授权（元数据卡：场景/依赖/权限/失败处理） + 贡献度量（资产复用率进看板）：会话可导出 Skill 草稿、资产带元数据卡（场景/依赖/权限/失败处理）、复用进度量（SII 资产复用率）、发布=授权+敏感扫描——高手的工作方式可以被看见、复用、验证和扩散。

🔀

工程可追溯是第一性买点

CR 16 态门禁 + 五道质量门 + traceability 五段链路 + 漂移检测。从 drafting 到 archived， 每步有 trigger、gate、产物、回写规则。人可以临场变通，Agent 需要明确轨道。

🛠

Agent · Skill · 受控工具

Skill 沉淀稳定做法，Agent 承担角色化任务，MCP 连接外部工具， Command（斜杠命令）把高频动作变成入口；git 操作走白名单受控工具，AI 能力越强，权限边界越要清楚。

🛡

质量门与度量系统

五类质量门（文档/设计/代码/追溯/AI 行为）前移到流程节点上； 度量重建为 Lead Time、Review 负担、变更失败率、资产复用率，而不是只统计"用了多少次 AI"。

🧭

场景工坊

产品、架构、开发、测试、管理者看到的不是同一组信息—— 需求工坊、质量中心、效能驾驶舱按角色组织同一份数据的不同投影，AI 内嵌在工作场景里，而非工作之外再挂一个聊天入口。

关键纪律：AI First 不是给 Agent 无限自由，而是给它足够清晰的责任、上下文和护栏。 AI 能力越强，权限边界越要清楚——否则你会得到一个很能干、也很容易越界的同事。

06产品要实现的目标

七个层次的目标，每一个都配了可度量的成功标志——不是"我们希望团队更高效"这种无法验收的愿景， 而是能在系统里查得到的数字。

层次目标可度量的成功标志
协作团队在同一平台完成需求→设计→编码→回写→归档全流程，不再靠 IDE 各自为战一条需求端到端跑完四条主 pipeline，产出完整 traceability
治理AI 产出的代码有证据链、过质量门、可追溯、可回滚门禁一次通过率可度量；绕过流程的直接提交（bypass-commit）可被检测
包容非技术角色（PM/设计/QA/客服）无门槛参与轻量档 runner 上线后，非技术用户可用只读/文档 Agent 提需求、查文档、审批、参与讨论
智能Agent 作为自主队友执行任务，人类专注决策Team Agent 单一写者 + 队列跑通；A2A 跨项目协作可用
组织管理层能看到 AI 原生转型的量化进度与交付价值AI 成熟度看板五维十指标 + 治理板块 + 交付效能板块（Lead Time/Review 负担/变更失败率）上线，周报 Autopilot 按 AI 净价值框架产出诊断；M3 后 3 个月完成四类指标价值复盘
知识个人经验沉淀为可复用组织资产；知识可被问答消费并回流事实源资产复用率可度量；LLM Wiki 问答带出处；高频问答自动触发知识晋升 Issue
自主平台可企业内网自托管，不依赖外部 SaaSDocker Compose / Helm 两条命令内网起全栈

这七个目标合在一起回答的正是 §01 提出的问题：怎么把"人才密度 × AI 杠杆"的分子做大之余，把"组织摩擦"这个分母持续压低。

08AI 净价值与度量：看结果，不看热闹

判断一个 AI-First 平台有没有价值，不看它接了多少模型、做了多少 Agent、页面多炫， 而看它有没有持续降低组织损耗。度量框架：

AI 净价值 = 时间收益 + 质量收益 + 知识收益 + 风险收益 − 模型与重跑成本

管理口径框架，非精确财务核算——早期人工估算，后续由 Pipeline 执行数据、Agent 执行记录与质量门结果自动统计

若这些问题没有改善，说明团队只是买了工具，或者多了几个超级个体；若持续改善， AI-First 平台才算真正开始落地——这也是平台 M3 上线满 3 个月后的价值复盘验收项。

09差异化定位

市面上"半个此类"的优秀产品各有所长，但对企业级大型软件研发团队而言仍显不足——本平台的定位是把这些能力 综合进一个面向产品、设计、研发、测试、发布、运维、管理者全员的正式交付系统。

维度Multica 类协作层Devin 类自治工程师本 AI-First 平台

主要对象多个编码 Agent、任务、issue、workspace单个或多个软件工程任务产品、设计、研发、测试、发布、运维、管理者
知识治理偏任务和技能层偏代码仓库与执行过程主事实源 + Wiki 消费层 + 知识晋升回路
流程治理issue 生命周期 + 任务队列任务执行过程 + 人工接管需求→设计→研发→测试→发布→复盘全流程状态机
质量治理依赖任务状态与团队 Review依赖测试、PR、人工验收5 道质量门 + 证据链 + 签名审批 + AI 行为审计

10结语：超级团队的本质是受控放大

AI 会放大已有系统。事实混乱，它放大混乱；流程松散，它放大松散；质量薄弱，它放大风险。 但如果团队有统一事实底座、AI First 工作平台、质量门禁和数据安全治理，AI 也会放大这些能力。

超级团队的本质：不是每个人都更快，而是整个团队在受控系统里更快、更稳、更可持续。 AI First 是执行方式的变化，不是责任主体的变化——AI 可以优先执行，系统必须完整留痕，但最终判断和结果责任仍然在人和组织这里。

这正是本平台存在的理由：不做锦上添花的效率工具，而是 AI 进入正式研发交付后，团队必须补上的新基础设施—— 知识有主事实源，流程有状态机，Agent 有职责和权限，质量有门禁和证据，度量看结果不看热闹。
